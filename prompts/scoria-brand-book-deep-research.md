Scoria Brand Book

Version: 0.1
Use case: OSS identity, landing page, docs, Hex package, Phoenix admin UI, dashboards, eval workbench, trace explorer, marketing copy, UX microcopy, logo/collateral direction.
Core brand idea: Volcanic clarity for production AI systems.

⸻

0. Important naming note

Scoria is a strong name, but do not brand it as “Scoria AI.” A quick collision screen surfaced an existing ScoriaAI / Scoria AI GitHub presence describing itself as a decentralized AI agent framework, plus unrelated software/projects named Scoria, including a Python molecular-modeling library and a Rust TUI components crate. This does not kill the name, but it means the public identity should be Scoria with a precise descriptor such as “AI ops for Phoenix”, not “Scoria AI.” Do a final Hex, GitHub, domain, and trademark check before publishing.  ￼

The category also needs visual separation from existing AI observability/eval platforms. Langfuse positions around tracing, prompt management, evaluation, and experimentation; Arize Phoenix is an open-source LLM tracing and evaluation platform; Braintrust emphasizes turning production traces into evals and comparing prompts/models. Scoria should feel more Phoenix-native, OSS, operational, earthy, and tool-governance-oriented, not like another generic blue-purple AI SaaS dashboard.  ￼

1. Brand foundation

1.1 Name

Scoria

Pronunciation: SKOR-ee-uh
Preferred casing: Scoria
Package/module casing: :scoria, Scoria
Avoid: ScoriaAI, Scoria AI, SCORIA, Scoria Platform

Scoria is a dark, vesicular volcanic rock: black, dark gray, brown, purplish red, or deep reddish brown, with visible bubble-like cavities called vesicles. That physical reality maps unusually well to this library: traces, spans, tool calls, evals, prompt versions, approvals, and datasets are the “holes” and internal structure inside an AI application. The brand should use that metaphor: AI systems are porous; Scoria makes the structure visible.  ￼

1.2 One-liner

Scoria is the Phoenix-native AI ops layer for tracing, evaluating, replaying, and governing LLM apps.

1.3 Short description

Scoria gives Phoenix teams a batteries-included runtime, trace store, eval workbench, prompt registry, MCP/tool governance layer, and LiveView operator UI for production AI features.

1.4 Positioning statement

For Phoenix developers building chat, copilots, RAG, tool-using agents, or MCP workflows, Scoria provides the missing production-quality layer: traces, evals, prompt versions, replay, cost/latency visibility, tool approvals, and regression gates, all wired into Phoenix, Ecto, LiveView, telemetry, and OTP.

1.5 Tagline options

Primary:

Trace the run. Prove the change. Ship the agent.

Alternate:

AI ops for Phoenix apps.

More technical:

A Phoenix-native control plane for LLM traces, evals, prompts, tools, and MCP.

More poetic:

Make the fire inspectable.

Do not use as the main tagline:

“The AI platform for everything.”
“Autonomous agents for Phoenix.”
“LangSmith for Elixir.”
“Phoenix AI.”
“The future of AI apps.”

Those either overclaim, collide with adjacent platforms, or make the project sound generic.

2. Brand personality

2.1 Brand archetype

The field engineer.

Scoria is not a magical assistant, a sci-fi robot, a hypergrowth SaaS mascot, or a luxury developer tool. It is a practical field kit for people who need to ship, debug, inspect, and improve AI systems under real constraints.

Scoria should feel like:

* An SRE who understands evals.
* A Phoenix maintainer who cares about DX.
* A field geologist mapping a volatile system.
* A control room that is calm during incidents.
* A lab notebook that can be audited.

2.2 Personality traits

Trait	Meaning
Grounded	Claims are evidence-based. UI shows traces, scores, costs, versions, and policies.
Composed	The product stays calm even when a run fails, a tool call is blocked, or an eval regresses.
Operator-grade	Designed for production debugging, not demos only.
Open-source practical	Clear docs, copy-pasteable examples, transparent defaults, no corporate fog.
Volcanic, not fiery	Heat, pressure, cinder, rock, ash, and texture are allowed. Flames, lava gimmicks, and phoenix birds are not.
Technical but humane	Uses real terms: trace, span, scorer, baseline, policy. Defines them clearly.

2.3 Brand principles

1. Evidence over intuition

Every claim should point to a trace, eval score, baseline, cost number, prompt version, dataset item, or policy.

2. Visible structure

Do not hide the system behind “AI magic.” Show the run tree. Show tool calls. Show approvals. Show what changed.

3. Production before spectacle

The landing page should sell reliability, replay, governance, and regression prevention before “cool agents.”

4. Phoenix-native, not Phoenix-branded

Scoria is built for Phoenix, but the brand should not rely on Phoenix orange, phoenix birds, fire icons, or “Phoenix AI” naming. This avoids confusion with both the Phoenix web framework and Arize Phoenix.

5. Calm heat

The visual system can be warm, dark, volcanic, and high-contrast, but it should never become aggressive, apocalyptic, or crypto-coded.

3. Brand narrative

3.1 Core story

AI apps are porous systems.

A single assistant response may contain prompt rendering, model calls, tool calls, retrieval, guardrails, approvals, retries, stream events, eval scores, cost records, and user feedback. Most frameworks show only the final answer. Scoria exposes the cavities inside the run.

Like volcanic scoria, the product identity is dark, textured, pressure-formed, and full of visible internal structure. The metaphor is not “fire is cool.” The metaphor is:

Under pressure, volatile systems leave structure behind. Scoria helps Phoenix teams inspect that structure, learn from it, and ship safer changes.

3.2 Brand promise

Scoria makes AI behavior observable, evaluable, replayable, and governable by default.

3.3 What Scoria is

* A Phoenix-native AI ops layer.
* A trace-first runtime.
* An eval flywheel.
* A LiveView control plane.
* A prompt/version registry.
* A tool and MCP governance layer.
* A production debugging kit.

3.4 What Scoria is not

* Not another generic LLM client.
* Not a black-box agent framework.
* Not a hosted SaaS dependency.
* Not a chatbot skin.
* Not “AI magic.”
* Not a replacement for every Elixir AI library.
* Not a Phoenix-branded clone of existing tracing/eval products.

4. Visual identity

4.1 Visual keywords

Use these words as direction for logo, site, UI, and collateral:

Basalt. Cinder. Vesicle. Trace. Pressure. Ash. Strata. Glow. Cutaway. Core sample. Field notes. Control room. Lab bench. Tool approval. Run tree. Regression gate.

Avoid these words as primary visual direction:

Sparkles. Brain. Robot. Wizard. Explosion. Fireball. Phoenix bird. Neon AI cloud. Cyberpunk. Magic wand. Crypto. Black-box oracle.

4.2 Logo concept

The Scoria logo should be a porous volcanic mark: a compact rock/cinder silhouette with negative-space vesicles. The vesicles can subtly align like trace nodes, dataset dots, or tool-call spans.

Recommended mark structure:

* Irregular rounded polygon or cinder chunk.
* 5–9 negative-space holes.
* One larger “core” vesicle.
* A few smaller cavities arranged like a trace tree.
* Slight asymmetry.
* Geometric enough to render at favicon size.
* Organic enough to avoid looking like a generic SaaS glyph.

Best logo directions:

1. Cinder Mark
    A small scoria fragment with holes. Best for favicon, package icon, docs sidebar, GitHub avatar.
2. Trace Vesicle Mark
    A porous rock where the holes form a subtle run tree: root span → LLM span → tool span → eval span.
3. Cutaway Cone Mark
    A simplified scoria cone or basalt cross-section with visible voids. More distinctive, slightly less compact.
4. Aperture/Vesicle Mark
    A circular central cavity surrounded by smaller cavities. Works well for “observability” and “trace explorer.”

Do not make the logo:

* A phoenix.
* A flame.
* A volcano eruption.
* A robot head.
* A brain/circuit.
* A sparkle cluster.
* A chat bubble.
* A generic hexagon.
* A literal Elixir droplet.

4.3 Wordmark

Preferred wordmark: Scoria

Typography: IBM Plex Sans SemiBold or Medium. IBM Plex Sans is a neutral, friendly grotesque with a broad family, which fits an OSS technical brand better than a decorative display face.  ￼

Wordmark treatment:

* Title Case: Scoria
* Tight but readable tracking: -1% to 0%
* Avoid all caps except tiny metadata labels.
* Avoid lowercase-only scoria for the main brand; reserve lowercase for package names.

5. Color system

The color system should be dark-first, volcanic, earthy, and high-contrast. Scoria should not look like the common AI palette of electric blue, violet gradients, and glassmorphism. It should look like a serious Phoenix-native engineering tool with warmth and texture.

5.1 Color strategy

Use color in this ratio:

* 70% neutrals: basalt, ash, graphite, pumice.
* 15% primary warmth: scoria red, ember, molten.
* 10% functional accents: olivine, fumarole, sulfur, lava.
* 5% texture/atmosphere: gradients, diagrams, subtle vesicle patterns.

The natural source palette is justified by scoria’s real dark, vesicular, reddish-brown/black character.  ￼

Use for landing pages, docs, UI, navigation, tables, buttons, forms, and README graphics. IBM Plex Sans works because it feels technical without being sterile, friendly without being cute, and has enough range for product UI and documentation. Recommended weights:

* 400 Regular: body
* 450/500 Medium: labels, nav, buttons

7. Voice and writing system

7.1 Voice formula

Calm + exact + useful.

Scoria should sound like a maintainer who has seen production incidents and wants to help you prevent the next one.

7.2 Voice principles

1. Say what happened

Bad:

Something went wrong.

Good:

The run failed during lookup_order. The tool returned a 403 for actor usr_184.

2. Prefer evidence verbs

Use:

* traced
* scored
* compared
* replayed
* promoted
* gated
* approved
* denied
* redacted
* sampled
* exported
* resumed

Avoid:

* magically understood
* thought
* dreamed
* unleashed
* hallucination-free
* autonomous intelligence
* revolutionary
* 10x everything

3. Do not anthropomorphize the model

Bad:

The agent is thinking.

Good:

Running support_agent: rendering prompt, calling model, waiting for tool result.

Bad:

The AI forgot your policy.

Good:

The rendered context did not include refund_policy@v7.

4. Do not expose hidden chain-of-thought

Use visible process summaries:

Scoria recorded 6 steps: prompt render, model request, tool call, retrieval, final model request, output guardrail.

Avoid:

Here is the model’s private reasoning.

5. Make safety and governance normal

Tool approval should feel like part of the workflow, not a scary emergency.

Bad:

Danger! AI wants to take an action!

Good:

Approval required: create_refund will issue a $74.00 refund.

7.3 Tone by context

Context	Tone
Landing page	Confident, concrete, low-hype
README	Direct, useful, fast to scan
HexDocs	Precise, example-heavy
Dashboard	Calm, compact, operational
Alerts	Specific, non-alarmist
Error messages	Diagnostic, actionable
Eval reports	Evidence-based, comparative
Security docs	Conservative, explicit
Release notes	Maintainer-like, transparent

7.4 Word bank

Preferred words

run, trace, span, step, score, dataset, baseline, gate, prompt version, tool policy, approval, replay, regression, redaction, cost, latency, quality, operator, control plane, LiveView, Phoenix-native, Ecto-backed, telemetry

Use sparingly

agent, workflow, autonomy, memory, judge, intelligence, platform

Avoid

magic, sparkles, revolutionary, sentient, brain, oracle, copilot for everything, AI employee, hallucination-proof, fully autonomous, set and forget

7.5 UX microcopy examples

Empty state: traces

No traces yet.
Run an agent, chat response, eval sample, or MCP request and Scoria will record the steps here.

Empty state: datasets

No dataset items yet.
Promote a production trace or add a test case manually to start building a regression suite.

Run status

State	Copy
queued	Queued
running	Running
streaming	Streaming response
waiting_for_approval	Waiting for approval
retrying	Retrying attempt 2
completed	Completed

Buttons:

* Approve tool call
* Deny
* View trace
* Open policy

Buttons:

* Compare runs
* Open failed samples
* Keep baseline
* Promote candidate anyway

Replay

Scoria will keep the original run unchanged.

7.6 Documentation style

Docs should prefer:

{:ok, run} =
  Scoria.run(MyApp.AI.SupportAgent,
    input: "Can I get a refund for order A123?",
    actor: current_user,
    thread_id: thread.id
  )

Then explain:

This creates a run, emits telemetry, stores a trace, streams events if configured, and links the output to the prompt version used.

Do not write:

With one magical line, your AI becomes production-ready.

Dark-first.

Trace explorer is the signature UI. Make it beautiful and legible.

Trace UI rules:

* Display hierarchy with indentation and connecting lines.
* Use time bars for duration.
* Use icons only as secondary cues.
* Always show status text.
* Always show duration.
* Always show model/tool/prompt version where relevant.
* Collapsed spans should still show cost, latency, status, and child count.
* Errors should expand to the failing span, not just the root run.

8.9 Eval workbench visual language

Eval UI should feel like a score lab, not a leaderboard.

Show:

* Current candidate.
* Baseline.
* Delta.
* Confidence/variance where applicable.
* Cost and latency beside quality.
* Failed samples.
* Scorer breakdown.
* Dataset version.
* Prompt/model/tool policy versions.

Avoid:

* Single “AI quality” magic score.
* Overconfident green/red conclusions without sample size.
* Hiding the scorer or judge model.
* Treating LLM-as-judge as objective truth.

11. Data visualization

11.1 Chart philosophy

Scoria charts should answer operational questions:

* What changed?
* Where did the run fail?
* Which prompt/model/tool caused it?
* Did quality improve?
* Did cost or latency regress?
* Which traces should become dataset items?

11.2 Chart style

* Dark neutral chart background.
* Thin gridlines in low-opacity ash.
* Labels always visible.
* Color only as secondary meaning.
* No rainbow palettes.
* No 3D charts.
* No decorative chart junk.

Great!

11.4 Quality colors

Use semantic status carefully:

* Green means passed threshold.
* Red means failed threshold or regression.
* Yellow means attention needed, not failure.
* Purple means experiment/variant, not quality.
* Scoria/ember means brand/action, not always warning.

18. Accessibility and inclusive design

18.1 Color

* Do not rely on color alone for status.
* Use label text: Pass, Fail, Warning, Approval required.
* Ensure all charts have legends and direct labels.
* Keep contrast at WCAG AA or better for normal text and UI components.  ￼

18.2 Motion

* Respect prefers-reduced-motion.
* No infinite pulsing except critical temporary states.
* Streaming text should be readable, not jittery.

18.3 Density

Scoria will have dense dashboards. Density is acceptable, but every dense view needs:

* Search.
* Filters.
* Clear status labels.
* Sticky headers.
* Expand/collapse.
* Keyboard navigation.
* Copyable IDs.
* Persistent URLs for traces/eval runs.

18.4 Redaction and privacy

Privacy states should be visible and explainable.

Good:

Raw payload redacted. Retained fields: trace ID, span kind, model ID, token usage, cost, latency, status, tool name.

Bad:

Hidden.
