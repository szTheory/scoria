# Research: Embedded Phoenix LiveView Operator UI for Scoria

**Domain:** Phoenix-native AI Ops (Scoria)
**Researched:** May 2026 Context
**Overall Confidence:** HIGH 

## Executive Summary

Scoria aims to be the foundational AI operations layer for Phoenix applications, adhering to the "szTheory Unix Philosophy" of being batteries-included, composable, and providing an operator-first DX. The control plane for this layer is an embedded Phoenix LiveView dashboard.

This research covers the best practices for architecting this embedded UI, specifically focusing on handling complex UI challenges like real-time trace tree visualization, asynchronous streaming responses, and delivering a seamless Day-0 to Day-2 operator experience. By leveraging modern LiveView features (like `start_async`, streams, and hooked components) alongside Scoria's dark, volcanic "cinder" brand identity, we can build a world-class production debugging kit.

---

## 1. Architectural Pattern: The Embedded Dashboard

Following the szTheory DNA, Scoria's UI must easily embed into any host Phoenix application without hijacking the root application's structure.

### Recommended Approach: Root Orchestrator with Hooked Widgets
Instead of forcing users to build their own UI or using heavy nested LiveViews for everything, Scoria should provide a pre-packaged "Root LiveView" orchestrator that is mounted via the host app's router.

```elixir
# Host App Router Example
scope "/admin/ai" do
  pipe_through [:browser, :require_admin] # Sigra Auth Integration
  live_session :scoria_ops, on_mount: [{Sigra.Auth, :ensure_admin}] do
    forward "/", ScoriaWeb.Router
  end
end
```

**Key Principles:**
- **Process Isolation:** The Scoria dashboard runs in its own LiveView processes.
- **Componentization:** Use `LiveComponent` for standard UI widgets (cost metrics, eval pass rates) and standard Phoenix function components for stateless UI.
- **Data Fetching:** Use `assign_async` (LiveView 0.20+) to load heavy trace or eval dataset queries so the initial dashboard mount is instant (Day-0 snappy feel).

## 2. Visualizing Trace Trees

A trace run in Scoria is a hierarchical tree of spans (Agent -> Prompt Render -> LLM -> Tool Call -> Eval). Visualizing this cleanly is the signature UI of the Scoria dashboard.

### DOM Optimization
A complex AI agent loop might generate hundreds of spans. Rendering these synchronously can bloat the DOM.
- **Virtual DOM Primitives:** Use `phx-update="stream"` for the root list of traces.
- **Lazy Rendering:** For deep trace trees, keep child nodes collapsed by default. Fetch or render deep span metadata lazily when a user clicks "expand" to preserve memory.
- **CSS over JS:** Use CSS Grid and flexbox for indentation and connecting tree lines (the "cutaway core sample" aesthetic). Avoid heavy JS tree-rendering libraries; pure HTML/CSS generated by LiveView is faster and more accessible.

### Visual Language (Brand Book Alignment)
The UI should feel like a "lab console" or "field notebook", using the dark volcanic palette:
- **Root Run:** Ember (`#E65A32`)
- **LLM Span:** Scoria (`#B94F31`)
- **Tool Span:** Olivine (`#A7C76F`)
- **Guardrail/Eval Span:** Sulfur (`#FFD166`) / Trace Purple (`#B798FF`)
- **Errors:** Lava (`#FF6B4A`) — Expand the tree automatically to the failing span, not just the root.

## 3. Streaming Responses & Async Operations

Handling streaming LLM responses or live trace events in the dashboard requires careful process management to avoid freezing the UI or dropping tokens.

### Best Practices for LiveView Streaming
1. **Never Block the LiveView Process:** LLM generation and heavy tool execution must happen outside the UI process.
2. **Use `start_async/3` or PubSub:** 
   - For internal playground/replay tools, use `start_async` to spawn an unlinked task that sends chunks back to the LiveView socket via `handle_info`.
   - For observing production runs, the Scoria runtime should broadcast telemetry events via `Phoenix.PubSub`. The LiveView dashboard subscribes to `scoria:runs:tenant_id` and updates the UI passively.
3. **Token Coalescing (Backpressure):** If the LLM generates tokens rapidly (e.g., Groq or local vLLM), sending a `handle_info` message for every single token can thrash the DOM. Buffer/coalesce tokens in the async task and flush them to the UI every ~50-100ms.
4. **Tool Call Buffering:** Tool calls stream as partial JSON. The UI should show a "Waiting for tool schema..." state and only attempt to render the tool execution block once the JSON is complete and parseable.
5. **Auto-Scroll Hook:** Use a tiny JS hook (`phx-hook="ScrollToBottom"`) to keep the streaming log in view.

## 4. Operator-First DX: Day-0 vs Day-2

The "Field Engineer" archetype demands that the tool is incredibly easy to start but powerful enough for a 3 AM production incident.

### Day-0: Onboarding & The Blank Canvas
- **Zero-Config Setup:** A `mix scoria.install` task must generate migrations, basic config, and the router mount.
- **Empty States:** A blank dashboard is intimidating. Provide contextual nudges: *"No traces yet. Run your first chat response or MCP request to see the run tree."*
- **Playground First:** Include a "Draft Mode" where developers can test a prompt against a model directly from the UI to ensure the credentials and adapters work immediately.

### Day-2: Operations, Governance & Debugging
- **Trace to Eval Flywheel:** A one-click button on a failed trace: `[Promote to Dataset]`. This immediately creates a regression test case.
- **Tool Approval Pauses:** When a tool call requires human approval (e.g., `financial_action`), the runtime pauses. The LiveView dashboard receives a PubSub event and surfaces a high-contrast (Sulfur) warning modal allowing the admin to `[Approve]` or `[Deny]`.
- **Replayability:** A button to branch and replay a historical trace with a tweaked prompt or different model, without mutating the original trace record.

## 5. Aligning with szTheory Unix Philosophy

Scoria is part of a larger ecosystem. The LiveView UI should explicitly provide hooks for sibling libraries rather than reinventing the wheel.

*   **Sigra (Auth/RBAC):** Scoria does not handle its own admin auth. The dashboard relies entirely on Sigra's session plugs and RBAC policies to determine if a user can view traces or approve tool executions.
*   **Threadline (Audit):** Every time an operator uses the LiveView UI to approve a tool, publish a new prompt version, or promote an eval, Scoria emits a structured event to Threadline for immutable audit logging.
*   **Chimeway (Alerts):** If a regression gate fails in CI or a budget alert is tripped in production, Scoria fires a telemetry event that Chimeway catches to route a Slack or email notification.
*   **Parapet (SRE):** Scoria tracks SLIs (latency, token costs, guardrail trip rates). Parapet consumes these to build higher-level operator SLO dashboards.

## 6. Conclusion & Roadmap Implications

To successfully build this UI, the development roadmap should prioritize:
1. **Core Data Structures:** Ecto schemas for Traces, Spans, and Prompts.
2. **PubSub Substrate:** Robust internal telemetry and PubSub broadcasting so the UI is fully decoupled from the AI execution runtime.
3. **The Trace Explorer (UI V1):** Focus intensely on the CSS and layout for the nested trace tree, as it is the most complex and important visual element of the brand.
4. **Actionable Modals:** Build the real-time Tool Approval and "Promote to Dataset" flows using LiveView forms and PubSub process resumption.
