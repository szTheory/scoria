<objective>
SC#1 says a step "appears in the trace tree as its own child span with a `parent_id`" and "the trace tree renders the nesting." Today it does not, and backend work alone cannot satisfy it: `trace_tree_component.ex:36` sets `style={"--indent-level: #{depth}"}` and **no CSS rule consumes `--indent-level`** (only `workflow_tree_component.ex:23` inlines its own `padding-left: calc(...)`). `TraceProjection.with_depths/1` computes the depth correctly and it is **thrown away**. The existing component test even locks the bug in — it is literally named *"renders trace span data using a flat DOM structure"* (D-00b).

This plan also disarms a DoS that **this phase itself activates**: `TraceProjection.depth_for/3` (`trace_projection.ex:58-62`) has no cycle guard and no depth cap. It is safe today only because `parent_id` is effectively always `nil`. Plans 53-03 and 53-05 populate `parent_id` — and hosts pass it explicitly (D-02a), so a self-parent or a 2-cycle can arrive from a buggy host call, not just from Scoria's own code. That would infinite-loop the operator's LiveView process (D-07d).

Purpose: SC#1's rendering half, plus the cycle guard and the tree-order correctness that populated `parent_id` values make load-bearing for the first time.
Output: cycle-guarded `depth_for/3`, `tree_order/1`, a nesting-consuming trace tree with an ERROR overlay and a guardrail badge, and a REWRITTEN component test.
</objective>

  <action>
    Extend `Scoria.Observe.TraceProjection`.

    **Cycle-guard `depth_for/3`.** Thread a `visited` `MapSet` accumulator through the existing recursion, in the same private-function-per-branch style already there: return the current `depth` if `span.id` is already a member of `visited`, or once `depth` exceeds a hard cap (use 100 — generous for any real trace, tight enough to bound the walk). Both guards are needed: the visited set catches cycles; the cap catches a pathologically deep chain and bounds the worst case even in the presence of a bug in the visited-set logic.

    This is a real DoS, not a theoretical one. `parent_id` values are host-declared (D-02a), so a self-parent can arrive from a buggy host call. `depth_for/3` runs inside the operator's LiveView process. An infinite loop there hangs an operator's dashboard connection.

    **Add `tree_order/1`** — a pre-order DFS over the parent/child graph. Roots (nil parent, or a parent not present in the input set) come first in their existing relative order; each root is immediately followed by its subtree. It must be cycle-safe by construction (carry a visited set; a span already emitted is never emitted again) and must emit EVERY input span exactly once, including orphans, so no span can be silently swallowed by a malformed graph.

    Both functions get `@spec` and `@doc`.

    **Apply `tree_order/1` on BOTH paths in `lib/scoria_web/live/orchestrator_live.ex`** — the hydrate path (`build_hydrated_trace/2`, which currently orders `asc: s.start_time` and calls `with_depths/1` at :258) and the live-append path (`upsert_trace_span/3`, which is arrival order and calls `with_depths/1` at :390).
