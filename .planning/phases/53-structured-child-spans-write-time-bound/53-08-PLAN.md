<objective>
Close SC#1's parent-linkage criterion. Right now it is literally unsatisfiable for the workflow gates: **nothing in the workflow runtime ever opens a span**, so G2/G3/G4's guardrail spans have nothing to be a child of (D-03c). And there is no `trace_id` convention at all — both adapters do `metadata[:trace_id] || Ecto.UUID.generate()`, minting a **fresh random orphan trace per span** (`req_llm.ex:~50`, `jido.ex:~46`). Without threading, a guardrail span and the LLM span from the same step land in *different traces*, and SC#1's linkage is true only within a single subtree.

This plan makes a run a trace: `execute_step/2` opens one step-level parent span, threads `trace_id = run.id` and the step span's id into the handler and telemetry metadata, and hangs G2/G3/G4's guardrail spans off it. It also wraps the live prompt-render site (`Scoria.Eval.JudgeRunner`, reached from an Oban `:evals` job) in a PROMPT span — SC#1's `prompt` leg on a real production path.

G3 and G4 ship (they were discretionary): with `Guardrail.emit/1` built in plan 53-07 they are ~3 lines each on the same seam as G2, and they complete the block/escalate coverage.

Purpose: SC#1's `parent_id` linkage and the `prompt` leg; SC#3 for workflow steps.
Output: the step-level parent span, `trace_id` threading, G2/G3/G4, the `JudgeRunner` PROMPT span, and `test/scoria/workflows/runtime_span_test.exs`.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| host `handler` fun -> `execute_step/2`'s step span | The handler is arbitrary host code. It can raise, throw, or exit; its exception must reach the host unchanged. |
| threaded `trace_id`/`parent_id` -> adapters -> `ai_spans` | These ids become the tree structure. A `parent_id` pointing at a span in another tenant's trace would cross-link traces. |
| `JudgeRunner`'s LLM output -> the PROMPT span | The judge's free-form explanation is the single most likely free-text leak in the codebase (`judge_runner.ex:167`, `:202`). |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-53-12 | Tampering (host behavior altered by observability) | `execute_step/2`'s span wrap | high | mitigate | `span/4` is transparent — it returns `fun`'s value verbatim and reraises the host's exception with its original stacktrace. Every outcome branch's return tuple is byte-for-byte unchanged. `test/scoria/workflows/runtime_test.exs` passing WITHOUT EDITS is the proof and an explicit acceptance criterion. A workflow step must not be able to observe that it is being instrumented. |
| T-53-01 | Information Disclosure | the `JudgeRunner` PROMPT span | critical | mitigate | The PROMPT span carries duration, kind, and ids. NOTHING from the judge's output. `judge_runner.ex:167`/`:202`'s free-form `explanation:` is a model-generated string produced by a model that just read the payload — it is the highest-probability free-text leak in this codebase, and the OTel-blessed key name actively invites putting it on a span. `Bounds`'s closed registry (plan 53-04) is the structural backstop: there is no registered key it could legally land under.
