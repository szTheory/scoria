This RESEARCH.md does not re-derive or second-guess any `D-NN` decision in it. Every line-number citation in `56.1-CONTEXT.md` I checked landed within 0–4 lines of the cited location, and every code-shape claim (six guards, `optimistic_lock`, `add_if_not_exists` house style, `unique_index` composition, `Ecto.StaleEntryError` precedent, `approval_error_message/2`'s existing clause shape, etc.) is accurate as of this commit (`e83d4d81`). Section "Codebase Verification" below lists the checked citations and the (very minor) discrepancies found.

**A directly reusable test precedent already exists in-repo** for the hardest part of this phase's validation story: `test/scoria/workflows_test.exs:476` ("stale concurrent replay approval and run updates raise instead of last-write-winning") proves `Ecto.StaleEntryError` on a stale-copy `Run.changeset/2` update using **zero** `Task.async` — just two sequential `Repo.get!` copies and two sequential updates. This is the exact pattern D-02's "accepted, documented" sibling-transaction-already-loaded interleaving needs, and it means that proof does not require real concurrent processes. Real concurrency (`Task.async` + `Ecto.Adapters.SQL.Sandbox.mode(Repo, {:shared, self()})`) **is** required for D-04's row-lock-ordering proof and D-09's CAS admission-count proof — and `test/scoria/workflows_test.exs`'s own `setup` block already establishes `{:shared, self()}` sandbox mode, so no new test harness work is needed to write those tests; `test/scoria/mcp/executor_test.exs:323` already uses `Task.async` for a different purpose (a blocking-tool timeout test), confirming the pattern is idiomatic in this codebase.

**Primary recommendation:** Implement in the wave order given in "Implementation Sequencing" below — migration and schema first (nothing else can compile against `rail_*` columns before they exist), then `Workflows.halt_run/3` and the six guards as one atomic unit (they share `lib/scoria/workflows.ex` and cannot be split across parallel plans without one plan racing the other's edits to the same file), then the two enforcement call sites and config resolution (`Params.start/2` + `Params.start_handoff/3`) in parallel, then telemetry/audit/trace, then docs. See the wave table for exact file-contention groupings.

## Architectural Responsibility Map

| Capability | Primary Tier | Secondary Tier | Rationale |
|------------|-------------|----------------|-----------|
| Rail limit resolution (config ladder) | API / Backend (`Scoria.Runtime.Params`) | — | Resolved once at run creation, a pure config-merge; no browser or SSR involvement |
| Rail counting (durable CAS increment) | Database / Storage (`ai_workflow_runs` columns via `Repo.update_all`) | API / Backend (`Scoria.Workflows.Rails`) | The atomicity guarantee is a Postgres row-lock property, not an application-level lock; the DB IS the enforcement mechanism |
| Halt terminality (six guards) | API / Backend (`Scoria.Workflows`) | Database / Storage (`optimistic_lock`, `FOR UPDATE`) | Guards are application code, but their correctness depends on DB-level locking primitives they invoke |
| Timeout rail (active-time accounting) | API / Backend (`Run.changeset/2` derivation) | Database / Storage (`rail_paused_ms`/`rail_paused_at` columns) | Derivation lives in the changeset (a Backend-tier invariant), persisted to Storage |
| Audit outbox row | Database / Storage (`ai_audit_outbox_events`) | API / Backend (`SRE.insert_audit_outbox_event/2`) | Durable evidence; API tier only composes and inserts |
| Telemetry (`:tripped`/`:observed`/`:skipped`) | API / Backend (`:telemetry.execute/3` call sites) | — | In-process event bus; no persistence tier of its own (adopter's own sink decides) |
| Trace span attributes (D-18) | API / Backend (`Observe.span/4` caller) | Database / Storage (`Buffer` → Postgres spans table) | Attributes attach to an existing span; Backend computes them, Storage persists them |
| Approval-inbox halt messaging (D-05) | Frontend Server / SSR (`ApprovalsLive`, a LiveView) | — | Pure operator-facing copy fix; no new Backend logic |
| Adopter docs (guide, CHANGELOG) | — (docs, no runtime tier) | — | Static content, no request path |

No capability in this phase touches the Browser/Client or CDN/Static tiers — this is an entirely server-side, database-adjacent enforcement mechanism. The one LiveView touch (D-05) is a copy/message fix on an existing SSR page, not new client behavior.

### Alternatives Considered

| Instead of | Could Use | Tradeoff |
|------------|-----------|----------|
| Atomic CAS `UPDATE ... RETURNING` | `SELECT ... FOR UPDATE` then app-level increment in the same transaction | Two round-trips instead of one; no correctness difference under proper locking, but D-09 prefers the single-statement form for its `RETURNING`-based simplicity and because it matches the `Relay`'s existing `inc:` precedent |
| NimbleOptions for rail-value validation | Hand-rolled `with`-chain returning `{:error, {tag, key, value}}` | NimbleOptions' error strings don't produce the tuple shape the rest of `Params` already speaks (D-12); would be the first *direct* validation dependency for three integer keys |
| Migration-time backfill of `rail_*` columns | No backfill (locked, D-07) | Postgres 16 `ADD COLUMN ... DEFAULT <constant>` is catalog-only; a backfill would be a needless full-table rewrite on every host upgrading |

### Pattern 1: Atomic Check-and-Increment (CAS admission)

**What:** A single `Repo.update_all` with a `WHERE` guard and `RETURNING`, exploiting Postgres's per-row exclusive lock during the statement's execution to serialize concurrent admits.
**When to use:** Any counter that must never overshoot under concurrent writers, where the "check" and the "increment" must be the same atomic operation.
**Example (from `56.1-CONTEXT.md` D-09, in-repo precedent at `lib/scoria/sre/relay.ex:108-111`):**
```elixir
# Source: 56.1-CONTEXT.md D-09, mirroring lib/scoria/sre/relay.ex's
# existing Repo.update_all(inc: ...) precedent on a claim path.
def admit_tool_call(run_id, now \\ DateTime.utc_now()) do
  query =
    from(r in Run,
      where: r.id == ^run_id,
      # is_nil/1 disjunct is MANDATORY: NULL < N is NULL (not TRUE),
      # so "unlimited" would silently become "deny everything" without it.
      where: is_nil(r.rail_max_tool_calls) or r.rail_tool_calls < r.rail_max_tool_calls,
      select: r.rail_tool_calls)

  case Repo.update_all(query, inc: [rail_tool_calls: 1]) do
    {1, [count]} -> {:ok, count}
    {0, _} -> :denied
  end
end
```

### Pattern 2: Changeset-Derived Invariant (pause accounting)

**What:** An invariant computed inside a changeset from a field transition, rather than written by every call site that could cause the transition.
**When to use:** Any durable accounting value whose correctness depends on catching EVERY writer of a related field — mirrors the exact in-repo precedent this phase's D-15 follows.
**Example (existing precedent, `lib/scoria/workflows/run.ex:66-76`):**
```elixir
# Source: lib/scoria/workflows/run.ex — the existing precedent D-15 mirrors
defp validate_replay_allowlist_immutability(changeset) do
  run = changeset.data
  next_overrides = get_field(changeset, :replay_overrides) || %{}
  previous_overrides = run.replay_overrides || %{}

  if replay_started?(run) and widening_allowlist?(previous_overrides, next_overrides) do
    add_error(changeset, :replay_overrides, "live_tool_allowlist cannot expand after replay start")
  else
    changeset
  end
end
```
D-15's `rail_paused_at`/`rail_paused_ms` derivation follows this exact shape: a private changeset function reads `changeset.data.status` (the pre-transition value) and `get_field(changeset, :status)` (the post-transition value), and derives the pause fields from the transition — never from a call site's explicit intent.

### Pattern 3: Idempotent Resolution With Struct-Match Guard

**What:** A resolution function that checks whether its output already exists on the input (by struct match, not key presence) before doing the expensive/telemetried work, so double-calling it from two call sites (executor + connector) never double-emits telemetry.
**When to use:** Any value computed once but potentially reachable from more than one entry point.
**Example (existing precedent this phase's guards should follow — already used for `Classification`, `lib/scoria/mcp/executor.ex:63-66` and `lib/scoria/connectors/invocation.ex:104-113`):**
```elixir
# Confirmed live pattern — Executor.resolve_classification/2's idempotence guard
case Map.get(context, :tool_classification) do
  %Classification{} -> {:ok, context}  # already resolved elsewhere, reuse unchanged
  _ -> # resolve + telemetry + persist, then Map.put
end
```
This is directly relevant to D-08's guidance that `max_tool_calls` must be enforced identically at both `MCP.Executor.execute/4` and `Connectors.Invocation.invoke/4` — the admission check itself is not idempotent (each call consumes budget), but the *pattern of two entry points sharing one implementation* is exactly what `Classification.resolve/2`'s struct-match guard already demonstrates working in this codebase.

### Anti-Patterns to Avoid

- **Reading `run.status` before writing a rail-triggered halt without a `FOR UPDATE` lock:** a read-then-decide (rather than a single locked statement or a locked-read-then-decide-inside-the-same-transaction) reintroduces the exact race D-04 closes. `claim_step/1`'s existing `Repo.get(Step, step_id)` outer check (line 227) followed by a locked re-fetch inside the transaction (line 232) is the correct shape to mirror — an outer optimistic pre-check is fine, but the transaction body must re-fetch under lock.
- **Treating a sibling's `Ecto.StaleEntryError` (D-02's un-clamped interleaving) as a bug to fix:** it is an accepted, documented consequence of `optimistic_lock`. Writing code to "catch and retry" that path would silently resurrect the exact halted-run race D-04 exists to prevent, or would mask a genuine correctness signal. Document it; do not paper over it.
- **Short-circuiting the CAS admission statement when `is_nil(limit)`:** this looks like an obvious optimization ("why increment if there's no limit to check against?") but directly breaks SC#3 — the sizing on-ramp depends on `rail_steps`/`rail_tool_calls` being non-zero for unlimited runs too (D-09).
- **Wiring the rail check inside `Observe.span/4`'s body when the DENY branch also needs to influence `span_opts`:** `Observe.span/4` reads `opts[:attributes]` at emit time with no API to inject them from inside the body (confirmed at `observe.ex:371-373`). The check must run and decide before the span opens; only the *trip* (raising `StepFailureSignal`) happens inside the span body.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Atomic "check limit, then increment" under concurrency | A `SELECT` + application-level `if` + `UPDATE` sequence, or a `GenServer`-owned in-memory counter | The single-statement `Repo.update_all(query, inc: [...])` CAS pattern (D-09) | A read-then-write sequence has a TOCTOU race under concurrent siblings unless it holds a lock for the whole sequence; a single atomic UPDATE statement needs no separate lock-acquire step and needs no process to own state that must survive node restarts |
| Cross-process/cross-node mutual exclusion for "has this run already halted" | A distributed lock manager, a `:global` registered name, or an ETS table shared across nodes | Postgres row-level `FOR UPDATE` (D-04) | The run row IS the natural, already-durable, already-replicated (via the DB) point of synchronization; a distributed lock adds an entire new failure mode (lock-manager unavailability) for a problem the DB already solves |
| Tracking "how long has this run been paused" | A background sweep/reaper job computing elapsed pause time on a schedule | Changeset-derived accumulation at the moment of transition (D-15), mirroring the existing `validate_replay_allowlist_immutability/1` pattern | A scheduled job introduces a second enforcement mechanism with its own multi-node story (exactly what D-07/deferred `sweep/1` was cut for); deriving at the transition point is correct by construction and needs no scheduler |
| Validating rail config values | A generic options-validation library (NimbleOptions) | A hand-rolled `with`-chain returning `{:error, {tag, key, value}}` tuples matching the existing `Params` module's error shape (D-12) | Three integer keys do not justify a new *direct* dependency, and NimbleOptions' error shape doesn't match the tuple contract the rest of the module already speaks |

**Key insight:** every "don't hand-roll" item in this phase is really the same insight stated four ways: **the database's own concurrency primitives (row locks, atomic UPDATE, changeset-time derivation) are already the correct answer, and building an application-level equivalent (locks, schedulers, or a new dependency) reintroduces exactly the race conditions or config-consistency problems the DB primitive was designed to prevent.**

## Common Pitfalls

### Pitfall 1: The three-valued-logic NULL trap in the CAS predicate
**What goes wrong:** `WHERE r.rail_tool_calls < r.rail_max_tool_calls` evaluates to `NULL` (not `TRUE`) when `rail_max_tool_calls IS NULL` — the row simply never matches, and an "unlimited" rail silently becomes "deny everything."
**Why it happens:** SQL's three-valued logic is a classic footgun; `NULL < anything` is always `NULL`, never `TRUE`, and Postgres treats a `WHERE` clause evaluating to `NULL` the same as `FALSE`.
**How to avoid:** The `is_nil(r.rail_max_tool_calls) or r.rail_tool_calls < r.rail_max_tool_calls` disjunct is mandatory on every rail predicate — locked in D-09's code example.
**Warning signs:** A test that asserts "an unlimited run's Nth tool call succeeds" starts failing at some small N even though no limit was ever configured.

### Pitfall 2: Confusing "the clamp covers every sibling" with "the clamp covers every sibling whose transaction starts after the halt commits"
**What goes wrong:** A test (or an implementer's mental model) assumes G4/G5/G6's clamp makes every concurrent completion/failure/escalation safe. It only covers siblings that read the run row AFTER the halting transaction commits. A sibling already inside `complete_step/3` (having read the run before the halt) hits its own `optimistic_lock` mismatch and raises `Ecto.StaleEntryError` when it tries to write — a DIFFERENT failure mode than the clamp, but still non-resurrecting.
**Why it happens:** The clamp is application logic (`if Run.halted?(run) do ... end`) evaluated against a `%Run{}` struct the sibling already loaded into memory before the halt was even initiated; it cannot see a status change that happens in another transaction after it already has its copy.
**How to avoid:** Test BOTH interleavings explicitly (see Validation Architecture below) — one where the sibling's `Repo.get!(Run, ...)` happens before `halt_run/3` commits (expect `StaleEntryError`), one where it happens after (expect the clamp to suppress the write).
**Warning signs:** A test asserting "no sibling can ever resurrect a halted run" passes for one interleaving and silently never exercises the other, giving false confidence.

### Pitfall 3: Testing rail admission at the Elixir level without a real concurrent DB transaction
**What goes wrong:** A test that calls `admit_tool_call/2` from N sequential (not concurrent) calls in the SAME process proves nothing about the CAS's actual concurrency guarantee — sequential calls never contend for the row lock at all, since Elixir/Ecto executes them one after another regardless of the SQL's atomicity.
**Why it happens:** It is easy to write a "looks like a concurrency test" that is actually just N ordinary calls, especially since the assertion ("exactly `limit` executions admitted") happens to hold true even for sequential calls — the sequential case is trivially correct and does not exercise the lock-wait/re-check path at all.
**How to avoid:** Use `Task.async/1` to spawn N genuinely concurrent processes hitting the SAME run row, with `Ecto.Adapters.SQL.Sandbox.mode(Repo, {:shared, self()})` (already set up in `test/scoria/workflows_test.exs`'s `setup` block) so all N tasks share the test's sandboxed transaction. `Task.await_many/1` to collect results, then assert the sum of `:ok` results equals `limit` exactly.
**Warning signs:** A CAS test that "passes" but takes near-zero wall-clock time for N=100 concurrent calls — that's a sign the calls ran sequentially, not concurrently, since real lock contention takes measurable time.

### Pitfall 4: Assuming `Repo.update_all` with `select:` returns the pre-increment value
**What goes wrong:** CONTEXT.md's own Residual Open Question #1 flags this: there is **zero in-repo precedent** for `Repo.update_all` combined with `select:`. If the returned value is PRE-increment rather than POST-increment, every `observed`/`attempted` value in D-17's telemetry payload flips by one.
**Why it happens:** Postgres's `UPDATE ... RETURNING` always returns the NEW (post-update) row values — this is well-documented Postgres behavior — but it has never been exercised in this codebase and deserves an explicit spike/test rather than an assumption.
**How to avoid:** Write a 10-line throwaway (or a permanent unit test) asserting the returned value from `Repo.update_all(query, inc: [rail_tool_calls: 1])` on a row starting at `rail_tool_calls: 5` is `6`, not `5`.
**Warning signs:** An off-by-one in every rail's `observed`/`attempted` telemetry and audit-row value — silent, since the CAS's admit/deny decision itself is correct either way (the WHERE clause is evaluated pre-increment regardless).

### Pitfall 5: A raw `timestamptz`/`timestamp` mismatch silently shifting the active-time computation by a UTC offset
**What goes wrong:** `started_at`/`inserted_at` are `timestamp(6)` WITHOUT time zone. Inside a raw SQL fragment computing `EXTRACT(EPOCH FROM ($now - COALESCE(...)))`, if `$now` (an Elixir `%DateTime{}`) is bound without an explicit type, Postgrex encodes it as `timestamptz`, and the implicit `timestamptz - timestamp` cast consults the session's `TimeZone` setting — silently shifting the computed elapsed time by the UTC offset on any non-UTC session.
**Why it happens:** This is CONTEXT.md's own Residual Open Question #2, flagged as "spike it" rather than asserted as solved.
**How to avoid:** Bind the parameter with an explicit type ascription — `type(^now, :utc_datetime_usec)` — inside the fragment, and add a regression test that sets a non-UTC session `TimeZone` (or runs in CI where the session default may differ from the app's assumed UTC) and asserts the computed `elapsed_active_ms` is correct.
**Warning signs:** The timeout rail fires early or late by a consistent number of hours in a specific deployment region, but never in local dev (where the session timezone happens to already be UTC).

### Six-guard terminality — the two `Ecto.StaleEntryError` interleavings, worked example

# Source: 56.1-CONTEXT.md D-02, mirroring the existing precedent at
# test/scoria/workflows_test.exs:476 ("stale concurrent replay approval
# and run updates raise instead of last-write-winning") — this precedent
# proves the interleaving-BEFORE case needs NO Task.async at all.

test "a sibling that read the run BEFORE halt_run/3 commits raises StaleEntryError on its own write" do
  {:ok, run} = Workflows.create_run(%{root_role_id: "executor"})
  {:ok, step_a} = Workflows.create_step(run.id, %{sequence: 1, kind: "t", role_id: "r", status: "running"})
  {:ok, step_b} = Workflows.create_step(run.id, %{sequence: 2, kind: "t", role_id: "r", status: "running"})

  # Simulates step_b's complete_step/3 having ALREADY loaded the run
  # before step_a's halt_run/3 commits.
  stale_run_copy = Repo.get!(Run, run.id)

  {:ok, _halted} = Workflows.halt_run(run.id, step_a.id, %{"status" => "run_halted", "reason_code" => "max_steps_exceeded"})

  # step_b's complete_step/3 tries to write against its stale copy —
  # optimistic_lock raises, the whole complete_step/3 transaction unwinds.

### CAS admission determinism — genuine concurrency, worked example

```elixir
# Source: 56.1-CONTEXT.md D-09; harness precedent confirmed live at
# test/scoria/workflows_test.exs:12-13 ({:shared, self()} sandbox mode)
# and test/scoria/mcp/executor_test.exs:323 (Task.async pattern already
# idiomatic in this codebase for a different purpose).

test "exactly N tool calls are admitted under 2N concurrent siblings, never N+k" do
  {:ok, run} = Workflows.create_run(%{root_role_id: "executor", rail_max_tool_calls: 10})

  results =
    1..20
    |> Enum.map(fn _ -> Task.async(fn -> Scoria.Workflows.Rails.admit_tool_call(run.id) end) end)
    |> Task.await_many(5_000)

  admitted = Enum.count(results, &match?({:ok, _}, &1))
  denied = Enum.count(results, &(&1 == :denied))

  assert admitted == 10
  assert denied == 10

  reloaded = Repo.get!(Run, run.id)
  assert reloaded.rail_tool_calls == 10
end
```

### Why this phase's validation is unusually concurrency-heavy, and what that means for the test plan

Three of the four ROADMAP success criteria (SC#1 halt-is-audited, SC#2 halt-is-terminal, SC#3 unlimited-is-unchanged) and several of the locked decisions (D-02, D-04, D-06, D-09, D-15) make claims that are **only true under specific Postgres concurrency semantics** (row-level locking, optimistic-lock version mismatches, `READ COMMITTED` EvalPlanQual re-checking). A plan that tests these claims with sequential, single-process ExUnit assertions will produce **passing tests that prove nothing about the actual race conditions the decisions exist to close**. The distinction that matters for every test below:

- **Provable with fast, sequential, single-process ExUnit tests:** anything that is a pure function of a `%Run{}`/`%Step{}` struct and its changeset (validation, status-transition derivation, telemetry-payload shape, config-ladder precedence, the `Ecto.StaleEntryError` interleaving where the sibling's stale copy was already loaded — no `Task.async` needed, per the existing `workflows_test.exs:476` precedent).
- **Genuinely needs a DB-backed concurrent transaction** (`Task.async` + `Ecto.Adapters.SQL.Sandbox.mode(Repo, {:shared, self()})`, already the pattern in this file's own `setup` block, and already used elsewhere in this codebase at `test/scoria/mcp/executor_test.exs:323`): the CAS admission-count determinism proof (D-09), the two-concurrent-halts-race proof (D-04), and the deadlock-absence proof (Open Question #3).

### Guard-by-guard test matrix (G1–G6, D-02)

| Guard | Site | What must be asserted | Test shape |
|-------|------|------------------------|------------|
| G1 | `claim_step/1` (`workflows.ex:226-246`) | A queued/retrying step on an already-halted run cannot be claimed; `Repo.rollback(:run_halted)` fires; the run's `lock_version` is unchanged by the failed claim attempt | Sequential ExUnit: halt a run, then call `claim_step/1` on a still-queued sibling step, assert `{:error, :run_halted}` or the transaction rollback shape D-03 specifies |
| G2 | `retry_step/1` (`workflows.ex:549-566`, refuse after `:554`) | A `retry_step/1` call against a halted run's step is refused, not silently allowed to requeue | Sequential ExUnit: halt a run whose current step is `"failed"`, call `retry_step/1` on that step, assert refusal |
| G3 | `resume_run/1` (`workflows.ex:604-659`) | `"halted"` structurally falls through to the existing `_ -> {:error, :not_resumable}` clause at 657-658 — **no code change, a test-only guard** | Sequential ExUnit: halt a run, call `resume_run/1`, assert `{:error, :not_resumable}` — this is a REGRESSION test guaranteeing nobody later adds a `"halted"` clause to the case statement that resurrects the run |
| G4 | `complete_step/3` clamp (after `:278-279`) | **Both interleavings** must be tested: (a) sibling's `Repo.get!(Run,...)` happens AFTER halt commits → clamp suppresses the `completed`/`running` write, run stays `"halted"`; (b) sibling already holds a stale copy from BEFORE the halt → `Ecto.StaleEntryError` raised on `repo.update!`, step strands `"running"`, result envelope lost — **accept and assert this, do not try to prevent it** | Two ExUnit tests, one per interleaving. Interleaving (a) is a plain sequential test (halt first, then call `complete_step/3`). Interleaving (b) mirrors `workflows_test.exs:476`'s stale-copy pattern exactly (load the run BEFORE the halt commits, halt, then attempt to complete against the stale copy) |
| G5 | `fail_step/3` clamp (after `:485`) | Same two-interleaving structure as G4 — CONTEXT.md calls this "the sneakiest path" because an un-clamped sibling failure would rewrite `"halted"` → `"failed"`, reopening `resume_run`'s resurrection clause at `:648-655` | Same two-test shape as G4, substituting `fail_step/3` |
| G6 | `mark_waiting_for_approval/3` clamp (after `:346-349`) | Same two-interleaving structure; an un-clamped sibling escalation would rewrite `"halted"` → `"waiting_for_approval"`, which `resume_run` would then resume via its approved-approval branch at `:608` | Same two-test shape, substituting `mark_waiting_for_approval/3` |

**Sampling adequacy for the guards:** 6 guards × 2 interleavings where applicable (G1/G2/G3 have only one meaningful interleaving each since they are refuse-side, not clamp-side) = **9 required test cases minimum** to cover every cell in D-02's matrix. A regression that removes any single clamp (G4/G5/G6) or any single refuse-check (G1/G2) would only be caught if the corresponding test exists — this is not a place where "a few representative tests" suffice, because each guard closes a DIFFERENT resurrection path with a DIFFERENT root-cause status transition (`"completed"`, `"failed"`, `"waiting_for_approval"`), and a passing test for one guard provides zero evidence about the others.

### Concurrency-determinism tests (D-04, D-09) — the genuinely-needs-real-concurrency group

| Claim | Test | DB requirement |
|-------|------|-----------------|
| D-04: two concurrent halt attempts on the same run — only one wins, the other gets `{:error, :already_halted}`, never a deadlock | `Task.async` × 2, both calling `Workflows.halt_run/3` on the same `run_id` with different `step_id`s (simulating two siblings both tripping a rail), `Task.await_many/1`, assert exactly one `{:ok, %Run{}}` and one `{:error, :already_halted}` | Real concurrent transactions; `{:shared, self()}` sandbox mode required so both tasks see the same DB state as the test process |
| D-04: `unique_index` and `optimistic_lock` collisions both normalize to `{:error, :already_halted}` | Force one path via a fast winner + slow loser (e.g., `Process.sleep` inside a mocked delay, or simply relying on Postgres's own lock-wait serialization under `Task.async`) and assert the loser's return value regardless of which underlying Postgres error fired | Real concurrent transactions |
| D-04: lock order is always run → steps (no deadlock cycle) | Run N concurrent `Task.async` calls mixing `halt_run/3` and `claim_step/1` against overlapping run/step sets; assert all N complete within a bounded timeout (a deadlock would manifest as a `Task.await_many/2` timeout or a Postgres `40P01 deadlock_detected` error surfacing) | Real concurrent transactions; this is Open Question #3's "one concurrent test against a live DB" |
| D-09: exactly `limit` executions admitted under `2×limit` concurrent siblings (no overshoot, no undershoot) | `Task.async` × `2N` calling `admit_tool_call/2` (or `admit_step/2`) against one run with `rail_max_tool_calls: N`, `Task.await_many/1`, assert `N` admits and `N` denials, and assert the persisted `rail_tool_calls` column equals exactly `N` after all tasks complete | Real concurrent transactions — see the worked example above |
| D-09: `is_nil(limit)` still increments (counting is unconditional, SC#3) | Sequential ExUnit is sufficient here — no concurrency needed to prove a single unlimited run's counter increments on each admit | Sequential |

**Why these specifically need `Task.async` + shared sandbox, and how to know the test is exercising real concurrency (not accidentally sequential):** see Common Pitfalls Pitfall 3 above. A concrete tell: the CAS admission test should occasionally (not always, since Postgres's row lock is fast) show at least one task actually blocking behind another's held lock — this can be observed indirectly by asserting the final counter value is exactly `N`, which is impossible to get wrong-but-passing under true concurrency the way it would be trivially "correct" under accidental sequential execution.

### CAS counter correctness (D-06/D-09) proof structure

Beyond the raw admission-count determinism above, the plan needs an explicit proof that the counter counts **executions, not rows** (D-06's core semantic claim, distinguishing it from D-56.1-B's superseded `count(*)` approach):

1. A fan-out test: create `M` step rows on one run (simulating a handler that creates many rows at once) but only admit/execute `K < M` of them; assert the counter reads `K`, not `M`.
2. A retry-loop test: `retry_step/1` on the same step `R` times; assert the counter increments `R` times (this is the exact scenario D-06 diagnoses as broken under the old `count(*)` approach — the row count stays at 1 but the counter must still climb, proving the fix addresses the retry-loop overshoot the aggregate approach could not catch).

### Migration test posture (D-07)

D-07 locks "one migration, no backfill." The test posture that proves this:

1. **Structural test:** the migration file uses `add_if_not_exists` for every column (a static assertion reading the migration file's source, mirroring the existing `Scoria.DockerDxDocContractTest`-style file-content contract tests already in this codebase) — this guards against a future edit reintroducing bare `add` and breaking the "copied into partially-applied host repos" contract.
2. **Behavioral test:** after running the migration against a DB with existing (pre-migration-era) rows, assert every pre-existing row now reads `rail_steps: 0, rail_tool_calls: 0, rail_paused_ms: 0, rail_max_steps: nil, rail_max_tool_calls: nil, rail_max_active_ms: nil` — i.e., a plain `ADD COLUMN ... DEFAULT` catalog-only operation, no explicit backfill `UPDATE` statement. This IS the SC#3 proof for pre-existing runs, distinct from the SC#3 proof for newly-created unconfigured runs (below).
3. **CHECK constraint validation-scan test (if the plan chooses to ship CHECK constraints per its Claude's-Discretion latitude):** if constraints are added, assert they are declared `NOT VALID` (or omitted in favor of `validate_number` in the changeset, the other permitted option) — a plain re-read of the migration file's SQL text is sufficient; no need to time an actual lock duration in CI.

### SC#3 proof — "adopter who configures nothing sees unchanged behavior"

This is a two-part claim and needs two distinct tests, easily conflated into one insufficient test:

1. **A brand-new run created with no `:rails` option and no app-level `config :scoria, Scoria.Runtime.Rails` set at all** must behave identically to pre-Phase-56.1 behavior: it must be able to execute an arbitrary number of steps/tool calls without ever halting. Test: create a run, execute N steps (N should be larger than any plausible accidental default, e.g., 50), assert zero halts and `run.rail_max_steps == nil`.
2. **The SAME run's counters must still be incrementing** (the "counting is always on" half of SC#3, D-09's most-load-bearing single sentence): after those N steps, assert `rail_steps == N` even though `rail_max_steps` is `nil`. A test that only proves part 1 (no halt) without also proving part 2 (the counter moved) would pass even if a future regression accidentally short-circuited the CAS on `is_nil(limit)` — exactly the anti-pattern flagged in "Anti-Patterns to Avoid" above.

### SC#4 proof — `MCP.Router`'s no-run-attribution no-op

1. Call `MCP.Executor.execute/4` (or route a request through `MCP.Router`'s `post "/"` handler) with a context that has no `:run_id` (mirroring `Identity.to_map/1`'s real shape — confirmed to return exactly `%{actor_id:, tenant_id:, session_id:, metadata:}`, no `run_id` key).
2. Attach a `:telemetry.attach/4` handler to `[:scoria, :run, :rail, :skipped]` inside the test, assert it fires exactly once per call with `metadata.reason == :no_run_id` and `metadata.site` distinguishing `MCP.Router` from `MCPController` from a direct host call (D-19's widening beyond just the router).
3. Assert the tool call itself still completes normally (this is a no-op, not a refusal) — the tool's own return value is unaffected.
4. A separate test for the `Logger.warning` once-per-boot-per-site behavior (only fires when `max_tool_calls` IS configured) — reuse the existing ETS `log_once` idiom's own test pattern from `bounds.ex`/its test file as a structural template, since D-19 explicitly reuses that idiom.

### D-15 pause-accounting regression tests (the two tests CONTEXT.md explicitly names)

1. **The invariant:** for every `%Run{}` where `status not in ["waiting_for_approval", "paused"]`, `rail_paused_at IS NULL`. Property-style test: generate/fetch runs across every reachable status transition in the test suite and assert this holds.
2. **The specific regression D-15 fixes:** two steps on one run; step A escalates (`mark_waiting_for_approval/3`, run becomes `"waiting_for_approval"`, `rail_paused_at` set); step B (already `"running"`) completes via `complete_step/3`. ### Trace/telemetry registry canary (D-18)

### D-16 audit-transaction-failure tradeoff test

D-16 explicitly widens the `halt_run/3` spec to admit `{:error, Ecto.Changeset.t()}` because the audit insert lives INSIDE the halt transaction — an audit failure aborts the whole halt (SC#1 beats SC#2 on failure, in CONTEXT.md's own words). Test: force the audit insert to fail (e.g., a duplicate `dedupe_key` collision, which the repo-arg form of `insert_audit_outbox_event/2` surfaces as `repo.rollback(failed_changeset)`), assert the ENTIRE `halt_run/3` transaction rolls back — the run's `status` must NOT be `"halted"` after a failed audit insert, proving the trade is real and intentional, not accidental.

### Known Threat Patterns for this stack

| Pattern | STRIDE | Standard Mitigation |
|---------|--------|------------------------|
| Runaway agent loop (unbounded steps/tool calls/wall-clock consuming host resources or budget) | Denial of Service (against the host's own infrastructure/budget, not an external attacker) | The rail mechanism itself — CAS-admitted counters + terminal halt (D-01 through D-09) |
| A misconfigured rail (`max_steps: 0`) bricking every run for an adopter | Denial of Service (self-inflicted, via config error) | D-12's loud, run-scoped refusal rather than a boot-time crash — the adopter sees an explicit error at `Scoria.start_run/2`'s call site, not a bricked application |
| A sibling execution racing a halt to resurrect a terminated run (privilege/state escalation of a supposedly-dead run) | Tampering / Elevation of Privilege (a halted run continuing to act with the authority/budget it was denied) | The six guards (G1-G6) plus D-04's single lock order — this is the central threat this phase's entire terminality design defends against |
| An audit row for a halt silently failing to persist, leaving no evidence the halt occurred | Repudiation | D-16's decision to place the audit insert INSIDE the halt transaction — a lost audit row means a lost halt too (fail together), rather than an inconsistent state where the halt "happened" but left no evidence |
| Config-driven telemetry/logging that logs every call forever, becoming its own resource-exhaustion vector or noise-drowns-signal problem | Denial of Service (of the observability channel itself) | D-19's explicit rejection of an info-log-every-boot-forever approach in favor of a once-per-boot-per-site `Logger.warning`, only when a rail IS configured |
