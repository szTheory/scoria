## Halt terminality & status vocabulary

| Option | Description | Selected |
|--------|-------------|----------|
| Reuse `"cancelled"` | D-56.1-C's assumption; no new vocabulary | |
| Reuse `"failed"` | Existing terminal status | |
| Add `"halted"` | New closed-enum member; no migration needed | ✓ |

**Locked:** `"halted"` (D-01). `"failed"` is disqualified outright — `resume_run/1:648-655` makes `Scoria.resume_run/2` a one-call resurrection of any failed run, which fails SC#2. `"cancelled"` has zero writers in `lib/` today and is reserved for a future operator cancel; conflating them is irreversible for historical rows.

**Notes:** D-56.1-C's terminality guard was found **severely incomplete** — it enumerated only initiation-side paths. Three completion-side writers (`complete_step/3`, `fail_step/3`, `mark_waiting_for_approval/3`) resurrect a halted run without ever touching `retry_step/1`. Six guards, not one. The red-team further found the draft's clamp rationale wrong: `optimistic_lock` makes an in-flight sibling *raise* rather than clamp, destroying its step write — accepted and documented rather than papered over.

## Enforcement point & counting/migration mechanics

| Option | Description | Selected |
|--------|-------------|----------|
| `Reconciler` preflight | Check before dispatch | |
| `Runtime.execute_step/2` before `claim_step/1` | Avoids a half-claimed step | |
| `Runtime.execute_step/2` after `claim_step/1` | Behind the exactly-one-executor gate | ✓ |
| `MCP.Executor` only (for tool calls) | Single site | |
| `MCP.Executor` + `Connectors.Invocation` | Two entry points, idempotence-guarded | ✓ |

**Locked:** after `claim_step/1`, inside `Runtime.execute_step/2` (D-08). Reconciler preflight is bypassable — `start_handoff_run/3` calls `execute_step/2` directly. Before-claim double-counts under concurrent dispatch.

| Counting option | Description | Selected |
|--------|-------------|----------|
| `count(*) + sum(retry_count)` per check (D-56.1-B) | No migration for `max_steps` | |
| Durable `rail_steps` counter | Exact; one writer; needs a migration | ✓ |

**Locked:** durable counters (D-06). D-56.1-B's *diagnosis* is exact and confirmed; its *prescription* is superseded because the aggregate is read-then-decide and overshoots by up to N−1 under concurrent siblings, and because it would have to stay correct across five `create_step/2` call sites plus `retry_step/1`.

**Notes:** limits materialize as **typed columns**, not jsonb — the GA-3 researcher argued jsonb on a convention-over-columns doctrine, but that doctrine governs span attributes, and a jsonb `::int` cast in a `WHERE` poisons a host transaction on junk. The red-team then corrected the migration itself: `add_if_not_exists`/`create_if_not_exists` (these files are copied into host repos), no composite index (blocking build, and it only existed for the cut `sweep/1`), and `NOT VALID` on the CHECK constraints.

## Config surface, precedence & naming

| Option | Description | Selected |
|--------|-------------|----------|
| Per-run only | Simple; one source of truth | |
| App default + per-run, tighten-only min-join | Mirrors Phase 56 D-04's doctrine | |
| App default + per-run, last-writer-wins | Same doctrine, different input class | ✓ |

**Locked:** two-rung ladder, per-run wins outright (D-11). Deliberately different from Phase 56's D-04 **on D-04's own stated predicate** — D-04 tightens only because its host operand is request-derived (`Map.new(conn.assigns)`); both rail operands are host source code, so the predicate returns false and the same doctrine yields last-writer-wins.

| Timeout key name | Selected |
|--------|-------------|
| `:timeout` | ✗ actively dangerous — an existing `@dispatch_keys` member meaning the 5s per-step handler bound; a top-level `timeout:` would be silently swallowed |
| `:max_duration_ms` | |
| `:max_active_ms` | ✓ |

**Locked:** `:max_active_ms` — once pause-exclusion is locked, "duration" misleads, and a name that has to be documented not to mislead is the wrong name.

**Notes:** the red-team killed three sub-decisions here. `:infinity` was cut as redundant under last-writer-wins. `validate_rails_tighten_only/1` was cut as a validator defending a path no Scoria code takes. And the boot-time `ArgumentError` was cut outright — it violates an explicit in-code doctrine (`application.ex:56-58`, T-53-08: "never let this raise or halt `start/2`, since a boot crash takes the entire host app down"), and its safety proof missed the set-but-empty env var case. It also found that `start_handoff/3` does **not** inherit rails "for free" — it is a separate function with its own `with` chain and its own `workflow_attrs` literal, so every delegated run would have shipped unrailed.

## Timeout anchor & paused-time semantics

| Option | Description | Selected |
|--------|-------------|----------|
| Pure wall-clock from anchor | Simplest | |
| Active time (wall clock minus paused) | Excludes `waiting_for_approval` | ✓ |
| Two rails (wall deadline + active budget) | Most expressive | |

**Locked:** active time (D-14). Wall clock would turn Phase 57's confluence gate — a *safety* mechanism — into a run killer: every escalation a human doesn't answer in time halts the run, and adopters learn to disable the gate. Temporal, Airflow's `HITLOperator`, and Step Functions all bound the human wait at the *wait*, never at the *run*.

**Notes:** the single most important red-team change in the phase landed here. The draft put pause accounting at two call sites; the red-team proved the accumulator **leaks** — `complete_step/3` reads the run with no regard for its status and writes `"running"` back over a `waiting_for_approval` run when a sibling step completes, stranding `rail_paused_at` and silently reverting the rail to wall clock. Fix: derive the accounting **inside `Run.changeset/2`** from the status transition, mirroring the in-repo `validate_replay_allowlist_immutability/1` precedent. That also fixed the Phase 57 obligation (below). The draft also cited `Workflows.request_approval/3`, which **does not exist** — the real seam is `mark_waiting_for_approval/3`, and the draft's line number pointed at the `Step` changeset, not the `Run` one.

`last_heartbeat_at` was evaluated as an anchor and rejected as a trap: two writers with different meanings, host-writable via the public cast list, and `retry_step/1` refreshes it on every retry — so a retry loop would reset the clock forever, making the rail immune to the exact runaway it exists to stop.

## Audit & telemetry contract

| Option | Description | Selected |
|--------|-------------|----------|
| One audit row per tripped rail | Complete | |
| One row with a list of rails | Compact | |
| One row naming the first-tripped rail + `rails_snapshot` of all three | DB-enforced one-per-run | ✓ |

**Locked:** one row (D-16), fixed check order `max_active_ms` → `max_steps` → `max_tool_calls`, explicit `dedupe_key`.

| `:observed` frequency | Selected |
|--------|-------------|
| Every check | ✗ forces every adopter to build a stateful per-`run_id` aggregator; gets filtered |
| Threshold crossings (50/80/100%) | ✗ no denominator — rails are nil for ~100% of adopters |
| Once per run at terminal transition | ✓ |
| Sampled | ✗ cannot answer "what is my p99" |

**Notes:** the researcher labelled the dedupe-key issue "the single highest-severity finding across all five areas"; **both red-teams independently proved it wrong** — `build_audit_dedupe_key/1` includes `trace_id`, and `trace_id_for_run/1` returns the run id verbatim, so the key was already unique per run. The explicit key is kept as cheap hardening but the severity claim was demoted, and the real risk (an audit failure aborting the whole halt transaction, so SC#1 beats SC#2 on failure) was named instead. Separately: there is no `reason_code` **column** on `ai_audit_outbox_events` — it lands in two jsonb slots. And `overage` was found to be structurally always `0` for the counter rails, contradicting the design's own no-overshoot guarantee; counter rails now report `limit`/`observed`/`attempted` instead.

## The finding that changed the phase most

Not one of the five areas — the adopter-brick red-team's headline: **`max_tool_calls` had ZERO coverage on every shipped path, not just `MCP.Router`.** `canonical_context/1` never derives `run_id`; all three in-repo callers of `Executor.execute/*` lack it; `Connectors.Invocation.invoke/4` has zero non-test callers; and `runtime.ex:744-758` says in a comment that the runtime deliberately threads only `trace_id`/`parent_id` and leaves tool contexts to the host. No adopter-facing doc mentions either entry point.

That is the Phase 55 "decorative hook" defect repeated — a rail that fires only if a host hand-threads a key Scoria never populates and never documents. Enforcing-and-disclosing was ruled **not acceptable** (the milestone already paid for that once). Locked fix: `Runtime.execute_step/2` injects `run_id`/`step_id` at the existing metadata seam and the host forward is documented as required (D-10).
