# Phase 56.1 Plan 04: Pause Accounting + Active-Time Rail Summary

**The timeout rail (`max_active_ms`) is now real: `Run.changeset/2` derives pause accounting from the `:status` transition itself so the accumulator can never leak, and `Rails.admit_step/2` enforces active time -- not wall clock -- timezone-proof and ahead of the counter rails in the fixed check order.**

## Accomplishments

- `Scoria.Workflows.Run` gains `derive_rail_pause_accounting/1`, wired into `changeset/2`'s pipe chain and mirroring the exact shape of the pre-existing `validate_replay_allowlist_immutability/1`: entering the pause set (`["waiting_for_approval", "paused"]`) sets `rail_paused_at`; leaving it folds the elapsed interval into `rail_paused_ms` and nulls `rail_paused_at`; transitions within the set or with no status change touch neither field. Neither field is in `cast/3`, so the derivation is the sole writer and every status-moving caller -- `mark_waiting_for_approval/3`, `resume_run/1`, `complete_step/3`, `fail_step/3`, `retry_step/1`, `halt_run/3`, and any future Phase 57 path -- is accounted for by construction, closing the accumulator-leak defect the derivation exists to fix (the scenario where a sibling step's unconditional `complete_step/3` write would silently revert an escalated run's pause interval to lost, and the rail to wall clock).
- The named regression -- step A escalates via `mark_waiting_for_approval/3`, sibling step B then completes via `complete_step/3` -- ends with `rail_paused_at == nil` AND `rail_paused_ms > 0`, proving the accumulator does not leak.
- `Scoria.Workflows.Rails.admit_step/2`'s atomic CAS now also enforces `rail_max_active_ms`: `EXTRACT(EPOCH FROM ($now - COALESCE(started_at, inserted_at))) * 1000 - rail_paused_ms < rail_max_active_ms`, composed via `Ecto.Query.dynamic/2`. `now` is bound as an Elixir parameter with an explicit `:utc_datetime_usec` type ascription -- proven correct under a non-UTC session `TimeZone` via a real `SET LOCAL TIME ZONE` test against the sandboxed connection, not a stub.
- `Rails.deny_reason/2` (extended from `/1` with a default `now` param, backward compatible) now names `:max_active_ms_exceeded` first per the fixed check order (`max_active_ms -> max_steps -> max_tool_calls`), so a run over both its time and step budgets reports the time reason.
- `Scoria.Workflows.Runtime.execute_step/2` adds a pure-Elixir `max_active_ms` pre-check (`active_time_check/1`) ahead of `Rails.admit_step/2` -- zero queries, since this rail maintains no counter -- and fails closed on a nil anchor. On denial it builds the `max_active_ms` envelope (carrying `"overage"`, which the two counter rails deliberately omit) and takes the same `halt_run/3` + `raise StepFailureSignal` path plan `56.1-01` established.
- The Phase 57 invariant ships as a named regression test: a run escalated into `waiting_for_approval`, backdated 10 minutes past its 5-minute `max_active_ms` ceiling via `rail_paused_at`, then approved and resumed, executes its next step without halting -- because the paused interval is folded into `rail_paused_ms` (D-15) before the next admission check runs, proving active time (not wall clock) is what the rail measures.
- Retrying counts as active time: a run cycling through `retry_step/1` never gets `rail_paused_at`/`rail_paused_ms` touched (since `"failed" -> "retrying"` is not a pause-set transition), so a retry loop cannot outrun the rail by accident.
- Added the required moduledoc sentences: `Scoria.Workflows.Runtime`'s moduledoc states `max_active_ms` is a ceiling on admission, not a wall-clock kill; `Scoria.Workflows.Rails`'s moduledoc states the accepted limitation (three residual gaps: a long tool call bounded only by the 5s `Task.yield`/`shutdown` default, orphaned-`"running"` crash recovery, and `waiting_for_approval` by design).
