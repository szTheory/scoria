# Phase 56.1 Plan 01: Tracer + Terminality Guards Summary

**Per-run `max_steps` rail: an atomic CAS admission halts a run terminally with audited evidence, and six guards (G1-G6) close every path that could resurrect it.**

## Accomplishments

- One migration adds seven `rail_*` columns to `ai_workflow_runs` (`add_if_not_exists` throughout, no index, no CHECK constraint, no backfill — `NULL` limits preserve today's unlimited behavior).
- `Run` gains the terminal `"halted"` status, `Run.halted?/1`, and the three `rail_max_*` limits in `cast/3` — the four counter/pause fields are deliberately excluded, with a load-bearing comment explaining why `Repo.update_all(inc: ...)` and `Repo.update` via changeset are disjoint writer classes by construction.
- New `Scoria.Workflows.Rails`: `admit_step/2` is a single atomic `Repo.update_all(inc: ...)` compare-and-swap (`{1, [count]} -> {:ok, count}`, `{0, _} -> :denied`); the `is_nil/1` disjunct makes an unlimited run admit-and-count rather than short-circuit, which is what makes the sizing recipe (`max(rail_steps)` over historical runs) possible. `deny_reason/1` is a cold-path `Repo.one/1`.
- A committed spike test proves `Repo.update_all` with `select:` returns the **POST-increment** value (RESEARCH Open Question 1 — zero in-repo precedent existed before this).
- `Scoria.Workflows.halt_run/3`: one transaction, run locked `FOR UPDATE` first (establishing the global run-then-steps lock order shared with `claim_step/1`'s G1 guard), cancels queued/retrying siblings, writes a `run_halted` checkpoint/event, a `run.rail.tripped` audit-outbox row (`actor_ref: "system:scoria.rails"`), and the terminal `Run.changeset` write. Normalizes `Ecto.StaleEntryError` and a dedupe_key unique-constraint collision to `{:error, :already_halted}`.
- `Runtime.execute_step/2` calls `Rails.admit_step/2` after `claim_step/1` succeeds and before `span_opts` is built; on `:denied`, the trip (not the check) happens as the **first** statement inside the existing step span, so the span stays ERROR-marked exactly as `fail_step_and_signal/2` already does.
- Six terminality guards close every resurrection path: **G1** (`claim_step/1`, refuse, run-first lock — the keystone, since `claim_step/1` has exactly one caller in `lib/`), **G2** (`retry_step/1`, refuse), **G3** (`resume_run/1`, no code change — ships a regression test only, since `"halted"` structurally falls through to the existing catch-all), **G4/G5/G6** (`complete_step/3`, `fail_step/3`, `mark_waiting_for_approval/3` — a shared `clamp_run_status/2` clamps the computed next status back to `run.status` when already halted; `complete_step/3` additionally suppresses `completed_at`/`current_step_id`/`error_envelope` via `suppress_when_halted/3`).
- The accepted, documented interleaving gap: a sibling already holding a stale `%Run{}` copy (loaded before the halt commits) never reaches the clamp at all — its own `repo.update!` raises `Ecto.StaleEntryError` and strands the step — proven by three dedicated tests using the existing two-copy stale-update pattern (no `Task.async` needed).
- A genuine two-concurrent-`Task.async` `halt_run/3` test (D-04) proves exactly one `{:ok, %Run{}}` and one `{:error, :already_halted}`, green across five different `--seed` values.

**3. [Rule 1 - Bug] Made the same guard's `update_all`/Approval-schema co-occurrence check proximity-scoped instead of whole-file**
- **Found during:** Task 1 full-suite verification
- **Issue:** The guard's second test flags any file containing BOTH an `update_all(` call AND an `Approval` schema reference ANYWHERE in the file — a whole-file check. `halt_run/3` legitimately introduced `workflows.ex`'s first `update_all(` call (cancelling sibling `Step` rows, not `Approval` rows), which false-positived purely because the same file also references `Approval` elsewhere (e.g. `mark_waiting_for_approval/3`).
- **Fix:** Rewrote the check to scan a bounded window (6 lines before to 2 lines after) around each `update_all(` call site for an `Approval` reference, rather than the whole file — this still catches the real offending shape (`Repo.update_all(from(a in Approval, ...), ...)`, whose `Approval` reference is always within a line or two of the call) without flagging an unrelated schema's `update_all` elsewhere in the same file.
- **Files modified:** `test/scoria/workflows/approval_write_invariant_guard_test.exs`
- **Committed in:** `93a4d30b`
