# Phase 56.1 Plan 03: Tool-Call Rail Enforcement + CAS Determinism Battery Summary

**`max_tool_calls` is now enforced at both MCP tool entry points (`MCP.Executor.execute/4` and `Connectors.Invocation.invoke/4`) via one shared, marker-guarded admission that never double-counts, with the residual no-run-attribution gap made honest via telemetry instead of silent, and a genuine-concurrency test battery proving the CAS holds under 20-way contention.**

## Accomplishments

- `MCP.Executor.execute/4` gained `admit_tool_call_rail/2` as the literal first statement of its dispatch, strictly ahead of `resolve_classification/2` -- proven by a shell-level line-number assertion and by a dedicated test showing the rail denies even a call that would otherwise have been refused as unclassified (`require_tool_classification: true` + `rail_max_tool_calls: 0`).
- Denial builds the D-03 string-keyed error envelope, calls `Workflows.halt_run/3`, and returns the atom-keyed `{:error, %{status: :run_halted, reason_code: "max_tool_calls_exceeded", rail: "max_tool_calls", limit:, observed:}}` shape mirroring `unclassified_tool_envelope/2`.
- The `:rail_admission` context marker (mirroring `resolve_classification/2`'s own struct-match idempotence guard) lets one logical call admitted at `Connectors.Invocation.invoke/4` flow into `Executor.execute/4` without being re-admitted or double-counted -- proven by a dedicated test asserting the persisted counter moves by exactly `1` across the hop. The marker is deleted from context immediately after the admission decision inside `execute/4`, so it never leaks into a tool's own `execute/2` context.
- SC#4's no-run-attribution no-op: a call with no `:run_id` executes the tool normally and emits `[:scoria, :run, :rail, :skipped]` exactly once with `reason: :no_run_id` and a `site` distinguishing the caller (default `:mcp_executor`, overridable via an explicit `:rail_site` context key). A `Logger.warning` fires once per boot per site, but ONLY when `max_tool_calls` is actually configured somewhere (`config :scoria, Scoria.Runtime.Rails, max_tool_calls: N`) -- never an info-level "rail not configured" line that would fire for every adopter forever.
- `Connectors.Invocation.invoke/4` admits before `replay_resolution/5` is evaluated, so a `:historical_stub` or `:blocked` short-circuit -- which never reaches `Executor.execute/4` -- has already consumed its budget (the attempts-not-successes contract). Denial returns through the same `{:error, %{...}}` shape `replay_blocked_response/1` uses, carrying `status: :run_halted` and `site: "connectors_invocation"` in the envelope handed to `halt_run/3`.
- `Runtime.execute_step/2`'s `decorate_run_with_trace_context/4` (was `/3`) now injects `"run_id"` and `"step_id"` into `run.metadata["runtime"]` alongside the existing `"trace_id"`/`"parent_id"` (D-10) -- the decorated copy is never persisted, and a handler test proves both the handler sees the ids and the reloaded run's stored metadata never carries them.
- CAS determinism and counter-semantics battery (Task 3), all genuine `Task.async`/`Task.await_many` concurrency where the claim requires it (not a sequential loop that would pass by accident): 20-concurrent `admit_tool_call/2` against a limit of 10 yields exactly 10 admits/10 denials/counter==10; a fan-out of 10 step rows with only 3 admissions leaves `rail_steps == 3`; five `retry_step/1` + `admit_step/2` cycles leave `rail_steps` five higher with exactly one step row (proving the counter counts executions, not rows); the SC#3 two-part proof (zero halts AND `rail_steps == 50`) is asserted on the SAME unconfigured run in one test body; a post-approval resumption is pinned to cost 2 against `max_steps` (RESEARCH Open Question 6, resolved affirmatively); and mixed concurrent `halt_run/3` + `claim_step/1` (in `workflows_test.exs`) and `halt_run/3` + `admit_tool_call/2` (in `rails_test.exs`) both complete inside `Task.await_many/2`'s bound with no Postgres deadlock, corroborating the run-first `FOR UPDATE` lock order established in plan 01.
- The concurrency lane (`test/scoria/workflows/rails_test.exs test/scoria/workflows_test.exs`) was run twice with `--seed 0`; both green, 48/48.

## Decisions Made

See `key-decisions` in frontmatter. Notably: the `:rail_admission` marker is a purely internal cross-module idempotence guard and must be stripped before a tool sees it (unlike `:tool_classification`, which is intentionally tool-visible); and a `:denied` CAS result is disambiguated via `Rails.deny_reason/1` before being treated as a genuine rail trip, since a synthetic/non-persisted `run_id` (an established pre-existing test/adopter pattern for budget-only context) must remain a no-op, not a crash.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Bug] Fixed `Ecto.NoResultsError` crash when a context's `:run_id` matches no persisted `%Run{}` row**
- **Found during:** Task 1, running the pre-existing `test/scoria/mcp/executor_test.exs` suite against the new admission gate
- **Issue:** `Rails.admit_tool_call/1` returns `:denied` identically whether a run is genuinely at its limit OR `run_id` never matched any row (`{0, _}` in both cases). Several pre-existing tests pass a synthetic `run_id: Ecto.UUID.generate()` purely for budget/trace-reservation context (not a real workflow run), and my first implementation called `Workflows.get_run!(run_id)` unconditionally on denial, raising `Ecto.NoResultsError` and crashing 4 previously-passing tests.
- **Fix:** On `:denied`, disambiguate via the already-shipped cold-path `Rails.deny_reason/1` (from plan 01). A `:no_run` result is treated as the same no-op class as a missing `:run_id` (emits `[:scoria, :run, :rail, :skipped]` with `reason: :no_run`, executes the tool normally) rather than crashing or halting a run that does not exist.
- **Files modified:** `lib/scoria/mcp/executor.ex`
- **Committed in:** `cb72a9eb` (Task 1 commit)

**2. [Rule 1 - Bug] Fixed the `:rail_admission` marker leaking into a tool's own execution context**
- **Found during:** Task 1, full-suite run surfaced a regression in `test/scoria/mcp/router_test.exs` (a pre-existing test whose fixture tool echoes its entire context back as its result)
- **Issue:** The `:rail_admission` marker, added to `context` for cross-module idempotence, was still present when `context` flowed into `tool_module.execute(args, context)`, changing the observable context a tool receives -- an implementation detail leaking into tool-visible state, and a real backward-compatibility break for any host inspecting its context.
- **Fix:** `execute/4` now deletes `:rail_admission` from `context` immediately after the admission decision, before `resolve_classification/2` and everything downstream runs.
- **Files modified:** `lib/scoria/mcp/executor.ex`
- **Committed in:** `cb72a9eb` (Task 1 commit)

**3. [Rule 1 - Bug] Fixed a pre-existing `KeyError` in `Connectors.Invocation.normalize_live_result/2`**
- **Found during:** Task 2, writing the first `invoke/4` admission test against an ordinary live (non-replay) `%Run{}`
- **Issue:** `replay_resolution/5`'s `nil`-run clause and its catch-all (non-replay) clause both returned an `:execute_live` evidence map omitting `:replay_idempotency_key`, while `normalize_live_result/2` unconditionally reads that key. Before this plan, `invoke/4` had only ever been exercised with either a genuinely absent run (`nil`, whose evidence map IS complete... actually the nil-run clause was ALSO incomplete) or a real replay-mode run (whose evidence comes from `ReplayDisposition.resolve/5` and always carries the key) -- an ordinary live run had zero test coverage and crashed on its first real exercise.
- **Fix:** Added `replay_idempotency_key: nil` to both incomplete evidence maps.
- **Files modified:** `lib/scoria/connectors/invocation.ex`
- **Committed in:** `3690b763` (Task 2 commit)
