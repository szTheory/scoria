## Sampling Rate

- **After every task commit:** Run the specific new/modified test file(s) for that task
  (e.g. `mix test test/scoria/workflows_test.exs`)
- **After every plan wave:** `mix test --warnings-as-errors` (full suite), **plus** a targeted
  concurrency re-run `mix test test/scoria/workflows_test.exs test/scoria/workflows/rails_test.exs --seed 0`
  **at least twice** — `Task.async` concurrency tests are schedule-sensitive
- **Before `/gsd-verify-work`:** Full suite green, plus an explicit note in the phase summary
  confirming the concurrency tests were run more than once during development
- **Max feedback latency:** ~30 seconds (quick lane)

> **Flake doctrine:** a flaky-once / green-on-rerun result on a NEW concurrency test is a signal to
> investigate the lock-ordering logic, **not** to retry until green. (Mirrors SEED-004 in STATE.md.)

## Required Coverage Floor (from RESEARCH § Validation Architecture)

These are the cells that must each have a distinct test. Research is explicit that
"a few representative tests" does **not** suffice here — each guard closes a *different*
resurrection path via a *different* status transition, so a passing test for one guard is
zero evidence about the others.

### Terminality guards — 9 test cases minimum

| Guard | Site | Interleavings | Shape |
|-------|------|---------------|-------|
| G1 | `claim_step/1` (`workflows.ex:226-246`) | 1 (refuse-side) | sequential |
| G2 | `retry_step/1` (`workflows.ex:549-566`) | 1 (refuse-side) | sequential |
| G3 | `resume_run/1` (`workflows.ex:604-659`) | 1 (**test-only**, no code change) | sequential regression test |
| G4 | `complete_step/3` clamp | 2 (after-commit clamp; stale-copy `StaleEntryError`) | sequential ×2 |
| G5 | `fail_step/3` clamp — *the sneakiest path* | 2 | sequential ×2 |
| G6 | `mark_waiting_for_approval/3` clamp | 2 | sequential ×2 |

> G4/G5/G6 interleaving (b) asserts the **accepted, documented** loss: step strands `"running"`,
> result envelope lost, `StaleEntryError` raised. Assert this — do not try to prevent it.

### Genuinely-needs-real-concurrency group

- D-04: two concurrent `halt_run/3` → exactly one `{:ok, %Run{}}`, one `{:error, :already_halted}`
- D-04: `unique_index` **and** `optimistic_lock` collisions both normalize to `{:error, :already_halted}`
- D-04: lock order run → steps proven deadlock-free (N mixed `halt_run`/`claim_step` tasks complete in bounded time)
- D-09: `2N` concurrent admits against `limit: N` → exactly `N` admits, `N` denials, persisted counter `== N`

### Counter semantics (D-06/D-09) — counts executions, not rows

- Fan-out: `M` step rows created, `K < M` admitted → counter reads `K`, not `M`
- Retry loop: `retry_step/1` ×`R` on one step → counter climbs `R` (row count stays 1)

### SC#3 — two distinct tests, easily conflated into one insufficient test

1. Unconfigured run executes ≥50 steps, zero halts, `rail_max_steps == nil`
2. **Same run:** `rail_steps == 50` — counting is on even when unlimited

> A test proving only (1) would pass even if a regression short-circuited the CAS on `is_nil(limit)`.

### SC#4 — `MCP.Router` no-run-attribution no-op

- `[:scoria, :run, :rail, :skipped]` fires once per call, `metadata.reason == :no_run_id`,
  `metadata.site` distinguishes Router / MCPController / direct host call
- The tool call still completes normally (no-op, not a refusal)
- `Logger.warning` once-per-boot-per-site, only when `max_tool_calls` IS configured

### Config ladder (D-11) — L1 must be a named test, not a table row

| Case | App default | Per-run | Effective |
|------|-------------|---------|-----------|
| **L1** | `10` | `100` | **`100`** ← naive "most restrictive wins" returns `10` here |
| L2 | `100` | `10` | `10` |
| L3 | `10` | absent | `10` |
| L4 | absent | `10` | `10` |
| L5 | absent | absent | `nil` |

Plus: `start_handoff_run(identity, role, rails: [max_steps: 1])` halts on step 2 — proves
`Params.start_handoff/3`'s separate `with` chain actually threads `Rails.resolve/1`.

### Validation refusals (D-12)

`max_steps: 0` / `-5` / `3.5` / `"ten"` → `{:error, {:invalid_rail, …}}` with **no DB row created**.
Unknown key (`max_tool_call:` typo) → `{:error, {:unknown_rail, :max_tool_call}}` — highest-value
test here; the typo silently becoming "unlimited" is the most likely real-world mistake.
Junk app env → run refused, `Logger.error` once per boot, **no `Application.start/2` crash**.

### D-15 pause accounting

1. Invariant: `status not in ["waiting_for_approval","paused"]` ⟹ `rail_paused_at IS NULL`
2. Regression: step A escalates, step B completes → `rail_paused_at IS NULL` AND `rail_paused_ms > 0`

### D-18 trace-registry canary

`test/scoria/observe/semconv_test.exs:276`'s sorted key-list assertion **will** go red when the three
`scoria.rail.*` keys are added. That is the mechanism working. The task touching `semconv.ex` must
update that assertion **in the same commit**. Routing around the canary means misunderstanding it.

### D-16 audit-failure tradeoff

Force the audit insert to fail (duplicate `dedupe_key`) → the **entire** `halt_run/3` transaction
rolls back; run status is NOT `"halted"`. Proves SC#1-beats-SC#2 is intentional, not accidental.

### D-07 migration posture

1. Structural: migration source uses `add_if_not_exists` for every column (file-content contract test)
2. Behavioral: pre-existing rows read `rail_steps: 0, rail_tool_calls: 0, rail_paused_ms: 0`,
   `rail_max_*: nil` after migration — catalog-only, no backfill `UPDATE`
3. If CHECK constraints ship: assert declared `NOT VALID` (or `validate_number` in the changeset instead)
