<domain>
## Phase Boundary

A single run cannot exceed its own step / tool-call / active-time budget unnoticed. Exceeding a rail halts the run **terminally**, and the halt is written to the audit outbox. Rails default to unlimited; **counting is unconditional** so adopters can size limits from real traffic.

**Not in scope:** tenant-level budgets and breakers (`SRE.BudgetEngine` already owns those — RAIL-01 says rails are "distinct from" them); the Govern surface (Phase 58); approval expiry (Phase 57); crash-orphan recovery (see `<deferred>`).
</domain>

<decisions>
## Implementation Decisions

### Halt semantics and terminality

- **D-01 — The halt status is a NEW `"halted"`. Not `"cancelled"`, not `"failed"`.** `Run.@statuses` becomes `~w(running waiting_for_approval paused retrying failed completed cancelled halted)` (`run.ex:5`), plus a `Run.halted?/1` predicate. **No migration** — `run.status` is a plain `:string` (`run.ex:17`) gated only by `validate_inclusion` (`run.ex:61`); `grep check_constraint priv/repo/migrations/` returns zero hits and there is no `Ecto.Enum`.
  `"failed"` is disqualified by SC#2: `resume_run/1`'s clause at `workflows.ex:648-655` (`{"failed", checkpoint, _} -> retry_step(...)`) makes the public façade `Scoria.resume_run/2` (`scoria.ex:75`) a one-call resurrection. `"cancelled"` is reserved — it has **zero** `run.status` writers in `lib/` today, and conflating a system-enforced limit halt with a future operator cancel is irreversible for historical rows (Temporal keeps `TERMINATED`/`CANCELED`/`TIMED_OUT` distinct for exactly this reason; Oban split `cancelled` out of `discarded`).
  Adding a status cannot 500 a page: Scoria already adopted the open-read doctrine and wrote down why (`ui.ex:52-62`, D-24a), and both `UI.tone/1` (`ui.ex:44-45`) and `Copy.status_label/1` (`copy.ex:93-98`) ship catch-alls. `RunSummary`'s `@type` is `status: String.t()` (`run_summary.ex:65`) — no typespec narrows.
  **Two mandatory one-line follow-ons:** add `halted` to `ui.ex:39`'s `:fail` clause (otherwise every halted run renders a `:neutral` badge), and ship a `tone("halted") == :fail` unit test — **(revised)**, there is no e2e spec that renders a run badge, so the follow-on would otherwise be unproven.
  — **Reversibility:** one-way — `"halted"` is written to `ai_workflow_runs.status` and to `redacted_refs`/`metadata` jsonb in the audit outbox; historical rows cannot be re-labelled.

- **D-02 — Terminality law: refuse on the initiation side, clamp on the completion side. Six guards.** D-56.1-C enumerated only initiation-side paths and is **incomplete** — an in-flight sibling resurrects the run without ever touching `retry_step/1`.

  | # | Site | Kind | Change |
  |---|---|---|---|
  | **G1** | `claim_step/1` `workflows.ex:226-246` | refuse | lock the run `FOR UPDATE` (D-04), then `repo.rollback(:run_halted)` if `Run.halted?(run)` |
  | **G2** | `retry_step/1` `workflows.ex:549-566` | refuse | after `repo.get!(Run, ...)` at `:554`, `repo.rollback(:run_not_retryable)` if halted |
  | **G3** | `resume_run/1` `workflows.ex:604-659` | **none** | `"halted"` structurally hits `_ -> {:error, :not_resumable}` at `:657-658`. Ship a test, not code |
  | **G4** | `complete_step/3` `workflows.ex:253-323` | clamp | after `run_status` is computed at `:278-279`, clamp to `run.status` if halted; suppress the `completed_at`/`current_step_id`/`error_envelope` writes at `:306-309` |
  | **G5** | `fail_step/3` `workflows.ex:479-533` | clamp | same clamp after `:485`. **Sneakiest path** — without it a sibling failing after the halt rewrites `"halted"` → `"failed"`, re-opening `resume_run`'s `:648` branch |
  | **G6** | `mark_waiting_for_approval/3` `workflows.ex:328-353` | clamp | same clamp at `:346-349`. Without it a sibling escalating flips `"halted"` → `"waiting_for_approval"`, which `resume_run` resumes at `:608` |

  **G1 is the keystone** — `claim_step/1` has exactly one caller in `lib/` (`runtime.ex:195`), so it closes the dispatched-Task race, direct public `Runtime.execute_step/2` calls, and adopter calls in one place.
  `Run.changeset/2` is called **only** from `workflows.ex`, so the terminality choke point is structurally real.
  **(revised) — the clamp rationale in the draft was wrong, and the real behavior must be documented, not asserted away.** `optimistic_lock(:lock_version)` (`run.ex:63`) force-changes `lock_version` on every `Run.changeset/2`. A sibling already inside `complete_step/3` (run read at `:258`, updated at `:311`) when the halt commits does **not** reach the clamp — its `repo.update!` raises `Ecto.StaleEntryError`, unwinding the whole transaction **including** the `Step.changeset(status: "completed", result_envelope: ...)` at `:260-268`. The step strands `"running"` and its result envelope is lost, and the unlinked Task at `reconciler.ex:56-58` logs a crash. Correctness survives (no resurrection either way) but evidence does not. **Accept and document.** The clamp covers only siblings whose transaction *starts* after the halt commits; G4/G5/G6 must be tested against **both** interleavings.
  — **Reversibility:** costly — six call sites inside `Workflows`' transaction bodies.

- **D-03 — `Workflows.halt_run/3`, a new lifecycle function. Not `fail_step` with `run_status:`.** `fail_step/3` accepts `run_status:` (`workflows.ex:485`), but its checkpoint transition and event type are hardcoded `"step_failed"` (`:499`, `:510`). SC#1 requires the *halt* be in the audit trail; a trail that says `step_failed` does not satisfy it — and G5's clamp would have to special-case its own caller.

  ```
  halt_run(run_id, step_id_or_nil, envelope)
    :: {:ok, %Run{}} | {:error, :already_halted} | {:error, Ecto.Changeset.t()}
  ```

  One `Repo.transaction`, in this order:
  1. **(revised)** `run = repo.one!(from r in Run, where: r.id == ^run_id, lock: "FOR UPDATE")`; if `Run.halted?(run)` → `repo.rollback(:already_halted)`. See D-04 — the draft's `repo.get!` + in-Elixir predicate is a read-then-act, not idempotency.
  2. If `step_id` present: transition that step to `"failed"` with the envelope, mirroring `fail_step` at `workflows.ex:489`. The step is `"running"` at this point (`claim_step/1` set it at `:236`); `Step.@statuses` (`step.ex:5`) permits `"failed"`.
  3. **(revised)** Cancel queued siblings via `update_all` carrying its own predicate — `from(s in Step, where: s.run_id == ^run.id and s.status in ["queued","retrying"])` — and write the `{n, _}` count into the audit row's `metadata["cancelled_sibling_count"]` so the disposition is auditable rather than asserted. `"cancelled"` is legal on `Step` (`step.ex:5`) and excludes them from `complete_step`'s `pending_count` (`workflows.ex:274`).
  4. `insert_checkpoint(repo, ..., replay_transition_checkpoint_attrs(run, "run_halted", "halted", envelope, :error))` — reuse `workflows.ex:903-924`. `Checkpoint.changeset` (`checkpoint.ex:25-37`) has `validate_required` only, no closed vocabulary.
  5. `insert_event(repo, ..., "run_halted")`. `Event.changeset` (`event.ex:22-31`) likewise.
  6. Write the audit-outbox row (D-14) — **inside this transaction**.
  7. `Run.changeset(run, %{status: "halted", current_step_id: step_id, latest_checkpoint_id: cp.id, error_envelope: envelope, completed_at: now})`.
  8. Post-commit: `broadcast(run.id, {:workflow_updated, run.id})` and the telemetry emits (D-15).

  **In-flight sibling disposition** (BPMN terminate-end-event semantics): `"queued"`/`"retrying"` → `"cancelled"`; `"running"` → left alone to finish (no kill primitive at step granularity, D-19); `"waiting_for_approval"` → left alone (D-05).

  **Error envelope — string keys** (it lands in a jsonb column; precedent `runtime.ex:325,353,715-719`, normalized by `to_string(key)` at `:854-857`):
  ```elixir
  %{"status" => "run_halted",
    "reason_code" => "max_steps_exceeded" | "max_tool_calls_exceeded" | "max_active_ms_exceeded",
    "rail" => "max_steps" | "max_tool_calls" | "max_active_ms",
    "limit" => 50, "observed" => 50, "attempted" => 51,   # (revised) — see D-15
    "run_id" => run.id, "step_id" => step_id,
    "halted_at" => DateTime.to_iso8601(now)}
  ```
  `limit` + `observed` are mandatory — LangGraph's un-attributed `GraphRecursionError` is the anti-pattern. **Do not include `"consecutive_failures"`**: `runtime.ex:657-658` reads that key off `run.error_envelope` to build budget metadata for a next step that by construction never runs.
  — **Reversibility:** costly — a new public `Workflows` function plus a new checkpoint/event vocabulary written to durable rows.

- **D-04 — (revised) Concurrency: a single `FOR UPDATE` on the run row, taken first, establishes one global lock order.** The draft's "multi-node safe by idempotency, not locking" is **false**. Under READ COMMITTED two concurrent halts (two rails tripping on sibling steps) both read `"running"` and both proceed; the loser hits either the `unique_index(:ai_audit_outbox_events, [:tenant_id, :dedupe_key])` (`20260511171000_create_sre_incident_and_audit_tables.exs:162`) → `repo.rollback(changeset)`, or `optimistic_lock` at step 7 → **raises `Ecto.StaleEntryError`** out of `Repo.transaction/1`. Neither is `{:error, :already_halted}`.
  Worse, the draft's lock order was inverted: `halt_run/3` locked Step rows (steps 2-3) then the Run row (step 7), while G1 inside `claim_step/1` reads the Run then updates a Step (`workflows.ex:232-236`) — a textbook `{step,run}` / `{run,step}` deadlock cycle, aborting one transaction at a random point inside a run-killing code path.
  And `Step` has **no `lock_version` and no `optimistic_lock`** (`step.ex:1-58`) and `claim_step/1`'s update carries a WHERE of only `id = ?` (`:236`), so without the run lock a queued sibling cancelled in step 3 can be overwritten back to `"running"` by an in-flight `claim_step` after the halt commits (EvalPlanQual re-checks only `id = ?`) and **execute under a halted run**.
  **Lock:** the run row is the FIRST lock taken by `halt_run/3` and by G1, so the order is always run → steps. `halt_run/3` additionally rescues `Ecto.StaleEntryError` and unique-violation and normalizes both to `{:error, :already_halted}`.
  — **Reversibility:** reversible.

- **D-05 — A run in `waiting_for_approval` is never halted in place; its approvals are untouched.** Rails are admission-time only and there is no tick, so `list_runnable_steps/0` (`workflows.ex:101`, joins on `r.status in ["running","retrying"]`) never dispatches a paused run. The only way in is a sibling still `"running"` when the run flipped — G6's clamp makes that safe. On halt, pending `Approval` rows are **not** modified: terminality already holds (`Workflows.approve/3` at `workflows.ex:665+` never writes `run.status`, and the subsequent resume hits G3), and auto-expiring couples the rail to the approval surface Phase 57/58 owns.
  **(revised) — this carries a one-clause UI obligation, because the dashboard does NOT degrade gracefully; it reports a false failure.** `maybe_resume_approval/3` (`approvals_live/index.ex:703-711`) calls `Resume.resume_run(run_id)` *after* `Workflows.approve/3` has already committed, and its `{:error, reason}` renders through the generic clause at `index.ex:749-751` as **"Could not record approved approval decision: :not_resumable"** — telling the operator their approval failed when it was recorded. Add `defp approval_error_message(_status, :not_resumable), do: "Decision recorded. This run was halted by a per-run rail and cannot be resumed."` above the generic clause, and make `maybe_resume_approval/3` return `{:ok, socket}` with an `:info`-tone toast for `:not_resumable`.
  — **Reversibility:** reversible.

### Counting, enforcement, and schema

- **D-06 — Counting is a durable counter on the run row. D-56.1-B's aggregate is superseded.** D-56.1-B's *diagnosis* is exact and confirmed: `retry_step/1` reuses the row (`workflows.ex:560`) then sets `run.status = "retrying"` (`:584`), which `list_runnable_steps/0` re-admits (`:101`), so plain `count(*)` is invariant across an unbounded retry loop. Its *prescription* (evaluating `count(*) + coalesce(sum(retry_count),0)` per check) is superseded because:
  1. **It is exact; the aggregate is not.** The aggregate is read-then-decide over rows the check does not mutate, so N concurrent siblings all read the same value and all pass — overshoot up to N−1. A single-statement compare-and-swap row-locks the run: exactly `limit` executions are admitted.
  2. **One increment site, not six** — the aggregate must stay correct across the five `create_step/2` call sites (`scoria.ui.e2e.ex:269`, `runtime.ex:178`, `workflows/runtime.ex:702`, `:1205`, `prompt_release.ex:29`) plus `retry_step/1`.
  3. **It is the semantics RAIL-01 means** — LangGraph `recursion_limit`, OpenAI Agents SDK `max_turns` and Claude Agent SDK `max_turns` all count *executions*. `count(*)` counts *rows*, so a handler fanning out 40 step rows would trip `max_steps: 20` before one executed.

  **Never use `sum(attempt)` as a shortcut** — numerically identical today but `:attempt` is host-castable (`step.ex:41-42`), i.e. a tamperable basis.
  **Accepted, documented gap:** step rows created but never executed do not count. A fan-out bomb creating 10 000 rows halts after `max_steps` of them *start*; the rest sit `queued` under a halted run, structurally undispatchable. Row-count explosion is a different problem from a runaway loop.
  — **Reversibility:** one-way — the counters are columns on `ai_workflow_runs`; removing them is a second migration and invalidates every historical row's evidence.

- **D-07 — Schema: typed columns on `ai_workflow_runs`, one migration, no backfill.** The limits are materialized as columns rather than jsonb because the atomic predicate (D-09) needs them: a jsonb `::int` cast inside a `WHERE` raises `invalid_text_representation` on junk and, inside a host transaction, poisons it. `replay_overrides` is direct in-schema precedent for materializing run state (`run.ex:66-76`).

  ```elixir
  alter table(:ai_workflow_runs) do
    add_if_not_exists :rail_max_steps,      :integer     # nil = unlimited
    add_if_not_exists :rail_max_tool_calls, :integer     # nil = unlimited
    add_if_not_exists :rail_max_active_ms,  :bigint      # nil = unlimited
    add_if_not_exists :rail_steps,          :bigint, null: false, default: 0
    add_if_not_exists :rail_tool_calls,     :bigint, null: false, default: 0
    add_if_not_exists :rail_paused_ms,      :bigint, null: false, default: 0
    add_if_not_exists :rail_paused_at,      :utc_datetime_usec
  end
  ```

  - **(revised) — `add_if_not_exists` / `create_if_not_exists` throughout.** House style (`20260523000100_add_replay_safe_execution_truth.exs:8-11,31-33`) exists precisely because these files are **copied into host repos** by `ApplyExecutor.copy_missing_migrations!/2` and may be partially applied. The draft used bare `add`.
  - **(revised) — NO `[:status, :started_at]` index.** `index(:ai_workflow_runs, [:status])` already exists (`20260511000100_create_workflow_tables.exs:23`); the composite existed solely to serve `sweep/1`, which is cut (see `<deferred>`). A plain in-transaction `CREATE INDEX` takes a `SHARE` lock blocking **all writes** to `ai_workflow_runs` for the build — and `grep -rln "disable_ddl_transaction\|concurrently" priv/repo/migrations/` returns **zero hits**, so there is no in-repo precedent for the safe form and the plan would ship the blocking one by default.
  - **(revised) — CHECK constraints are `NOT VALID` or omitted.** The cited house style (`20260523000100...:25-29`) has no `NOT VALID`, so it takes `ACCESS EXCLUSIVE` plus a full-table validation scan. Ship the counters `>= 0` / limits `IS NULL OR >= 0` constraints as `NOT VALID` (new rows are checked; the backfill scan is skipped), or rely on `validate_number` in the changeset and omit them. Planner's call; the blocking scan must not be silent.
  - **Postgres 16** (`compose.yml:32`, `.github/workflows/ci.yml:36`): `ADD COLUMN ... DEFAULT <constant>` is catalog-only, no rewrite. **No backfill** — existing runs get `0` counters and `NULL` limits, and `NULL` = unlimited, so every pre-existing and unconfigured run behaves exactly as today (SC#3).
  - **`:bigint` for counters, not `:integer`** — an *unlimited* run counts forever; `int4` overflow would create a new crash class inside the crash-prevention feature.
  - **`rail_steps` / `rail_tool_calls` / `rail_paused_ms` / `rail_paused_at` are deliberately absent from `Run.changeset/2`'s `cast/3`.** This is the read-modify-write defence and needs a load-bearing comment: `Repo.update` SETs only `changeset.changes`, so a concurrent changeset holding a stale `%Run{}` cannot clobber a counter; conversely `Repo.update_all(inc: ...)` does not touch `lock_version`, so the increment can never provoke `Ecto.StaleEntryError`. The two writer classes are disjoint **by construction**. (The pause fields are written by the changeset itself — D-11 — not by `cast/3`.)
  - **Only the three `rail_max_*` limits enter `cast/3`**, with `validate_number(greater_than_or_equal_to: 0)`.
  — **Reversibility:** one-way — a released migration copied into host repos. Never edit this file after release; corrections ship as a new file.

The marker survives the hop — `canonical_context/1` (`executor.ex:832-848`) is purely additive and `attach_replay_context/3` (`invocation.ex:137-153`) is additive with a passthrough fallback.

  **Check order is fixed and testable: `max_active_ms` → `max_steps` → `max_tool_calls`.** `max_active_ms` first because it is the only rail whose overage is unbounded and unrelated to work performed, and it is the cheapest (pure `DateTime.diff/3`, zero queries).
  **(revised) — the trip, not the check, goes inside the span.** The draft contradicted itself (D-10 said "inside the `Observe.span/4` body"; D-14 said "before the span opens"). `Observe.span/4` reads `opts[:attributes]` at emit time (`observe.ex:371`) with no API to add them from inside the body, so the check must precede `span_opts`. On `:ok`, no `:attributes` key is added — zero change and zero span overhead. On denial, add `attributes: Semconv.rail_attributes(...)` to `span_opts`, then call `Observe.span/4` and, as the **first** statement of its body, call `halt_run/3` and `raise StepFailureSignal, return_value: {:error, envelope}`. `observe.ex:144-149` marks the span `ERROR` and reraises; `execute_step/2`'s `rescue e in StepFailureSignal -> e.return_value` (`runtime.ex:236-238`) sits outside the span and restores the value verbatim — the working precedent is `fail_step_and_signal/2` (`runtime.ex:408-411`).

  **(revised) — two public return contracts must be locked in the plan.** `MCP.Executor.execute/4` returns `{:error, %{status: :run_halted, reason_code: ...}}` on denial, mirroring Phase 56's `unclassified_tool_envelope/2` shape (`executor.ex:95-102`). `Runtime.execute_step/2`'s new `{:error, envelope}` propagates to `Scoria.start_handoff_run/3`, whose `with` matches `{:ok, _completed_step}` (`runtime.ex:184-186`) — enumerate the shape.

- **D-09 — The atomic check-and-increment, and the honest overshoot contract.**

  ```elixir
  def admit_tool_call(run_id, now \\ DateTime.utc_now()) do
    query =
      from(r in Run,
        where: r.id == ^run_id,
        # THREE-VALUED-LOGIC TRAP: `r.rail_tool_calls < r.rail_max_tool_calls`
        # is NULL (not TRUE) when the limit is NULL, the row does not match,
        # and "unlimited" silently becomes "deny everything". The is_nil/1
        # disjunct is MANDATORY on every rail predicate -- and it is also what
        # makes an unlimited run admit-and-COUNT rather than short-circuit.
        where: is_nil(r.rail_max_tool_calls) or r.rail_tool_calls < r.rail_max_tool_calls,
        select: r.rail_tool_calls)

    case Repo.update_all(query, inc: [rail_tool_calls: 1]) do
      {1, [count]} -> {:ok, count}
      {0, _} -> :denied
    end
  end
  ```

  `admit_step/2` is the same statement over `rail_steps`/`rail_max_steps` plus the active-time predicate:
  ```sql
  AND (r.rail_max_active_ms IS NULL
       OR (EXTRACT(EPOCH FROM ($now - COALESCE(r.started_at, r.inserted_at))) * 1000
           - r.rail_paused_ms) < r.rail_max_active_ms)
  ```
  In-repo precedent for `inc:` on a claim path: `relay.ex:108-111`.

  **(revised) — COUNTING IS UNCONDITIONAL. The draft's "the ~100% of adopters with rails unset pay zero queries" destroys SC#3 and must be deleted.** ROADMAP SC#3 says verbatim *"counting is always on so limits can be sized from real traffic"*, D-17's sizing recipe reads `max(rail_steps)` off the table, and the `is_nil` disjunct above exists **precisely so an unlimited run admits-and-increments**. Short-circuiting on `is_nil(limit)` would leave `rail_steps`/`rail_tool_calls` at `0` forever for every adopter, making the entire sizing on-ramp unimplementable and the counters write-only. **Lock: `admit_step/2` and `admit_tool_call/2` always execute their single UPDATE.** The only conditional work is the cold-path deny-reason `Repo.one/1`. The pure-Elixir `max_active_ms` pre-check may short-circuit on `is_nil` because it maintains no counter. Cost: one indexed single-row UPDATE per step and per admitted tool call for every adopter — accepted, and named as accepted, because SC#3 requires it.

  **`^now` as an Elixir parameter, never `fragment("now()")`** — Postgres `now()` is transaction-start time; inside a long host transaction it is stale and the rail under-fires, and it cannot be frozen in tests. Matches `workflows.ex:229,254,480`.
  **Deny-reason disambiguation is a cold path** — `{0, _}` means no matching row; one follow-up `Repo.one/1` over the rail columns resolves it (`nil` → `:no_run`; else the fixed check order names the reason).
  **Rejected: `r.status in ["running","retrying"]` in the admission WHERE.** A host calling `MCP.Executor.execute/4` with a `run_id` for a run currently `waiting_for_approval` or `paused` succeeds today; adding the predicate would start denying it. That is a brick.
  **Increment ordering: BEFORE the work, unconditionally, never decremented.** This is **not** a contradiction of Phase 55's D-07 — D-07 governs *billing* (metering actual consumption, which legitimately reads the result afterwards); a rail is *admission control*. Say so in the docs. Increment-after is structurally inert against the primary threat: an infinite loop of crashing calls never reaches a post-hoc increment. Oban's precedent is identical (`attempt` bumped in the fetching UPDATE).
  **Documented consequence: rails count ATTEMPTS, not successes.** A run with `max_tool_calls: 100` that times out 100 times halts. Replayed and stubbed calls count.

  **The honest contract, verbatim for the moduledoc and guide:**

  > `max_active_ms` is a **ceiling on admission, not a wall-clock kill** — work already in flight when the budget is exhausted is allowed to finish.

  **(revised) — a new serialization class, not an "asymmetry".** If a host wraps `MCP.Executor.execute/4` in `Repo.transaction/1`, the run row's exclusive lock is held for that transaction's full duration — up to the tool Task timeout (`executor.ex:544`, default 5 000 ms) — blocking every sibling's `complete_step` (`workflows.ex:311`), `fail_step` (`:521`) and `mark_waiting_for_approval` (`:348`). ### The timeout rail

- **D-14 — The timeout rail measures ACTIVE time, not wall clock.** `elapsed_active_ms = diff(now, anchor) - run.rail_paused_ms`, anchored at `coalesce(run.started_at, run.inserted_at)`. `create_run/1` sets `started_at: now` inside the insert `Multi` (`workflows.ex:119`) and no `started_at:` write in `lib/` ever targets `Run` again; the fallback covers a caller explicitly passing `started_at: nil` (`Map.merge/2`'s second argument wins), and `inserted_at` is `NOT NULL` via `timestamps()` (`run.ex:35`). Fail-closed on a nil anchor, never skip the rail.
  **Pause set = `["waiting_for_approval", "paused"]`.** `"paused"` has zero writers in `lib/` today; include it now so a Phase 57/58 pause that picks it is covered without a second migration.

  **Why active time, not wall clock.** RAIL-01's threat is a runaway *executing* agent. A run in `waiting_for_approval` consumes no compute and dispatches nothing (`workflows.ex:101` structurally excludes it). Under wall clock, Phase 57's confluence gate — a *safety* mechanism — becomes a *liability*: every escalation a human doesn't answer in time converts to a halted run, and adopters learn to disable the gate to keep their timeouts usable. That is a security-negative outcome from a security feature. Every comparable system bounds the human wait at the *wait*, never at the *run*: Temporal's guidance is not to use workflow-execution timeout for business logic; Airflow 3.1's `HITLOperator` has a task-scoped `response_timeout` separate from `dagrun_timeout` (3.3 moved HITL tasks to a non-running `awaiting_input` state); Step Functions scopes `TimeoutSeconds`/`HeartbeatSeconds` to the `.waitForTaskToken` task.

  **Time in `"retrying"` counts as active** — deliberately: `retry_step/1` sets `status = "retrying"` (`workflows.ex:583-589`), which is dispatchable, and the retry loop is the canonical runaway.

  **`last_heartbeat_at` is a TRAP — do not resurrect it.** Confirmed written-but-never-read; the only writes are `workflows.ex:403` (in `mark_waiting_for_approval`) and `:588` (in `retry_step`). Three reasons, the third decisive: two writers with *different meanings*, so it is not "last progress"; it is in `Run.changeset/2`'s public cast list (`run.ex:57`), i.e. host-writable, and a rail anchored on a host-writable field is not a rail; and **`retry_step/1` refreshes it on every retry, so a retry loop would reset the clock forever** — the rail would be immune to the exact runaway it exists to stop.

  **Rejected: deriving paused intervals from `ai_workflow_events` at check time.** The data exists and is never pruned (`EventCompactor.maybe_enqueue_compaction/2` is a literal `:ok` stub, `event_compactor.ex:4`), but it is an unbounded aggregate scan per dispatch on a table with no `event_type` index, and unmatched open intervals silently produce wrong arithmetic in a code path that **kills runs**. The event history stays the *audit* record of pauses; the column is the *arithmetic* record.
  — **Reversibility:** one-way — `rail_paused_ms` is a column and the semantics are a published contract that Phase 57 depends on.

## Deferred Ideas

**Cut from 56.1 during the red-team pass** (RAIL-01 is one requirement; these were a second feature wearing its badge):

- **`Scoria.Workflows.Rails.sweep/1`** — a background reaper is a *second* enforcement mechanism with its own multi-node story, its own `detected_by:` telemetry dimension, and a shipped Oban snippet; it is default-off so it satisfies no success criterion, its real target (crash-orphaned runs wedged in `"running"`) is **crash recovery** rather than RAIL-01, and its "multi-node safe by idempotency" argument was false. **Keep the prose limitation statement** (below); defer the function to Phase 58 or the backlog.
- **The `:persistent_term` schema probe and `Rails.reset_schema_probe/0`** — cannot prevent the failure they claim to (D-21), and `:persistent_term.put/2` on a TTL is a global-GC hazard.
- **`:infinity` as a rail value** — redundant under last-writer-wins precedence.
- **`validate_rails_tighten_only/1`** — defends a path no Scoria code takes.
- **A `mix scoria.rails.observe` task** — four lines of SQL answer the question.
- **A composite `[:status, :started_at]` index** — existed only for `sweep/1`.

**The accepted-limitation prose, which DOES ship** (guide + moduledoc):
> Rails are enforced at **admission**. A run already executing a step or a tool call when its budget is exhausted is not interrupted; it is denied at the next admission point. Three cases are not caught: (1) a run wedged inside one long tool call — the only bound is the per-call `Task.yield`/`Task.shutdown` at `executor.ex:549-553`, default 5 000 ms; (2) a run whose steps are all orphaned in `"running"` after a node death — `complete_step/3` leaves `run.status = "running"` while any step is pending (`workflows.ex:277-278`), `list_runnable_steps/0` returns only `"queued"`/`"retrying"` (`:98-104`), so it is never dispatched again and never preflighted (**this is the real residual gap, and it is crash recovery, not approvals**); (3) a run in `waiting_for_approval` — **by design**, not a gap.

**Found during the red-team, out of 56.1 scope, must not be lost:**

- **Replay runs do not inherit rails, contradicting D-09's determinism claim.** A replay is a **new `Run` row** with its own `rail_*` columns resolved at creation, and nothing copies the original run's frozen limits onto it. Either replay rehydration carries the rails or the "deterministic between an original run and its replay" claim must be withdrawn. → Phase 57/58 or a rails follow-up.
- **`Scoria.Workflows.PromptRelease`** creates steps on runs (`prompt_release.ex:29`) — should a release-gate run be railed, and what does a halt do to a pending release? Unaddressed.
- **`Scoria.Workflows.Handoff` rows have no halt disposition.** `Handoff` carries its own `~w(pending running completed failed cancelled)` (`handoff.ex:5`); D-03's sibling table covers `Step` only, so a `pending` handoff on a halted run is left dangling.
- **Nil-tenant runs are invisible to per-tenant audit.** `tenant_id` is nullable on `ai_workflow_runs` (`20260513000100_add_canonical_identity_to_workflow_runs.exs:7`) and `normalize_audit_envelope/1` defaults it to `"system"` (`sre.ex:273`), so every rail halt from a nil-tenant run lands in the `"system"` audit stream — invisible to Phase 58's per-tenant Govern filter. → Phase 58.
- **Phase 55 span-projection gap** (carried from `56-CONTEXT.md`): `Adapters.MCP.emit_tool_span/4` (`adapters/mcp.ex:84-107`) never spreads metadata, so Phase 55's `scoria.trust.*` attributes reach live handlers only and are dropped from the persisted span. Still a phase-55 follow-up; D-18 routes around it rather than fixing it.

**Cleared during the red-team** (recorded so a later reader does not re-investigate): `Scoria.Workflows.BatchEnqueue` (`batch_enqueue.ex:17-31`) only chunks Oban jobs and never touches runs; `Scoria.Orchestrator` has no `create_run`/`execute_step`/`start_run` call. No rail interaction in either.

<open_questions>
## Residual Open Questions

Genuinely undecidable from code. Flag at planning only if blocking.

1. **`Repo.update_all` + `select:` returns the POST-increment value — verify with a 10-line spike.** There is **zero in-repo precedent**: every `Repo.update_all` in `lib/scoria/` is select-less. Postgres `RETURNING` on `UPDATE` returns new-row values, so POST is very likely right, but if it is PRE, D-17's `observed`/`attempted` values flip.
2. **The active-time SQL fragment is timezone-fragile — spike it.** `started_at`/`inserted_at` are `timestamp(6)` **without** time zone (`20260511000100_create_workflow_tables.exs:16,19`). Inside a raw `fragment`, Postgrex encodes a bare `%DateTime{}` as `timestamptz`, and `timestamptz - timestamp` forces an implicit cast that consults the session `TimeZone` — silently shifting the rail by the UTC offset on a non-UTC session. Bind as `type(^now, :utc_datetime_usec)` and test it.
3. **`Redactor.redact/1` on `redacted_refs["reason_code"]`** (`sre.ex:367`) — verify `"max_active_ms_exceeded"` is not caught by a secret pattern.
4. **`normalize_ref_value/1` + `stringify_nested_keys/1` on the two-level `rails_snapshot` with `nil` limits** — verify `nil` survives into jsonb rather than being dropped.
5. **Deadlock surface after D-04's run-first lock order** — should be eliminated by construction; worth one concurrent test against a live DB.
6. **Does a post-approval resumption count as a second step execution against `max_steps`?** `resume_run/1` sets the step back to `"queued"` (`workflows.ex:613`), so under D-06 it increments again — a human-approval round trip costs 2. Defensible; recommend counting it and documenting, with a note that an exemption is a one-line `WHERE` change. **This interacts with D-20's Phase 57 re-sizing warning.**
7. **What rails does a delegated child run inherit?** `start_handoff_run/3` creates a *new* run. Recommend independent per-run rails for 56.1; shared-lineage budget is future work.
8. **Should the pause accumulator be cross-checked against the `waiting_for_approval`/`resume_requested` event pairs in a consistency test?** Cheap, and it would catch a future path bypassing the derivation. 56.1's suite or 57's is a scoping call.
9. **Will an operator-initiated `Workflows.cancel_run/1` ship?** `"cancelled"` is reserved for it. If the product answer is a firm never, it becomes permanently dead vocabulary.
10. **An escape hatch (`force_resume_halted_run/2`) for an operator who raised the limit?** Precedent (Oban's separate `retry/2` verb) says eventually yes. Deliberately not in 56.1 — shipping it alongside the rail invites it becoming the default workaround.
11. **Does a new audit `event_type` warrant a CHANGELOG callout?** `SRE.Relay` is event_type-agnostic (`relay.ex:242`) and every UI filter is positive, so it is inert — but an adopter's own `AuditSink` may pattern-match exhaustively. Inclination: yes, call it out.
</open_questions>
