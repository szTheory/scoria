# Phase 56.1 Plan 02: Config Surface Summary

**`Scoria.Runtime.Rails.resolve/1` two-rung config ladder (last-writer-wins, per-run beats app default in either direction), threaded into both `Params.start/2` and `start_handoff/3` so no run -- including a bounded handoff run -- ships unlimited by accident.**

## Accomplishments

- New `Scoria.Runtime.Rails` module (mirrors `Scoria.Runtime.Defaults`'s shape): `resolve/1` implements `effective = first_present([per_run_value, app_value])` independently per key across the three recognised keys (`:max_steps`, `:max_tool_calls`, `:max_active_ms`) -- last-writer-wins, deliberately NOT Phase 56's D-04 tighten-only join, with the moduledoc stating why (both operands are host source code, not request-derived, so D-04's own predicate is false here).
- Validation is fail-loud, not fail-quiet: `0`, negative integers, floats, and binaries at either rung are `{:error, {:invalid_rail, key, value}}`; an unknown key inside `:rails` (e.g. a typo'd `max_tool_call`) is `{:error, {:unknown_rail, key}}` rather than silently becoming "unlimited".
- `validate_app_env/0` reads `config :scoria, Scoria.Runtime.Rails` in isolation, never raises (defensive `rescue` wrapper plus an inner `Enum.reduce_while` that only ever inspects integers/nil), and is never called from `Scoria.Application.start/2` -- a misconfigured app env refuses the *next run*, logged once per boot via the same ETS `log_once` idiom `Scoria.Observe.Bounds` uses, never the boot itself (T-53-08).
- `Rails.resolve/1` is threaded into BOTH `Scoria.Runtime.Params.start/2` and the genuinely separate `start_handoff/3` `with` chain, each merging `rail_max_steps:`/`rail_max_tool_calls:`/`rail_max_active_ms:` into its own `workflow_attrs` literal as top-level keys (never nested under `metadata:`), so `Workflows.create_run/1`'s existing `run_attrs`-merge-into-`Run.changeset/2` flow persists them with no further wiring.
- `@dispatch_keys` in `params.ex` is untouched -- `:rails` stays absent, confirmed by a direct test that `Params.resume/2` never forwards a `rails:` option into `dispatch_opts`, which is what structurally prevents a resume from ever changing a live run's limits.
- An end-to-end proof (mirroring Plan 01's own `test/scoria/workflows/rails_test.exs` pattern) starts a bounded handoff run via `Scoria.start_handoff_run/3` with `rails: [max_steps: 1]`, then calls `Scoria.Workflows.Runtime.execute_step/2` directly on the delegated child step -- the run reaches `"halted"` with `reason_code == "max_steps_exceeded"`, proving the handoff chain threads the resolution rather than leaving every `start_handoff_run/3` call unlimited (the exact gap D-11 flags as the path that bypasses the Reconciler).
