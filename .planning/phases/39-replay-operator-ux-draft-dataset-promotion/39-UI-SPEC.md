### Type Rules

- Keep exactly two weights in this phase: `400` for narrative and metadata, `600` for headings, counters, selection emphasis, and status chips.
- Use uppercase tracked labels only for section markers, execution-mode chips, dataset state chips, and evidence notebook headings.
- Use monospace only for run IDs, checkpoint IDs, dataset versions, reason codes, replay overrides keys, and frozen evidence references.
- Do not shrink below 12px to fit dense evidence. Solve density with grouping, truncation, and collapsible sections instead.

## Color

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | #FAFAF9 | Workflow page canvas, empty-state background, low-emphasis comparison gutters |
| Secondary (30%) | #FFFFFF | Comparison cards, detail panel blocks, promotion modal, evidence snapshot cards |
| Accent (10%) | #1D4ED8 | Selected comparison source, replay lineage deep links, primary `Promote Trace to Draft Dataset` action, and the single highlighted changed field per comparison group |
| Destructive | #BE123C | Baseline-approval warnings, irreversible confirmation copy, and explicit blocked/error states only |

Accent reserved for: selected original-versus-replay toggle, source run/checkpoint deep links, the primary draft-promotion CTA, and one highlighted changed outcome/value within a comparison card. Do not use accent for every badge, every heading, or sealed-dataset labels.

### Semantic State Colors

- `live`: neutral stone chip; live truth is the baseline, not a warning state.
- `replay`: blue-tinted neutral chip; use for replay branch identity and source-vs-replay framing.
- `historical_stub`: amber chip; indicates replay used frozen historical evidence instead of live execution.
- `replay_blocked`: rose chip; indicates the replay path could not execute because safety conditions failed.
- `draft_open`: emerald chip; selectable promotion targets only.
- `sealed`: stone chip with rose or amber helper copy; visible but never selectable from the draft-promotion action.

## Copywriting Contract

| Element | Copy |
|---------|------|
| Primary CTA | Promote Trace to Draft Dataset |
| Empty state heading | No Replay Comparison Available |
| Empty state body | Select a workflow step with durable checkpoint evidence to compare the original run against its replay branch. Promotion stays disabled until Scoria can freeze an evidence snapshot for the selected trace. |
| Error state | Replay evidence could not be loaded. Refresh the workflow run; if the problem persists, inspect source checkpoint lineage and dataset state before attempting promotion again. |
| Destructive confirmation | Baseline Promotion Approval: Promote this draft evidence into a sealed release-driving baseline? The baseline dataset will remain immutable until an explicit approval workflow records the decision. |

### Copy Rules

- Use `original` and `replay` consistently; never alternate with `before/after` or `old/new`.
- Execution-mode language must stay typed: `live`, `replay`, `historical_stub`, and `replay_blocked` only when backed by durable truth.
- Promotion copy must say `draft dataset` for selectable targets and `sealed baseline` for approval-gated targets. Do not collapse both into generic `dataset`.
- Frozen-evidence language must be explicit: `snapshot`, `source run`, `source checkpoint`, and `recorded outcome`.
- If a replay path was blocked, show the typed `replay_reason_code` in monospace secondary copy under the operator-readable explanation.

## Phase-Specific Visual Contract

- Keep this work inside the existing `/scoria/workflows/:id` truth surface. Do not introduce a separate replay console or dataset-management page for the primary operator flow.
- Preserve the existing two-column workflow layout on desktop:
  - left: workflow tree and timeline truth
  - right: selected-step inspection upgraded into a replay evidence notebook
- Add a replay provenance strip directly below the page header when `run.execution_mode == "replay"`. It must show, in this order:
  - replay branch label
  - source run ID
  - source checkpoint ID
  - execution mode
  - override summary
  - latest replay disposition summary if present
- Replace raw `inspect(...)` blobs in the step detail experience with structured evidence blocks. JSON remains available in collapsible raw sections, but never as the default first read.
- Original-vs-replay comparison stays inline in the detail panel. The promotion form remains modal or drawer-based so operators keep source context visible until the commit-like promotion step.
- Comparison cards must prefer field-group deltas over patch-style text diffs. Show one row group for:
  - provenance
  - overrides
  - checkpoint/output summary
  - safety/execution evidence
  - promotion snapshot summary
- Use calm emphasis. The only saturated focal points should be the selected comparison source, the primary promote CTA, replay-blocked warnings, and explicit baseline-approval warnings.

## Component Inventory

- Replay provenance strip: compact header band for replay runs with source lineage, execution mode, and override summary.
- Comparison source toggle: original trace versus replay trace selector scoped to the selected workflow step.
- Replay evidence notebook: right-rail panel replacing raw dump presentation for the selected step.
- Provenance card: source run, source checkpoint, selected step, actor/tenant if available, and snapshot timestamp.
- Overrides card: normalized replay overrides rendered as key/value chips or rows with `unchanged` and `modified` markers.
- Outcome comparison card: structured original-versus-replay summary for projected context, checkpoint result/error, and replay disposition.
- Safety evidence card: execution mode, replay scope, replay reason code, idempotency key presence, and historical-stub/live indicators.
- Draft dataset target list: open draft datasets as selectable rows; sealed baselines shown below in a disabled, read-only section with approval helper copy.
- Promotion modal or drawer: dataset selection, frozen snapshot summary, optional editable notes/expected output area, and confirmation footer.
- Baseline approval notice card: rendered when the operator inspects sealed targets or tries to promote into a release-driving baseline lane.
- Success notice: inline durable confirmation showing which trace variant was promoted and which dataset version received the snapshot.

## Interaction Contract

- Selecting a workflow step updates the right-rail evidence notebook without losing workflow-tree context.
- If the run is live-only and no replay branch exists, show original checkpoint truth and hide the comparison toggle; do not fabricate an empty replay column.
- If the run is a replay, default the comparison toggle to `Replay` and keep `Original` available as a secondary tab or segmented control.
- Switching between `Original` and `Replay` must update:
  - promoted evidence source
  - displayed checkpoint/output summary
  - execution-mode chip
  - replay safety evidence
  - CTA helper copy
- Promotion is disabled until Scoria can resolve a durable selected source with frozen evidence inputs. Disabled state must explain why, not just dim the button.
- Open draft datasets are selectable targets. Sealed datasets must still be visible, but they render as disabled rows with `Approval required` or `Sealed baseline` helper text. Operators should never wonder whether a baseline exists.
- Promotion must create a frozen evidence snapshot from the chosen source variant. The modal must restate which source is being promoted: `Original trace` or `Replay trace`.
- Any editable JSON/raw fields belong in an advanced section collapsed by default. The first-read experience is structured evidence, not manual JSON surgery.
- Promotion success closes the modal and leaves a durable inline success notice on the workflow page. The notice must identify source variant, dataset name, and dataset version.
- If promotion fails because the target dataset sealed between render and submit, keep the modal open, mark the dataset row as sealed, and refresh the target list rather than dropping the operator back to a blank state.
- If baseline promotion approval is offered, it opens a dedicated confirmation step that repeats immutability semantics. Approval is a workflow-owned action, not an immediate mutation.

## State Contract

- `Live-only run`: no replay strip; detail panel shows original checkpoint truth and draft-promotion affordance if snapshot evidence exists.
- `Replay provenance ready`: replay strip visible, comparison toggle enabled, and replay evidence notebook populated.
- `No comparable source`: neutral empty-state card in the notebook with the empty-state copy above.
- `Historical stub used`: amber badge and helper copy explain that replay reused frozen historical evidence for this seam.
- `Replay blocked`: rose alert block with operator-readable explanation plus typed `replay_reason_code`.
- `Draft promotion ready`: primary CTA enabled and target list shows at least one open dataset.
- `No open draft datasets`: neutral card in the modal explaining that only draft/open datasets accept direct promotion; sealed baselines require approval.
- `Sealed baseline visible`: disabled target row with explicit immutability copy and approval-required notice.
- `Promotion saving`: modal footer disables secondary submits and shows `Promoting snapshot...`.
- `Promotion succeeded`: inline emerald notice with source variant and target dataset version.
- `Promotion failed`: inline rose error inside the modal; preserve operator-entered notes and current source selection.

## Assumptions

- This phase extends the existing workflow run screen and dataset promotion component instead of creating a new top-level dataset UI route.
- Phase 37 and 38 durable replay truth is available on the workflow run, checkpoint, approval, or event surfaces before this UI work lands.
- Promotion in this phase targets open draft datasets directly; sealed release-driving baselines remain visible but gated behind explicit approval semantics.
- No new icon package, JS-heavy diff viewer, or third-party component registry is required.
