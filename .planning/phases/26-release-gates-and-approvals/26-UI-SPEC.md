## Phase-Specific Visual Contract

- Keep the page in the existing calm operator control-plane posture: stone canvas, white evidence cards, compact uppercase section labels, and explicit lineage text before decorative treatment.
- Use a two-column comparison deck on desktop and a stacked deck on mobile. Left column is always `Draft candidate`; right column is always `Active baseline`.
- Put the release gate status strip above the comparison deck. It is the primary focal point on first load and must show three states in order: `Draft blocked`, `Evidence ready or missing`, `Workflow approval pending or recorded`.
- Every metric shown for the draft must sit beside the active value and a concise delta badge. Do not show a draft metric in isolation.
- Favor bordered cards and chips over heavy fills. Reserve filled accent/destructive buttons for final decisions only.
- Monospace text is allowed only for IDs, versions, fixture keys, run IDs, and immutable lineage refs.

## Component Inventory

- Release status strip: three compact gate chips with one-sentence helper copy under the strip.
- Comparison header: draft version, active version, shared dataset version, shared eval spec version, latest run timestamps.
- Summary metric cards: pass rate, threshold verdict, avg latency, total cost, total items.
- Delta evidence table: one row per metric with `draft`, `active`, and `delta` columns.
- Eval evidence notebook: score distribution, failing items list, concise explanations, and links to durable evidence refs.
- Workflow lineage panel: approval request ID, workflow run ID, actor, current approval status, and latest audit event.
- Approval footer: secondary `Reject Release`, primary `Approve Prompt Release`; both remain visible while the page scrolls on desktop.
- Blocking notice card: rendered when dataset version, eval spec version, or baseline anchor mismatch prevents approval.

## Interaction Contract

- Default selection is the most recent draft version for an entity. The active version is fixed as the baseline comparator and cannot be swapped.
- Approval is disabled until all of the following are true:
  - draft prompt status is `draft`
  - active prompt status is `active`
  - both sides have a completed `EvalRun`
  - both runs use the same dataset version
  - both runs use the same eval spec version
  - the draft run has a resolved threshold verdict
  - a workflow approval record exists or can be requested from this surface
- If comparison prerequisites fail, show the blocking notice inline above the footer and keep the primary CTA disabled. Do not hide the CTA.
- Evidence panels that fetch deeper data must use the repo's existing async-result pattern with explicit loading and failure text, not silent spinners.
- Clicking a failing-item row expands inline evidence beneath that row; do not open a separate page for the first level of detail.
- Rejecting a release opens a confirmation modal. Approving a release opens a confirmation modal that repeats the draft version, active version being replaced, dataset version, and eval run ID.
- After approval or rejection, show an inline durable notice in the page body summarizing the workflow-owned outcome and leave lineage links visible.

## State Contract

- `Draft blocked`: neutral/amber status chip; explains that runtime traffic still resolves to the active version.
- `Evidence ready`: emerald chip only when both comparable runs are complete and aligned.
- `Evidence missing`: amber chip when any required run is absent or still running.
- `Comparison invalid`: rose notice when baseline anchor, dataset version, or eval spec version differs.
- `Approval pending`: sky or blue-toned chip linked to workflow lineage.
- `Approved`: emerald notice with activation timestamp and actor.
- `Rejected`: rose notice with actor and persisted reason if present.
