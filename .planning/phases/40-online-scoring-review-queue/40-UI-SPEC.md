## Layout and Interaction Contract

- Primary focal point and first-read hierarchy: operators should notice the highest-severity selected queue row first, then the detail-rail action area, then the summary strip. The queue exists to drive a decision on one candidate at a time, so selection and actionable evidence outrank aggregate counts.
- Use a dedicated review queue page or review queue section inside the operator surface with a two-column desktop layout: left queue list, right evidence/detail rail.
- Keep queue rows dense and scannable: status badge, score summary, trigger reason, workflow/run refs, timestamp, and one-line rationale visible without expansion.
- Selecting a queue row updates the detail rail in place; do not force full-page navigation for primary triage.
- Provide deep links from the detail rail to existing operator surfaces: `/scoria/workflows/:id` for workflow evidence and `/scoria?runtime=...` when runtime context exists.
- Use tabs or pill toggles only for mutually exclusive evidence sources, matching the existing original/replay toggle pattern from Phase 39.
- Keep promotion and dismissal as explicit operator actions in the detail rail footer, not inline row actions, to reduce accidental decisions.
- Any action that could change review state must disable during submit and show `phx-disable-with` copy.
- Approval-required flows for sealed baselines must open a confirmation step with amber styling before dispatching the workflow-owned approval request.
- Dismissal must be reversible only through a deliberate reopen action if implemented later; this phase should treat dismissal as an intentional terminal triage outcome for the queue view, not a silent hide.

---

## Component Inventory

- Review queue list: vertically stacked card rows with filter bar above.
- Filter bar: status, severity, scorer kind, and dataset-candidate state filters; default to `needs review`.
- Summary strip: total flagged items, low-quality count, policy-triggered count, promotion-candidate count.
- Detail rail: evidence notebook with score rationale, scoring provenance, sample provenance, workflow refs, and dataset-promotion readiness.
- Action rail: `Promote candidate`, `Request baseline approval`, `Dismiss candidate`, `Open workflow`.
- Empty-state panel: full-width card in the queue column, not a blank table.
- Error-state panel: inline alert card above queue results with retry action.

## Color

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | `#fafaf9` (`stone-50`) | Page background, queue canvas, muted evidence wells |
| Secondary (30%) | `#ffffff` (`white`) | Cards, detail rail, modal bodies, selected content surfaces |
| Accent (10%) | `#2563eb` (`blue-600`) | Primary CTA, selected queue row border/state, active toggle pill, deep-link text |
| Destructive | `#e11d48` (`rose-600`) | Dismiss/destructive confirmations only |

Accent reserved for: primary review CTA, selected row treatment, active evidence-source toggle, deep links to workflow/runtime detail, and retry actions. Do not use accent blue for neutral badges, passive metadata, or approval warnings.

Additional semantic tones already established in the repo remain valid:
- `#d97706` / amber for approval-required and caution states.
- `#059669` / emerald for successful promotion-ready or completed states.

## State Semantics

- `Needs review`: amber badge, row remains in default queue ordering.
- `Low quality`: rose or amber emphasis depending on severity; show score value and failing rubric/rule immediately.
- `Policy triggered`: rose emphasis; put the rule name or reason code on the first metadata line.
- `Promotion candidate`: emerald secondary badge plus neutral row surface until selected.
- `Dismissed`: not shown in default queue; if visible through filters later, render as subdued stone treatment.
- `Approval required`: amber card or modal treatment only; never use blue for sealed-baseline approval moments.

Sort order default:
1. `policy triggered`
2. `low quality`
3. `promotion candidate`
4. oldest within same severity first if they are awaiting operator action

## Copywriting Contract

| Element | Copy |
|---------|------|
| Primary CTA | Review flagged traces |
| Empty state heading | No traces need review |
| Empty state body | Scoria has not produced any low-quality, policy-triggered, or promotion-ready traces for this filter set yet. Check back after scoring jobs complete or widen the filters. |
| Error state | Scoria could not load the review queue. Retry the query, or open the linked workflow directly if the scoring evidence already exists. |
| Destructive confirmation | Dismiss candidate: Remove this trace from the active review queue? Scoring evidence and workflow history will stay intact, but this candidate will no longer appear in the default review list. |

Additional action labels:
- Open workflow
- Promote candidate
- Request baseline approval
- Retry queue load
- View runtime context

---

## Promotion and Approval Contract

- Open-dataset promotions use blue primary action styling and must say `Promote candidate`.
- Sealed-baseline promotions use amber primary action styling and must say `Request baseline approval`.
- Show a frozen-evidence summary above both actions, matching the Phase 39 promotion modal pattern.
- Never present sealed-baseline mutation as immediate success; success copy must say that an approval request was recorded.
- After successful draft promotion, keep the review item visible long enough to show success feedback and link to the promoted dataset target.
