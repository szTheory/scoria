# Phase 54.1: Wire ReqLLM/Jido adapters at boot + reconcile CHANGELOG - Context

**Gathered:** 2026-07-18
**Status:** Ready for planning

<domain>
## Phase Boundary

Close the runtime integration gap where `Scoria.Observe.Adapters.ReqLLM.attach/0` and
`Scoria.Observe.Adapters.Jido.attach/0` register span-emitting telemetry handlers but have
**no `lib/` caller** — only tests call them. In a real host app those LLM/TOOL spans fire
into a void while the CHANGELOG (`## [Unreleased]`, the `0.1.4` cut) claims "zero host wiring."

This phase boot-attaches both adapters through the existing `observe_children/0` seam so a
real `req_llm` chat call (and a `jido` action, if the host runs Jido) persists a span with no
host hand-wiring, and reconciles code / CHANGELOG / `runtime_span_test.exs` moduledoc so they
no longer disagree.

**In scope:** the boot-attach wiring, the SC#2 boot-path test, the `runtime_span_test.exs`
moduledoc rewrite, the scoped CHANGELOG amendment, and one new adopter guide + one
troubleshooting entry.

**Out of scope:** any change to the adapters' `attach/0`/`handle_event/4` internals (they are
correct per Phase 51); making `jido` a dependency; a per-adapter config switch; Phase 54's
docs-accuracy/conformance work (separate phase).
</domain>

<decisions>
## Implementation Decisions

These decisions were reached via parallel research (Elixir/Phoenix telemetry idioms, adopter
DX, ecosystem prior art) plus an adversarial red-team pass that verified every claim against
the actual files. They are LOCKED and internally coherent — the planner should not re-open them.

- **D-01 — Attach design: AUTO boot-attach both adapters (resolve SC#1 to the boot-attach fork, NOT the opt-in fork)**
Extend `Scoria.Application.observe_children/0` (`lib/scoria/application.ex:42-50`) to also call
two new private helpers, `safe_attach_observe_req_llm/0` and `safe_attach_observe_jido/0`, each
mirroring `safe_attach_observe_mcp/0` (`application.ex:68-73`) **verbatim** in shape:
- gated by the same `Application.get_env(:scoria, Scoria.Observe, [])[:enabled] != false` switch (D-04);
- match-and-ignore `{:error, :already_exists}` (never let attach raise/halt `start/2` — T-53-08);
- distinct handler ids (already set: `"scoria-observe-reqllm"`, `"scoria-observe-jido"`).

**Why boot-attach, not host-opt-in:** `req_llm` is a hard dep (`mix.exs:98`, `~> 1.13`), the
events (`[:req_llm, :request, :stop]` / `[:jido, :action, :stop]`) are fixed known names, and
there is nothing app-specific to discover. The one reason the OpenTelemetry suite forces an
opt-in `setup/1` — it must be told the host's app-specific telemetry prefix — does not apply
here. The internal bus (`Telemetry.attach/0`) and MCP are already boot-attached under the same
gate; leaving the LLM span (the single most important span kind for an *AI*-observability lib)
opt-in is the anomaly, and it is exactly what keeps the CHANGELOG claim false. Prior art:
Sentry Elixir auto-attaches integration handlers in its own `start/2`, config-gated.

- **D-02 — Jido: UNCONDITIONAL attach (mirror MCP verbatim); do NOT presence-gate; do NOT make it an optional dep**
`jido` is absent from `mix.exs`/`mix.lock`. Attach the Jido handler unconditionally, exactly
like MCP — **no `Code.ensure_loaded?(Jido)` guard.**

**Why (red-team T1, decisive):** `lib/scoria/observe/adapters/jido.ex` references **zero**
`Jido.*` modules (only `Scoria.Observe.Semconv`/`SpanKind`); it only pattern-matches the raw
atom-list event and reads `metadata`. A `Code.ensure_loaded?(Jido)` gate therefore guards
nothing real and is actively misleading (it implies the handler needs Jido loaded, which is
false). "Presence" is self-enforcing at the telemetry layer: with no producer, the handler is
one idle ETS row that never runs — provably harmless, no boot/perf hazard. MCP sets the binding
precedent (unconditional, match-and-ignore). Keep `jido` **telemetry-coupled, not `optional: true`**:
an optional dep would add a version-range conflict surface and an implicit support commitment
for a package Scoria never calls — pure telemetry decoupling is strictly looser coupling
(this is how `opentelemetry_ecto`/`_phoenix` and PromEx plugins integrate). This also honors the
project's own doctrine (`prompts/phoenix-ai-lib-deep-research.md` L65: optional integrations are
not hard dependencies; L1133: "composable via adapters, not NIH").

- **D-03 — CHANGELOG reconciliation: amend the ADAPTER trace-join claim only; keep the (true) default-pipeline persistence claim**
Amend the `## [Unreleased]` "Added" block (~`CHANGELOG.md:183-191`) to distinguish **persist**
from **join**: adapter spans *persist* to Postgres with zero host wiring, but only *join the run
trace* as a child span when the host forwards `trace_id`/`parent_id`/`tenant_id` into the
telemetry metadata (in-workflow, `Scoria.Workflows.Runtime.execute_step/2` threads these
automatically; a raw out-of-workflow call persists as a standalone single-span trace until the
host forwards them). Keep the value prop in bold ("persist … with zero host wiring") + one calm
caveat sentence + a link to the D-05 guide. Note that `jido` is not a Scoria dependency — that
adapter stays dormant unless the host runs Jido.

**Scope guard (red-team T5):** amend ONLY the adapter trace-join sentence. Do **not** touch the
separate, still-accurate default-span-pipeline "zero wiring" persistence claim — the same claim
is mirrored in `test/scoria/application_test.exs:6-7` (about hand-synthesized `span:stop`), and a
blanket edit would make the CHANGELOG contradict that still-true moduledoc. Tone: honest, not
scary — no ALL-CAPS "ORPHAN" in adopter-facing copy (that phrasing belongs in the moduledocs).

- **D-04 — Single disable switch**
Route both new attaches through the existing `config :scoria, Scoria.Observe, enabled: false`
gate in `observe_children/0`. Do **not** add a per-adapter config knob (scope creep).

- **D-05 — Docs: add ONE capability guide + edit the EXISTING troubleshooting page**
Add `guides/capabilities/llm-and-tool-adapters.md` and register it in **all three** `mix.exs`
lists — `docs_extras` (~L157-177), `docs_extra_groups` "Capabilities" group (~L191-196), and the
Hex `package` `files:` list (~L366-380) — or the docs-source inventory tests fail.
`guides/troubleshooting.md` **already exists and is already registered** (L172/198/376): add an
orphan-span entry ("Why is my LLM/tool call a standalone single-span trace?") as an **edit** — no
registration change.

Guide outline (keep minimal, one page): (1) what auto-attaches (ReqLLM + Jido → LLM/TOOL spans,
config-gated, `already_exists`-tolerant, handler ids); (2) persist-vs-join distinction;
(3) how to forward metadata — the keys + one `req_llm` snippet and one `jido` snippet, pointing
at the adapter **moduledocs as the SSOT** to resist doc rot; (4) ownership-boundary tie-in
(trace lineage/identity are host-owned nouns Scoria never infers — same class as tenant/actor);
(5) the jido asymmetry (req_llm is a dep, jido is not — handler dormant unless host brings Jido).

- **D-06 — SC#3 reconciliation: rewrite the `runtime_span_test.exs` moduledoc; existing tests need NO functional change**
Observe **is enabled in the test env** (red-team T2: no `config :scoria, Scoria.Observe, enabled:`
in `config/test.exs` or `config/config.exs` → gate defaults ON), so both boot-attaches fire in
`:test`. All four affected test files already `:telemetry.detach(...)` before their per-test
`attach/0`, so they are **already boot-attach tolerant** — no functional edits:
- `test/scoria/observe/adapters/req_llm_test.exs` (detach at L6) — no change
- `test/scoria/workflows/runtime_span_test.exs` (detach L160 before `:ok = ...attach()` L161) — no functional change, but **REQUIRED moduledoc rewrite** at L13-15 (currently states ReqLLM "is NOT boot-attached" — now false; rewrite to say it is boot-attached like MCP and the per-test detach/re-attach only keeps its lifecycle independent of the scoped telemetry handler)
- `test/scoria_web/live/orchestrator_live_integration_test.exs` (detach L174, on_exit L187) — no change (name it in the plan's blast radius)
- `test/scoria/observe/adapters/jido_test.exs` (detach L6) — no change

The MCP precedent to follow: `mcp_test.exs` never re-attaches/detaches the boot handler and
Test 9 (L221-224) asserts a 2nd `attach()` returns `{:error, :already_exists}`, proving boot
registered it.

- **D-07 — SC#2 boot-path test (the only additive test work)**
Add a new test proving an upstream `[:req_llm, :request, :stop]` event with **no manual `attach/0`
in the test body** results in a persisted span. Place it as an `application_test.exs`-style test
(global supervised `Buffer` + shared-sandbox mode + `Buffer.flush_now()`), **NOT** as a `describe`
in `req_llm_test.exs` (that file's `setup` detaches `"scoria-observe-reqllm"` at L6, which would
strip the very boot handler the test must prove). Assert boot registration first
(`assert [_] = :telemetry.list_handlers([:req_llm, :request, :stop])`, or the Test-9
`{:error, :already_exists} = ReqLLM.attach()` idiom), then `:telemetry.execute/3` the event,
`Buffer.flush_now()`, and `Repo.get_by!/2` the span. Self-heal the reqllm attach in `setup`
(tolerate `{:error, :already_exists}`) as `application_test.exs` does for telemetry (L34-37),
because `runtime_span_test.exs`'s on_exit (L165) can strip the boot handler earlier in the suite.

**Jido's SC#2-equivalent** can only assert handler registration + drive a **hand-synthesized**
`[:jido, :action, :stop]` event — jido is not a dep, so there is no real in-suite upstream
producer. State this explicitly so code/CHANGELOG/tests agree on what "proven" means for Jido.

<code_context>
## Existing Code Insights

### Reusable Assets
- `safe_attach_observe_mcp/0` (`application.ex:68-73`): the byte-for-byte template for the two new
  `safe_attach_observe_req_llm/0` / `safe_attach_observe_jido/0` helpers.
- Adapter `attach/0` functions already exist and are correct — this phase only supplies the missing
  `lib/` caller. Handler ids (`"scoria-observe-reqllm"`, `"scoria-observe-jido"`) are already
  distinct, so no attach/detach collision with MCP/telemetry.
- `test/scoria/application_test.exs` "default pipeline" test (L68-93) + self-healing telemetry
  attach (L34-37): the pattern for the D-07 SC#2 test.

### Established Patterns
- Config-gated, `Mix.env`-independent boot-attach: `observe_children/0` reads
  `Application.get_env(:scoria, Scoria.Observe, [])[:enabled]`, defaulting ON — the same gate must
  cover the new attaches (D-04).
- T-53-08 invariant: attach helpers must match-and-ignore `{:error, :already_exists}` and never
  raise in `start/2` (a boot crash takes the host app down).
- Tests self-heal by detaching the handler id before re-attaching — already true for all four
  affected test files, which is why boot-attach requires no functional test edits (D-06).

### Integration Points
- `observe_children/0` is the single wiring point; Buffer is returned as a supervised child from
  the same function. Attach happens during child-spec construction (before Buffer starts), which is
  already the case for Telemetry+MCP and is safe (no producer fires during `start/2`; a cast to the
  not-yet-started Buffer is a silent no-op, never a crash — red-team T3).

</code_context>

<specifics>
## Specific Ideas

- Mirror `safe_attach_observe_mcp/0` **verbatim** — the strongest coherence signal is that the
  three source adapters (MCP first-party, ReqLLM hard-dep, Jido telemetry-only) end up treated
  identically at the boot seam, differing only in the docs' explanation of the dependency status.
- Steal OpenTelemetry's "context propagation" vocabulary and its blunt "spans won't link without
  it" framing for the guide/CHANGELOG — honest but not scary.
- Frame metadata forwarding via the existing ownership-boundary doctrine: "your app owns trace
  lineage; Scoria records what you forward" — a direct parallel to the existing "Run records and
  traces" row.
