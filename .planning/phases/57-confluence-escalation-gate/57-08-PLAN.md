<objective>
Make an escalation survive the real world: resumable after a sibling step completes, un-retryable while pending, un-strandable when the run halts, and crash-free when two writers hit the run row at once.

Purpose: RESEARCH.md names this the single highest-risk untested interaction class in the phase. Three independent predicates gate resumability, and widening only one of them passes every single-step test while stranding real multi-step runs in production. `retry_failed_step/2` has no status check and targets the run's current step — which after an escalation IS the escalated step — so calling it flips the run to retrying, zeroes the step's result envelope, leaves the approval pending forever and mints a second approval on re-execution. And `mark_waiting_for_approval/3` lacks the stale-entry rescue `halt_run/3` has, while the step executor rescues only its own failure signal, so a sibling completing mid-escalation crashes the unlinked dispatch task and strands the step.

Output: the three-axis resume widening, a retry guard, the mandatory call-site rescue, the halt precedence check, and the halt-with-pending-approval invariant.
</objective>

Widen resumability on all THREE axes for confluence-kind approvals only, leaving every other blocker kind byte-identical.

Axis one — the OUTER predicate. `resume_run/1`'s case head currently matches only a `waiting_for_approval` run status, and a sibling step's `complete_step/3` rewrites the run status back to `running`, so resume falls through to the not-resumable error REGARDLESS of any finder change. That step-status conjunct is what keeps the widening safe: a running run with no paused step is still not resumable.

Axis two — drop the current-step predicate for the confluence blocker kind in `current_approved_approval/1`. Two concurrent escalations in one run each overwrite the run's current step pointer, so requiring a match strands all but the last.

Axis three — drop the latest-checkpoint predicate for the confluence blocker kind in the same function, for the same reason: each escalation overwrites the latest checkpoint pointer.

Keep the approved-status requirement on all paths. Anything less than all three axes strands runs in production while passing every single-step test — widening only the finder is necessary but not sufficient, because the outer predicate breaks first.

Add a comment above the widened predicates naming the three axes and citing D-26, so a later reader tightening one of them sees why it is there.

Write the tests first in `test/scoria/workflows_test.exs`, tagged so `--only confluence` selects them, covering every behavior above. The two-concurrent-escalations case must assert BOTH are resumable, in each approval order. Add a regression case asserting a non-confluence approval still requires all three original predicates.
