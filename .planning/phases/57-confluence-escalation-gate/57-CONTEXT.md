<domain>
## Phase Boundary

A tainted execution path that touches private data, untrusted content, and an exfil-capable action at once is **classified**, and — when the evidence is adopter-declared — **paused for human approval before the exfil action executes**, audited and replayable, with a graded default that can never brick an adopter who declared nothing.

**In scope:** GATE-01 (confluence evaluator), GATE-02 (escalation/pause), GATE-03 (audit + replay), GATE-04 (graded enforcement default), plus the mandatory Phase 55 mint-site repair (D-03) without which all four are inert.

**Split to Phase 57.1 (see `<deferred>`):** approval expiry, the adopter guide, and the standalone copy module. **Out of scope:** the Govern read-only surface, safety hooks, and `SECURITY-BOUNDARY.md` (all Phase 58); any shipped injection/moderation detector (permanently host-owned per scope doctrine); a policy builder or per-user tool allowlist.

### ⚠️ A — The prerequisite: Phase 55's untrusted-content leg is currently unusable

- **D-01 (revised) — `MCP.Executor.scan_tool_output/2` clamps EVERY tool output to `"untrusted"` regardless of what the scanner returns, and this must be fixed in Phase 57 or the entire gate is inert.** Verified directly by the orchestrator: `scan_tool_output/2` calls `Trust.scan(value, Map.put(context, :content_scanner, scanner))` (`executor.ex:526-529`) and **never passes `:incoming_tier`**; `Scan.scan/2` defaults it to `Trust.default_tier()` = `"untrusted"` (`scan.ex:67`, `trust.ex:36`); `most_restrictive/2` is min-wins over `%{"untrusted" => 0, "trusted" => 1}` (`scan.ex:128-130`). So `most_restrictive("untrusted", anything) == "untrusted"`, always. A correctly-installed scanner returning `%Verdict{tier: "trusted"}` on clean content still resolves `"untrusted"`.
  `Knowledge.retrieve/2` gets this right — `aggregate_incoming_tier/1` seeds `"trusted"` and threads `incoming_tier` (`knowledge.ex:431-434, 444-448`). The executor is the outlier.
  **Fix (both parts required):** (a) pass `incoming_tier: "trusted"` at the tool-output mint site — a freshly minted tool output has no *prior* taint, so `"untrusted"` is the wrong identity element for a mint (it is the right one for a *read*, which is why `Trust.tier/1`'s reader default is correct and must not change); (b) add a pre-clamp `scanner_tier` field to `%Scoria.Trust.Verdict{}` (`verdict.ex:26` is currently `[:tier, :score, :reason_code, :scanner]`) so the scanner's own opinion survives the monotonic law and the gate can grade on evidence quality. The monotonic law (55 D-19) is preserved untouched — `tier` remains the clamped value; `scanner_tier` is evidence, never authority.
  — **Reversibility:** reversible (both are additive); **but the phase is inert without it.**
- **D-02 (revised) — The untrusted-content leg is TOOL-DECLARATION-SOURCED plus REAL-SCANNER-observed only. RAG-retrieved content does not light it this milestone, and that must be stated, not implied.** Nothing in `lib/scoria/workflows/` calls `Knowledge.retrieve/2` — the host calls it out of band — and `Knowledge.create_retrieval_run/1` persists no `workflow_run_id`/`step_id` (`knowledge.ex:236-250`; `knowledge/retrieval_run.ex` has neither field). There is therefore **no path from a retrieved chunk's trust tier into a run-scoped accumulator**, and one cannot be built in this phase.
  **Consequence to record honestly: `ROADMAP.md` §Phase 55's goal — "supplying the missing untrusted-content leg that the Phase 57 confluence gate will read" — is currently false.** Phase 57 does not make it false; it makes it visible. Either thread `workflow_run_id` through retrieval in a later phase, or let `SECURITY-BOUNDARY.md` (Phase 58) state the residual.

### B — Vocabulary, module shape, and the trace contract (GATE-01)

- **D-03 — `Scoria.Confluence`** — root-namespace, dependency-free leaf. **Not** `Scoria.MCP.Confluence` (the legs are not tool-scoped) and **not** `Scoria.Gate.Confluence`. It aliases nothing Scoria-side — not `Semconv`, not `Workflows`, not `Trust`, not `MCP.Executor`. Both operands (`%Trust.Verdict{}`/tier and `%MCP.Classification{}`) are leaf structs passed IN as arguments, so **no protocol is needed** (unlike 55 D-23's `Trust.Tiered`, which existed only for foreign-struct dispatch). The caller (`MCP.Executor`) already holds every edge, so the graph is a DAG by construction. Config key is the module name, per the shipped `__MODULE__` idiom. — **Reversibility:** one-way (published module name; Phase 58 renders it).
- **D-04 — `Confluence.classify/1 :: {combination, %Confluence.Evidence{}}`, a PURE classifier that never emits**, mirroring `ReplayDisposition.resolve/5`'s `cond` → `{atom, evidence}` shape, which GATE-01 explicitly names as the model. `%Evidence{}` is `@derive Jason.Encoder` with a closed field set of enums/ids/booleans/timestamps and carries the same module-level prohibition on a `reason`/`note`/`score` field as `classification.ex:38-43`.
- **D-05 — Closed 8-value STRING combination enum** (total over the 3-bit leg vector, so `classify/1` is total and property-testable over all 8 inputs): `none`, `private_data`, `untrusted_content`, `exfil_capable`, `private_data_and_untrusted_content`, `private_data_to_egress`, `untrusted_content_to_egress`, `exfiltration_path`. Strings not atoms — these land on a span, matching `Trust.tiers/0` and `Classification.action_classes/0`. `normalize_combination/1` fails closed to `"none"` + `Logger.warning` + telemetry (`Trust.fallback/1` shape). — **Reversibility:** one-way.
- **D-06 — The `cond` ladder DELIBERATELY DIVERGES from `ReplayDisposition` at the terminal clause.** `ReplayDisposition`'s catch-all is `true -> {:execute_live, ...}` — fail-**open** (`replay_disposition.ex:58-59`), the exact hazard 56 D-02 names. Phase 57's terminal clause is `{:unevaluable, "confluence_resolver_fallthrough"}` + telemetry: unreachable by construction, and if reached it is a bug that must be visible **without changing execution**. It must not be `:escalate` either — escalating on a resolver bug is the bricking cascade. Comment this divergence in the moduledoc or a future reader will "fix" it back.
- **D-07 — No "lethal trifecta" coinage in any API name.** `ai_doc_contract.ex:87-88` machine-forbids the literal strings; brandbook bans alarm-coded language ("make safety & governance normal, not an alarm"); and "trifecta" hard-pins three legs into a one-way Hex contract when a fourth (authority expansion) already exists as a live concept. Coinage stays as moduledoc prose attribution only — the precedent at `classification.ex:3`.
- **D-08 (revised) — The confluence attribute group is emitted BY THE GATE on all three dispositions, NOT by riding the tool-completed telemetry event.** The `scoria.confluence.*` keys are listed below. The draft pinned them to `executor.ex:342-346`; the red team proved that event fires **only** inside `execute_live`'s `{:ok, {:completed, ...}}` branch, and D-14 places the gate *before* `execute_live/4`. So on `escalate` and `block` the event never fires and **no confluence attribute would ever reach a span** — GATE-04's "inspectable" false for exactly the cases that matter, and the registry key `scoria.confluence.approval_ref` ("escalate only") provably dead. This is the prior-phase "decorative hook" defect class reproduced. The gate emits its own event on every disposition and the span adapter carries it.

  Fixed no-passthrough projector `Semconv.confluence_attributes/1`; `@confluence_keys` **hand-written** (the shipped `@trust_keys` pattern at `semconv.ex:283` — calling into `Scoria.Confluence` would create the edge D-03 forbids). ### C — The evaluation model (GATE-01)

- **D-11 — Scope: per-run accumulation of the two EXPOSURE legs; the EXFIL leg is per-call and never accumulated.** `reads_private_data` / `sees_untrusted_content` describe what the agent has been *exposed to* (monotone, run-scoped); `can_exfiltrate` describes what *this call can do*. That split is exactly what makes GATE-02's "pause before the exfil action" pause the right call. Accumulating all three would pause a later harmless read once any exfil-capable tool had run. A single tool declaring all three still escalates on itself, because its own legs fold in before evaluation — per-call is a strict subset, not a second mode. — **Reversibility:** one-way (this is the published differentiator's semantics).
- **D-12 — Legs are monotone within a run; the only reset is a new run.** No untaint/laundering primitive — Perl taint's `untaint` is the canonical footgun, and it is why the Ruby `$SAFE` post-mortem reads the way it does. Approval clears the GATE (keyed by the idempotency key), never the LEGS.
- **D-13 (revised) — Leg sourcing. "Observed taint is never sufficient alone" is DELETED — it made Phase 55's entire deliverable dead code.** The draft said declared-primary, observed-additive-only; the red team showed that with D-26's grade axis this makes `default_tier` and `scanner_infra` unreachable as the weakest grade, i.e. one-third of the cascade model is dead and TAINT-01..04 contributes nothing. Corrected per-leg:

  | leg | source | grade contributed |
  |---|---|---|
  | private-data | `Classification.reads_private_data` — **declared only**; no observed signal exists or can be built (D-02) | `declared` / `unclassified` |
  | untrusted-content | declared `sees_untrusted_content`, **or** observed taint from a REAL scanner (`verdict.scanner != Scanner.NoOp`) graded on the post-D-01 `scanner_tier` | `declared`; `scanner_infra` when `reason_code ∈ [:scanner_error, :scanner_timeout, :scanner_malformed]`; `default_tier` when the tier is the shipped fail-closed default with no scanner |
  | exfil | `Classification.can_exfiltrate` **alone** | `declared` / `unclassified` |

  **`can_exfiltrate AND action_class != "read"` is REJECTED:** `Classification.declared/1` defaults `action_class` to `"read"` (`classification.ex:141`), so the AND would silently exempt every adopter who declares `can_exfiltrate: true` and nothing else — inverting a declaration into an exemption. Semantically it is also wrong: a pure read that ships bytes to a third party *is* exfiltration. `action_class` rides the evidence as a telemetry tag only.
- **D-14 — Ordering in `execute/4`: rail → classification → replay_gate → CONFLUENCE → `execute_live`.** All three researchers who considered ordering converged independently, and the red team verified it end to end. After the rail (56.1 D-22.3 — a halt beats a pause, and escalation loops must still count against `max_tool_calls`); after classification (it IS the leg source); after `replay_gate/3` (a `:historical_stub` never executes the exfil action, and re-asking a human on replay makes replay unusable — Temporal's determinism law); before `execute_live/4` (`executor.ex:305`) and therefore before `maybe_capture_sensitive_mcp_access/3` and `reserve_budget/3` — an escalated call must reserve no budget and write no `mcp.access.granted` row for an action that did not happen.
- **D-15 (revised) — The accumulator is a new `confluence_legs` jsonb column on `ai_workflow_runs`, and it keeps the STRONGEST witness per leg, not the first.** Three red-team corrections to the draft, each of which alone would have silently disabled the gate:
  1. **Strongest-wins, not first-wins.** The draft's `fragment("? || ?", new, existing)` preserved the *first* witness; composed with D-26's weakest-evidence grading, a leg first lit by a `default_tier` observation is pinned to grade `default_tier → allow` **for the rest of the run** no matter how strong the later evidence — ordering luck, or an attacker choosing which tool runs first, silences the gate permanently. jsonb `||` cannot express strongest-wins; rank sources numerically (`declared` > observed > `default_tier` > `unclassified`) and use a per-leg `GREATEST`-style expression, or accept a read-modify-write under the run row's existing lock. **Do not paper over this with `||`; no shape-based test catches it.**
  2. **Write ONLY lit legs — never a `false`, never an absent leg.** Writing the full three-leg map each call freezes the first call's `false` values permanently under any merge order.
  3. **Column default `%{}`, `null: false`.** In Postgres `'{"a":1}'::jsonb || NULL` is **NULL**. A nullable column with no default makes the accumulator permanently dead for every pre-migration row, silently. Mirror the 56.1 rail migration's `null: false, default:` discipline.

  Also load-bearing: `confluence_legs` **must not** appear in `Run.changeset/2`'s `cast/3` list (`run.ex:66-104`; the LOAD-BEARING comment at `:106-118` states the rule — counter writers and changeset writers must be disjoint or `optimistic_lock` raises `StaleEntryError`). Ship the structural test asserting its absence. — **Reversibility:** one-way (durable column + a jsonb shape Phase 58 re-derives from).
- **D-16 (revised) — A failed accumulator write must NOT be silently swallowed.** `persist_taint_to_step/3` and `persist_classification_to_step/3` both `rescue _ -> :ok` (`executor.ex:628-630`, `:678-680`). Copying that discipline here means a failed `confluence_legs` merge produces no leg, no escalation, and no signal — a **silent fail-open on the security control** under strict mode. The observe-layer "never break host business logic" rule still applies (do not crash the call), but the rescue must emit a fallback telemetry event.
- **D-17 (revised) — Fold the leg merge and the accumulator read into ONE statement.** The draft's accumulate-then-read sequence is a TOCTOU between two concurrent tool calls in the same run. Use `Repo.update_all(query, [...], returning: [:confluence_legs])`. This also holds the added serialization to one extra row lock rather than two — note the gate adds a **second** exclusive lock per tool call on top of the rail counter (`executor.ex:91` → `rails.ex:120`), doubling the window 56.1 D-09 documented as an accepted limitation. Accept and document; do not pretend it is free.

### D — The pause mechanism (GATE-02)

- **D-18 (revised) — GATE-02's literal text cannot be honored, but the DRAFT'S REASON WAS WRONG.** The draft claimed the executor "structurally cannot own the pause." False — the executor already calls `Workflows.halt_run/3` directly on the rail path (`executor.ex:215`) and writes terminal run state today. What it cannot do is **stop the handler from continuing after the decision**. Proposed replacement wording for GATE-02 and ROADMAP SC#2:
  > When private-data + untrusted-content + exfil co-occur in one tainted execution path, the confluence gate decides and refuses at `Scoria.MCP.Executor`, before the tool's execution Task is started, and the run's step is transitioned to `waiting_for_approval` via `Scoria.Workflows.mark_waiting_for_approval/3`, so the escalation is resumable by `Workflows.resume_run/1`. Tool calls that reach the executor with no runtime step attribution cannot be paused; the gap is telemetried and documented.
- **D-19 — The pause transition reuses the EXISTING `Workflows.mark_waiting_for_approval/3`. No new lifecycle function.** `escalate_run/3` (a `halt_run/3` mirror) is **rejected**: `halt_run` works only because six clamps make `"halted"` un-overwritable, which is permissible *only* because a halt is terminal. An escalation must be RELEASED, so the equivalent clamps would need a principled release point that does not exist, and would additionally have to suppress checkpoint/event inserts (which `halt_run`'s clamps never do) because a post-escalation checkpoint alone breaks `current_approved_approval/1`. That is re-implementing terminality for a non-terminal state.
- **D-20 (revised) — The executor→runtime signal is `exit({:shutdown, {:scoria_confluence_escalation, attrs}})`, NOT a raised exception.** The draft chose `raise` on the rationale that an exit "would emit a SASL crash report on a deliberate control-flow path." The red team **measured** this and it is false: `exit({:shutdown, term})` from a `Task.Supervisor.async_nolink` task yields `{:exit, {:shutdown, term}}` at `Task.yield` with **no log line** (only non-`{:shutdown, _}` reasons log). It also measured that `try/rescue _ -> …` **does not catch an exit**. So the draft chose the *more* swallowable mechanism — a raise is defeated by `rescue _ ->`, the single most common defensive pattern in adopter code, whereas an exit is defeated only by `catch :exit`, which is rare. One new clause in `execute_handler/6` above the existing `{:exit, reason}` clause (`runtime.ex:770`):
  ```elixir
  {:exit, {:shutdown, {:scoria_confluence_escalation, attrs}}} ->
    {:ok, {:waiting_for_approval, attrs, elapsed_ms(started_at)}}
  ```
  No task-lambda `try/rescue` is needed, which also resolves the draft's internal contradiction (it simultaneously specified a lambda rescue *and* a new `execute_handler/6` clause — mutually exclusive designs).
- **D-21 (revised) — The containment proof is a process-dictionary marker resolved through `$callers`, because there is genuinely NO channel from `Runtime` into the executor's `context`.** The red team tested the draft's own proposed alternative and refuted it: `decorate_run_with_trace_context/4` (`runtime.ex:906-918`) writes `run_id`/`step_id` into `run.metadata["runtime"]` on an ephemeral run copy, and **the host handler must hand-forward them** (the comment at `runtime.ex:894-905` says so verbatim). An explicit context key is therefore impossible to guarantee. But a bare `Process.get/1` is too weak: `Task.async` and `Task.async_stream` **do** propagate `:"$callers"` (the pdict itself never is). So the proof is: the marker on `self()`, **or** on any pid in `Process.get(:"$callers", [])`. That covers both idiomatic nesting patterns for parallel tool calls. Raw `spawn` is the honest residual — telemetried, mirroring 56.1's rail-skipped precedent, never papered over.
- **D-22 (revised) — `unattributed:` defaults to `:allow`, NOT `:deny`.** The draft defaulted strict-mode unattributed calls to deny. The red team found that **Scoria's own reference handler does not forward the keys the gate depends on** — `test/scoria/workflows/runtime_span_test.exs:82-91` passes `workflow_run_id:` (a different key from the `:run_id` the executor reads at `executor.ex:78`) and **no `step_id` at all**. So the canonical copy-paste an adopter has is already unattributed, and `:deny` would refuse every tool call from a handler written against Scoria's own example. That is this phase's fail-closed→brick cascade. Deny-by-default on a seam Scoria itself admits it cannot attribute is a brick, not a guard. **Three required follow-ons:** fix the in-repo example handler to forward `run_id`/`step_id`; alias `:workflow_run_id → :run_id` in `canonical_context/1` (`executor.ex:1013-1029`); and gate the strict-mode ladder rung on a measured skipped-rate of zero. Telemetry mirrors `[:scoria, :run, :rail, :skipped]` exactly. **Never create an `Approval` row on this path** — a pending approval nobody can consume is decorative.
- **D-23 — Run status written is `"waiting_for_approval"`; `"paused"` is rejected** (`resume_run/1` has no clause for it — `workflows.ex:985-1041` — and adopting it buys nothing). Confluence escalations are distinguished by `Approval.blocker_kind: "confluence"`, an existing, purpose-built, indexable column already used this way by `Connectors.Auth` (`auth.ex:325-328`). `ScoriaWeb.UI.tone/1` needs **no** edit — `"waiting_for_approval"` already maps to `:warn` (`lib/scoria_web/ui.ex:35`). *(Note: prior context cited `lib/scoria/ui.ex`; that file does not exist.)*
- **D-24 — `Run.halted?/1` is checked before escalating; halted ⇒ deny, never an approval row** (56.1 D-22.3 verbatim). Necessary even given G1, because a sibling rail can trip after `claim_step/1` passed.
- **D-25 (revised) — The escalation is a STEP-level pause, not a run-level one, and this must be scoped in writing or fixed in `complete_step/3`.** `list_runnable_steps/0` (`workflows.ex:99-105`) requires `r.status in ["running","retrying"]`, so an escalation does freeze sibling dispatch — **until an already-in-flight sibling completes and flips the run back to `"running"`**. `complete_step/3` computes `run_status` and writes it unconditionally (`workflows.ex:305-350`); its only clamp is `Run.halted?`, not `waiting_for_approval`. Every remaining queued sibling then becomes dispatchable again and the rest of the run proceeds around the pause. Either add a `waiting_for_approval` clamp to that computation (a real `workflows.ex` change) or scope GATE-02's wording to the escalating step. **Decide explicitly at planning; do not ship the ambiguity.**
- **D-26 (revised) — Re-escalation is prevented by an atomic approval CONSUME, and `resume_run/1`'s finder must be widened on THREE axes, not one.** On resume, `resume_run/1` re-queues the step (`workflows.ex:994`) and the whole handler re-executes, reaching the identical tool call — without a consumed marker this escalates forever (LangGraph's documented `interrupt()` footgun). Two parts:
  - **Consume CAS:** new columns `consumed_at` + `consumed_by_step_id` on `ai_approvals`; the gate's first action is a single-statement `UPDATE … WHERE workflow_run_id=$run AND blocker_kind='confluence' AND status='approved' AND consumed_at IS NULL AND args_fingerprint=$fp … RETURNING id`, mirroring `Rails.admit_tool_call/2`. `{1,[id]}` ⇒ pass through; `{0,_}` ⇒ evaluate; a `rejected` match ⇒ deny with `confluence_rejected`, never re-escalate. A **`nil` `args_fingerprint` must fail closed** (treat as no match ⇒ escalate) — `build_replay_seam/2` reads it with no default. Repeat D-15's disjointness rule with opposite polarity: `consumed_at`/`consumed_by_step_id` go in the schema but **never** in `Approval.changeset/2`'s `cast/3` (`approval.ex:100` has `optimistic_lock`, and `approve/3` passes caller attrs straight through at `workflows.ex:1064-1067` — a caller-supplied `consumed_at: nil` could otherwise **un-consume** an approval).
  - **Finder widening (revised):** the draft widened only `current_approved_approval/1`, and the red team proved that is **necessary but not sufficient** — the outer predicate breaks first. `resume_run/1`'s case head matches `{"waiting_for_approval", _, %Approval{status: "approved"}}` (`workflows.ex:988-989`), and a sibling `complete_step/3` rewrites `run.status` to `"running"`, so resume falls to `{:error, :not_resumable}` **regardless of any finder change**. Widen all three: accept `run.status in ["waiting_for_approval","running"]` for a `blocker_kind: "confluence"` approval whose step is still step-status `waiting_for_approval`; drop the `current_step_id` predicate for that blocker kind; drop the `checkpoint_id == latest` predicate for that blocker kind (`workflows.ex:1191-1201`). Anything less strands runs in production while passing every single-step test.
- **D-27 (revised) — `Workflows.Resume.retry_failed_step/2` strands pending confluence approvals and DESTROYS classification evidence.** `resume.ex:16-27` has no status check and targets `run.current_step_id` — which after an escalation *is* the escalated step (`workflows.ex:394`). Calling it flips the run to `"retrying"`, **zeroes the step's `result_envelope`** (`workflows.ex:945`), leaves the approval `pending` forever, and on re-execution mints a *second* approval. Add a status guard to `retry_step/1` (refuse when the step is `waiting_for_approval` or a pending confluence approval exists), or document and test it as an accepted stranding path. Related: 56.1 D-22.5 already forbids routing escalations through `"retrying"`.
- **D-28 — Concurrency.** No new terminality guards (an escalation is *supposed* to be undone; clamping siblings would break 56.1 D-15's own regression test). But: `mark_waiting_for_approval/3` is **not** `StaleEntryError`-rescued (unlike `halt_run/3`), and `Runtime.execute_step/2` rescues only `StepFailureSignal` (`runtime.ex:310-312`) — so a sibling completing mid-escalation crashes the unlinked dispatch Task and strands the step in `"running"`. **The call-site rescue is mandatory, not optional**, normalizing fail-closed. Two concurrent escalations in one run each overwrite `run.current_step_id`/`latest_checkpoint_id`, so only the last is resumable — D-26's three-axis widening is what makes both resumable. Escalation attrs must be **atom-keyed** and always carry `tool_name` (`Approval.changeset/2` has `validate_required([:tool_name, :status])` and `mark_waiting_for_approval/3` uses `repo.insert!`; mixed atom/string keys raise in `cast/3`).

### E — Enforcement, grading, and the never-brick cascades (GATE-04)

- **D-29 — Disposition is graded by the WEAKEST evidence backing its lit legs.** Four grades, fixed order, first applicable wins (so exactly one grade is recorded and the decision is deterministically replayable): `unclassified` → `scanner_infra` → `default_tier` → `declared`. A boolean or a flat mode enum **cannot** express "block the deliberate declaration, not the missing one," and that distinction is the entire never-brick argument. `source` is `@enforce_keys` (`classification.ex:45`) and `reason_code` is a closed enum (`verdict.ex:35-41`) precisely so this branch is constructable — 56 D-06 and 55 D-22 wrote those fields for this.
- **D-30 — There are FOUR cascades, not two, and all four are absence-of-evidence cases.** 56 D-06's `unclassified_default` (all three legs true, `classification.ex:117-126`); 55 D-22's `scanner_error`/`scanner_timeout`; the previously-unnamed `default_tier` cascade (`Trust.@default_tier == "untrusted"` + shipped `Scanner.NoOp` ⇒ every RAG-touching run trips the untrusted leg with no scanner involved) — found independently by two blind researchers, which is the strongest signal in this synthesis; and **(revised)** `Trust.normalize_tier/1`'s junk-value fallback (`trust.ex:132-141`), where a malformed scanner tier resolves `"untrusted"` on a non-NoOp scanner with a non-infra reason code and would grade as `declared` — i.e. a *buggy* scanner graded as positive evidence. Hence the new `scanner_malformed` reason code (D-09), grading as `scanner_infra`.
- **D-31 (revised) — The shipped default ENFORCES for the `declared` grade. The draft's `enforcement: :observe` default is REVERSED.** The two red teams split on this and the brick lens won on four independent grounds:
  1. **"Ungated" is a defined term of art, and GATE-04 names its source.** In `release_gate.ex` the telemetry event is literally `[:scoria, :release_gate, :ungated]` (`:84`) and fires on exactly one branch — `handle_missing_verdict/1`, evidence *absent*. Positive evidence of danger (`check(%PromptTemplate{status: "draft"})`, `:20`) returns an error with no flag at all; the opt-in `require_eval_verdict` governs only whether *absence* becomes an error. Mapped onto Phase 57, every word of SC#4 keeps its meaning: ungated = the three weak grades (telemetry, never block); `declared` = positive evidence (escalates); "opting into strict mode makes the pause actually enforce" = strict extends enforcement to the ungated grades, exactly as `require_eval_verdict` does. **Under the draft's reading, 100% of confluence is "ungated" and the word does no work.**
  2. **The draft literally violated GATE-04.** GATE-04 says a *"fail-closed-but-inspectable default."* Hard-forcing every grade to `allow` is fail-**open** by definition.
  3. **The never-brick constraint is satisfied STRUCTURALLY, not by a switch.** v3.7 is unreleased (published Hex is `0.1.3`, `mix.exs:4`); Phases 55/56/56.1 all completed 2026-07-28 and ship together. The `classification/0` declaration surface therefore has **zero users in the world**, so `declared: :escalate` is a provable no-op at upgrade and can only become live once an adopter writes `can_exfiltrate: true` on a tool — which is literally a request to be gated.
  4. **The rollout evidence is one-sided.** Controls shipped "observe by default, flip later" do not get flipped: CSP `Report-Only` is a terminal state, not a stage; Istio `PERMISSIVE` meshes largely never reach `STRICT`; Gatekeeper's `dryrun` signal degrades by truncation exactly at the scale you would need it; and **Kubernetes explicitly reversed `failurePolicy`'s default from `Ignore` to `Fail` at v1 GA** for this reason. The controls that *do* achieve enforcement use scoped opt-in then enforce inside the scope — and `classification/0` is Scoria's scope label.

  **Hard precondition: do not ship this without D-01.** With the mint-site bug live, `declared: :escalate` means the first adopter who installs a scanner and declares two tools gets a 100% pause rate — the brick the draft feared, arriving by a different route.
  **This requires a wording amendment to ROADMAP SC#4 / GATE-04 to name the grades.** Flagged explicitly: there is no design that satisfies both sentences exactly as currently written, and the phase is already amending GATE-02 (D-18) for the same class of reason.
- **D-32 — The config surface.**
  ```elixir
  config :scoria, Scoria.Confluence,
    enforcement:   :enforce,   # :enforce (default) | :observe — :observe is the INCIDENT KILL SWITCH, not the shipped state
    declared:      :escalate,  # positive evidence enforces (ReleaseGate doctrine)
    unclassified:  :allow,     # 56 D-06 guard  — telemetry only, ALWAYS active
    scanner_infra: :allow,     # 55 D-22 guard  — telemetry only, ALWAYS active
    default_tier:  :allow,     # cascade #3     — telemetry only, ALWAYS active
    strict:        false,      # SC#4's opt-in: true ⇒ the three ungated grades escalate too
    unattributed:  :allow      # D-22 — deny-by-default here is a brick
  ```
  One greppable kill switch retained; both inherited cascade guards **always** active rather than hidden behind a mode. Dispositions are `allow | escalate | block` (`guardrail_decisions/0` verbatim); `warn` is rejected — Scoria has no caller-warning channel at the executor return and adding one changes the return shape (55 D-08's one-way part). Telemetry IS the warning. **Evaluation, persistence and telemetry are always on with no off switch**, verbatim the shipped rails contract — an off switch would disable the very evidence that tells an adopter whether to enable enforcement.
- **D-33 — Precedence: per-call `context[:confluence]` tighten-only, over app-env (which MAY loosen), over shipped defaults.** 56 D-04's tighten-only doctrine applies here but **not** the way `Runtime.Rails` handles it: `Rails.resolve/1` uses last-writer-wins because both operands are host source code, whereas `context` at `execute/4` is built per call and a host that spreads request params into it makes it request-adjacent. App-env may legitimately loosen — an operator who cannot turn a security control down during an incident turns it off permanently. **A per-run rung is rejected:** rails freeze at creation because they are an accrual budget; enforcement is a point-in-time decision with no accrual, and freezing would prevent killing a bad config on in-flight runs. Read live; snapshot the resolved grade + decision into the audit envelope so replay reads the recorded decision and never re-resolves config.
- **D-34 — `Confluence.validate_app_env/0` mirroring `Runtime.Rails`** — never raises, **never** called from `Application.start/2` (a boot crash takes the host app down, T-53-08), ETS log-once, `{:unknown_grade, key}` on a typo. Refuses at `Params.start/2` (loud, early); at the hot path a malformed value falls back to that grade's shipped default and logs once — refusing every tool call on a config typo is itself the brick. Belt at the cold path, braces at the hot one. Note the coverage is partial by construction: `Params.start/2` is a run-creation entry point, and `MCP.Router`/`MCPController`/direct callers never reach it.
- **D-35 (revised) — The adoption ladder, with rung 2 INVERTED.** The draft claimed `require_tool_classification: true` "structurally eliminates" the unclassified cascade. **False on two counts.** (a) It is bypassable: `resolve_classification/2`'s first clause (`executor.ex:245-247`) matches *any* `%Classification{}` already on the context — including `source: :unclassified_default` — and returns before `refuse_unclassified_tool?/1` is consulted; both `Connectors.Invocation.invoke/4` (`invocation.ex:31,172`) and `Runtime.default_replay_seam/2` (`runtime.ex:703-709`) inject exactly that. (b) Even where it works, "eliminate your false positives by making 100% of your undeclared tool calls error" is an outage with a security rationale — an adopter with 40 tools who has declared 6 takes down 34 tool paths.
  Corrected ladder: **rung 1** upgrade (zero config; every event `grade: unclassified, decision: allow`; zero behavior change). **Rung 2 = declare every tool**, watching `[:scoria, :class, :unclassified]` (already shipped) fall to zero. **Rung 3 = close the ratchet** with `require_tool_classification: true`, only after that counter has been zero for a week — the same discipline the draft correctly applied to its own last rung. **Rung 4** install a real `Trust.Scanner`; **re-size rails AND drain in-flight runs** first (each round trip costs 2 against `max_steps`, and rails freeze at creation, so a run in flight when strict is flipped cannot be re-sized). **Rung 5 (optional)** `strict: true`, only after the infra-failure rate is provably ~0. Also fix (a) by gating on `source` at the idempotence clause.
  **No `mix` preflight task and no refuse-to-boot check:** there is no tool registry to enumerate (`MCP.Router` takes `tools:` as a plug opt and direct `execute/4` callers bypass it), so any static scan is structurally partial and gives false assurance.
- **D-36 — One telemetry event, always emitted, `decision` as a tag** — `[:scoria, :gate, :confluence, :observed]`, `%{}` measurements (the `[:scoria, :class, :unclassified]` shape), metadata carrying grade/decision/combination/action_class/the three leg sources/reason_code/tool_ref/site plus correlation ids (`run_id`/`step_id`/`trace_id` are correlation-only and must **never** be used as metric dimensions). All emits wrapped `try/rescue -> :ok`. Not ReleaseGate's ungated-only shape: an ungated-only event has **no denominator**, which is exactly how Gatekeeper's truncated `dryrun` and CSP `Report-Only`'s unsegmentable noise both failed. **(revised)** The adopter-facing number must be *would-have-paused counts segmented by grade*, never a raw firing count — the raw count is 100% by construction and is the number that makes operators stop looking.

### F — Audit, replay (GATE-03)

- **D-37 — One new `event_type`: `"tool.confluence.escalated"`**, `policy_class: "confluence_gate"`, `actor_ref: "system:scoria.confluence"` — matching the shipped `<domain>.<mechanism>.<verb>` family (`tool.replay.stubbed`, `run.rail.tripped`, `approval.requested`).

GATE-03 says *"every confluence escalation **decision**"*, and a deny is a decision. The volume argument survives intact: rows stay proportional to blocked-or-human-decided events, never to tool calls — which matters because in observe mode the trifecta fires on 100% of legacy traffic.
- **D-39 — No new columns on `ai_audit_outbox_events`.** The verdict rides `metadata` jsonb as the **output of the projector**, never a spread. This is not stylistic: `SRE.build_audit_metadata/1` (`sre.ex:374-416`) is a **drop-list**, not an allowlist — it drops `:args`/`:arguments`/`:raw_args` in atom and string form and passes everything else through, so a spread would leak.

- **D-41 — Write the confluence audit row first, then pass its id into `mark_waiting_for_approval/3`'s `attrs`** (which merges caller attrs straight through — zero `workflows.ex` changes for this part). The failure direction is deliberate: an orphan row saying "the trifecta fired" is the truth and beats a silent unaudited exfil. **`:dedupe_key` must NOT appear in those attrs (revised)** — it would be consumed for the `approval.requested` row too, and a second escalation in the same run would then hit the unique index inside the transaction where `SRE.insert_audit_outbox_event/2` does `repo.rollback` (`sre.ex:166`), failing the **entire** `mark_waiting_for_approval/3`.
- **D-42 — `dedupe_key` is set EXPLICITLY** to `"tool.confluence.escalated:<run_id>:<step_id>:<args_fingerprint>"`. The auto-key composes `event_type:tenant_id:approval_id:trace_id:access_decision` (`sre.ex:422-432`); for a row written before the approval exists, `approval_id` and `access_decision` are `nil` and `Observe.trace_id_for_run(%Run{id: id}) == id` (`observe.ex:203`), so it would collapse to `event_type:tenant_id:<run_id>` and **merge two genuine escalations in one run into a single row** against the existing `unique_index(:ai_audit_outbox_events, [:tenant_id, :dedupe_key])`.
- **D-43 — Phase 57 adds NOTHING to `ReplayDisposition`** — no disposition, no `replay_reason_code`, no `replay_scope`. Placed downstream of `replay_gate/3`'s `{:continue, _}` leg, all three outcomes are already correct: `:historical_stub` ⇒ the tool never executes, so there is no exfil and the gate must not fire (**not** "fires and auto-approves" — building an auto-approve path would create a bypass primitive a bug could reach on a live run); `:blocked` ⇒ unreachable; `:execute_live` during replay ⇒ reachable only via `live_override_approved`, so the call really is re-executing and the gate correctly fires. Verified: `Connectors.Invocation.invoke/4` reaches `Executor.execute/4` only on `{:execute_live, evidence}` (`invocation.ex:41-62`), so the connector seam needs no separate hook.

An approved escalation is NOT a reusable replay grant** — that is approve-once-exfil-forever, and no existing `replay_scope` value expresses "same trifecta, different data." This is Temporal's rule that a human signal is recorded in history and replay must never re-solicit it.

## Specific Ideas

- **Prior art deliberately mirrored:** ReleaseGate's evidence-conditioned enforcement (positive evidence enforces; absence is telemetried, and only a flag makes absence an error) — the doctrine GATE-04 names and D-31 restores. Kubernetes' reversal of admission `failurePolicy` from `Ignore` to `Fail` at v1 GA, and the scoped-opt-in-then-enforce pattern (Pod Security Admission namespace labels, Istio per-workload `STRICT`) — `classification/0` is Scoria's scope label. Temporal's rule that a human signal lives in event history and replay never re-solicits it (D-43/D-44).
- **Prior art deliberately avoided:** CSP `Report-Only` as a terminal state; Istio `PERMISSIVE` meshes that never reach `STRICT`; Gatekeeper `dryrun` whose signal truncates exactly at the scale you need it; LangGraph `interrupt()`'s re-execution-on-resume footgun (D-26); Perl `untaint` as a rubber stamp (D-12); LangChain `ToolMessage.status` dead metadata — the classification MUST terminate in a decision or it is decorative.
- **The phrase to keep saying out loud:** all three legs are, today, **declaration-sourced**. The gate is a static analysis over adopter-declared tool metadata plus (post-D-01) real-scanner verdicts. That may be the right v1, but the milestone's story is "the taint substrate feeds the gate," and until D-01 and D-02 are resolved that story is not what ships.
