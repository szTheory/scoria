<objective>
Make every confluence decision durably auditable and its outcome reconstructable from persisted evidence, reusing the existing outbox machinery with zero new columns.

Purpose: GATE-03 asks that every confluence escalation DECISION be written to the audit outbox and be replayable, consistent with existing approval and replay evidence. A deny is a decision, and denies currently have no durable record anywhere — the tool-completed event does not fire on a refusal and the gate's telemetry event is ephemeral because Scoria persists telemetry only through span adapters, which handle completion, timeout and failure. This plan closes that.

It also pins the replay contract negatively: Phase 57 contributes NO `ReplayDisposition` value, which is what structurally defuses the fail-open fall-through hazard instead of merely mitigating it, and it proves that an approved escalation is not a reusable execution grant.

Output: audit rows on escalate and block with an explicit dedupe key and an approval back-link, a small closed metadata projector, and replay-contract tests.
</objective>

  <action>
Write ONE audit outbox row per confluence decision that is an escalate or a block, and none on an allow. Use the existing SRE audit outbox creation function unmodified; add no columns to the outbox table.

Set the event type to `"tool.confluence.escalated"`, matching the shipped domain-mechanism-verb family alongside the existing replay-stubbed, rail-tripped and approval-requested types. Set the policy class to `"confluence_gate"` and the actor reference to `"system:scoria.confluence"`.

Write the row on BLOCK as well as on escalate (D-38). Both the unattributed deny under a strict configuration and the rejected-approval deny are decisions, and neither has a durable record anywhere else: the tool-completed event does not fire on a refusal, and the gate's telemetry event is persisted only through span adapters that handle completion, timeout and failure. The volume argument survives intact because rows stay proportional to blocked-or-human-decided events, never to tool calls — which matters because under an observe posture the trifecta fires on effectively all legacy traffic.

Set the dedupe key EXPLICITLY to a value composed of the event type, the run id, the step id and the args fingerprint (D-42). Do not rely on the automatic builder: for a row written before the approval exists, the approval id and access decision are both nil and the trace-id-for-run helper returns the run id itself, so the auto key would collapse to event type plus tenant plus run id and would merge two genuine escalations in one run into a single row against the existing tenant-and-dedupe-key unique index.

Order the writes deliberately: write the audit row FIRST, then pass its id into `mark_waiting_for_approval/3`'s attrs so the created approval carries it as its blocker audit outbox event id, alongside the confluence blocker kind (D-40, D-41). This needs zero changes in the workflows module because that function merges caller attrs straight through. The failure direction is deliberate: if the pause transition then fails, the orphan audit row saying the trifecta fired is the truth and beats a silent unaudited exfil.

Do NOT include a dedupe key in the attrs handed to `mark_waiting_for_approval/3` (D-41). It would be consumed for the approval-requested row that function writes as well, and a second escalation in the same run would then hit the unique index inside the transaction where the in-transaction insert performs a rollback, failing the ENTIRE pause transition.

Read the blocker audit outbox event id defensively wherever it is consumed downstream — the column is a bare binary id with no foreign key, so it can legitimately be nil or dangling (D-40).

Write the tests first in a new `test/scoria/confluence_audit_test.exs`, covering every behavior above. The two-escalations-in-one-run case is the load-bearing one for D-42: assert two distinct rows exist with two distinct dedupe keys.
