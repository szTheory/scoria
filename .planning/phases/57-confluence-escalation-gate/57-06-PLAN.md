<objective>
Build the per-run leg accumulator: a strongest-wins, lit-legs-only, single-statement jsonb fold that gives the gate the two exposure legs a run has accumulated, while the exfil leg stays per-call.

Purpose: plan 01's tracer escalates only when one tool declares all three legs at once. The real confluence case is distributed — an earlier step reads private data, a later step ingests untrusted content, and a third step calls an exfil-capable tool. That case is only reachable through run-scoped accumulation, and CONTEXT.md names three ways the naive implementation silently disables the gate: a first-wins merge lets ordering luck (or an attacker choosing which tool runs first) pin a leg to its weakest grade for the rest of the run; writing the full three-leg map freezes an early false; and a read-then-write pair opens a time-of-check window between concurrent tool calls in one run.

Output: a correct accumulator, its wiring into the gate's evaluation, non-swallowed write failures, and per-leg witness detail rich enough for Phase 58 to re-derive the classification.
</objective>

Implement STRONGEST-WINS per leg, not first-wins. Rank witness sources numerically with the declared source strongest, then observed scanner evidence, then the default tier, then unclassified weakest, and select the per-leg maximum. A plain jsonb concatenation cannot express strongest-wins — it preserves the FIRST witness — and composed with the weakest-evidence grading a leg first lit by a default-tier observation would be pinned to the default-tier grade for the rest of the run no matter how strong the later evidence, so ordering luck or an attacker choosing which tool runs first would permanently silence the gate. Express the per-leg maximum in the update expression, or take a read-modify-write under the run row's existing lock; do NOT paper over it with a plain concatenation, and note in a comment that no shape-based test catches that mistake, which is why the ordering-independence test below is mandatory.

Write ONLY lit legs. Never write a false value and never write an absent leg — writing the full three-leg map on every call would freeze the first call's negatives permanently under any merge order.

Do NOT swallow a failed write. `persist_taint_to_step/3` and `persist_classification_to_step/3` both rescue to an ok result; copying that discipline here would mean a failed merge produces no leg, no escalation and no signal, which is a silent fail-open on the security control under strict mode. The observe-layer rule that the mechanism must never break host business logic still applies — do not crash the call — but the rescue must emit a fallback telemetry event carrying the run id and the failure reason (D-16).

Add a comment at the fold recording the accepted limitation honestly: this adds a SECOND exclusive lock on the run row per tool call on top of the rail counter, doubling the serialization window that 56.1 D-09 already documented as accepted. Accept and document; do not present it as free (D-17).
