## Spacing Scale

Declared values (must be multiples of 4):

| Token | Value | Usage |
|-------|-------|-------|
| xs | 4px | Dot indicators, inline separators, micro badge spacing |
| sm | 8px | Status chip padding, compact row gaps, metadata label spacing |
| md | 16px | Default card padding, body rhythm, progress legend spacing |
| lg | 24px | Section padding inside matrix cards and detail panels |
| xl | 32px | Gaps between dashboard modules and sub-sections |
| 2xl | 48px | Separation between summary band, health matrix, and campaign board |
| 3xl | 64px | Page-level top and bottom breathing room on desktop |

Exceptions: 44px minimum hit area for campaign-row selection, filter chips, drawer toggles, and cancel actions; progress bars may use 12px height for dense matrix readability.

## Typography

| Role | Size | Weight | Line Height |
|------|------|--------|-------------|
| Body | 14px | 400 | 1.5 |
| Label | 12px | 600 | 1.4 |
| Heading | 18px | 600 | 1.25 |
| Display | 30px | 600 | 1.15 |

### Type Rules

- Keep exactly two weights in this phase: `400` for narrative and metadata, `600` for headings, counters, and selected-state emphasis.
- Use uppercase tracked labels only for section markers, queue/state labels, and compact matrix headings.
- Use monospace only for model IDs, provider:model pairs, campaign IDs, eval run IDs, queue labels, and typed failure/fallback reasons.
- Do not introduce smaller-than-12px text or larger-than-30px display text; density should come from grouping and hierarchy, not text shrinkage.

## Color

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | #F8FAFC | App canvas, dashboard background, empty-state canvas, inactive matrix backdrop |
| Secondary (30%) | #FFFFFF | Health cards, campaign cards, detail drawers, drill-in panels |
| Accent (10%) | #2563EB | Selected campaign row, selected model cell outline, primary deep link, active filter chip, and fallback drill-in link |
| Destructive | #BE123C | Cancel campaign action, fatal failure alert band, destructive confirmations only |

Accent reserved for: selected campaign row, selected model-health cell, `Inspect Campaign Progress`, `View Eval Run`, active queue/status filter, and the single fallback lineage link within a detail panel. Do not use accent for every status badge or every metric.

### Semantic State Colors

- `healthy`: `#047857` text on pale emerald background; use for closed/healthy breaker posture and completed-success counts.
- `degraded`: `#B45309` text on pale amber background; use for fallback activity, elevated retries, or mixed success posture without fatal breakage.
- `open`: `#B91C1C` text on pale rose background; use for breaker-open models and fatal campaign states.
- `queued`: neutral stone palette; queued work is pending, not warning.
- `running`: sky-tinted neutral panel with blue text accents limited to progress movement and live selection.
- `completed_partial`: amber-toned status band; partial completion must never look identical to full success.
- `cancelled`: muted stone badge with explicit cancellation label.

## Copywriting Contract

| Element | Copy |
|---------|------|
| Primary CTA | Inspect Campaign Progress |
| Empty state heading | No Evaluation Campaigns Yet |
| Empty state body | Campaign progress appears here after an operator launches a distributed evaluation. Use the model health matrix to confirm provider posture before starting a new campaign. |
| Error state | Real-time dashboard data could not be loaded. Refresh the dashboard; if the issue persists, inspect the persisted campaign and eval-run records to confirm durable state. |
| Destructive confirmation | Cancel Campaign: Cancel this campaign? Running targets may still finish because cancellation is best-effort. Completed eval runs and recorded scores will remain available for audit. |

### Copy Rules

- Status language must match durable phase semantics exactly: `queued`, `running`, `completed`, `completed_partial`, `failed_fatal`, and `cancelled`.
- Model health language must be typed and operator-legible: `Healthy`, `Degraded`, `Open`, or `Unknown`.
- Fallback language must be explicit: use `Fallback used` or `Primary model succeeded`; never imply fallback is an error when the target ultimately completed.
- Counter labels must say what is counted: `completed targets`, `failed targets`, `fallback targets`, `breaker-open models`.
- Any cancel copy must repeat that cancellation is best-effort, not transactional.

## Phase-Specific Visual Contract

- Keep the primary surface inside the existing `/scoria` dashboard. Do not introduce a separate fleet-console visual language or a new design system for this phase.
- The dashboard root must read in three vertical bands:
  - summary strip with campaign counts and breaker-open count
  - model health matrix
  - live campaign progress board with an inline detail panel
- The model health matrix is the top diagnostic surface. Each configured provider:model pair gets one compact card or cell showing current health, current breaker posture, recent fallback activity, and last-seen freshness.
- The campaign progress board is the operational truth surface for this phase. Each campaign row must surface, in this order:
  - campaign status
  - eval spec identity
  - tenant scope
  - total target count
  - stacked progress counts
  - fallback usage summary
  - latest progress timestamp
  - primary drill-in action
- The detail panel for a selected campaign must remain inline below or beside the campaign list, not in a modal. Operators need stable context while watching live progress updates.
- Use calm emphasis. The only saturated focal points should be:
  - breaker-open model cards
  - selected campaign row or model cell
  - explicit fatal or cancel alerts
  - fallback drill-in link when a target used a secondary model

## Component Inventory

- Summary strip: four compact cards for `active campaigns`, `completed today`, `fallback targets`, and `breaker-open models`.
- Model health matrix: grid of provider:model cells grouped by provider, each showing health badge, breaker state, fallback count, and last update age.
- Health detail drawer or inline expansion: selected model metadata with provider, model name, current breaker state, recent fallback indicator, and linked active campaigns using that model.
- Campaign progress board: stacked list of active and recent campaigns ordered by `last_progress_at` descending.
- Campaign row: status pill, eval spec/version, tenant label, total-target count, segmented progress bar, per-state counts, fallback count, and primary action.
- Segmented progress bar: ordered segments for `queued`, `running`, `completed`, `failed`, and `cancelled`; partial completion must remain visually distinguishable.
- Campaign detail panel: selected campaign headline, terminal or live status, timestamps, aggregate counters, target shard table, and durable lineage links.
- Target shard table: one row per target with tenant, provider:model, current status, fallback indicator, linked eval run, and latest error reason when present.
- Empty-state card: rendered when there are no campaigns yet; model health matrix still renders if model configuration exists.

## Interaction Contract

- Subscribe the dashboard to live campaign and model-health projection topics when connected, but treat PubSub as a projection layer over durable Ecto truth rather than the source of truth itself.
- Selecting a campaign row updates the inline detail panel without leaving the page. Selection must persist across live refreshes when the campaign is still present in the list.
- The primary action on each campaign row is `Inspect Campaign Progress`. It selects the row and scrolls the detail panel into view on smaller screens.
- The primary action inside target rows is `View Eval Run` when an eval run exists. That action navigates to the durable run surface rather than opening a modal.
- Model health cells support one secondary action: open health details. Do not overload matrix cells with multiple inline buttons.
- Fallback usage is shown as a visible badge or count on both campaign rows and target rows. A target that completed via fallback must not be visually grouped with ordinary primary-path completions.
- Progress updates must animate by number change and bar-width movement only. Do not use flashing pulses, color cycling, or transient toast spam for ordinary completion updates.
- Live updates must be monotonic from the operator’s perspective:
  - counts can increase
  - status can advance to a terminal state
  - a row must not visually jump backward unless durable truth changed and the detail panel explains the reason
- Cancel actions open an inline confirmation panel. The confirmation must state best-effort semantics before the operator confirms.

## State Contract

- `No campaigns yet`: neutral empty card with the empty-state copy above; model health matrix still visible.
- `Campaign queued`: stone-toned status pill with all progress in the queued segment.
- `Campaign running`: blue-neutral live state with active progress movement and `last updated` label.
- `Campaign completed`: emerald success pill with all targets resolved and no fatal/partial warning.
- `Campaign completed_partial`: amber status pill with completed and failed segments both visible.
- `Campaign failed_fatal`: rose alert band with fatal reason summary and affected campaign still drillable.
- `Campaign cancelled`: muted stone badge with explicit cancellation label and completed work preserved in counts.
- `Model healthy`: emerald chip with closed/healthy breaker label.
- `Model degraded`: amber chip indicating fallback activity or elevated retry posture without breaker-open state.
- `Model open`: rose chip indicating breaker-open posture; the matrix cell should become the strongest visual warning on the page.
- `Fallback used`: amber inline badge attached to the target row and included in campaign rollup counts.
- `Unknown health`: neutral chip used only when configuration exists but live posture cannot be resolved.
- `Detail load failed`: inline failure state inside the panel or shard table, never a page-level blocking overlay.

## Assumptions

- The phase stays within the existing embedded `/scoria` dashboard posture rather than introducing a dedicated standalone eval-ops application.
- Phase 33 durable campaign truth is available through `EvalCampaign`, `EvalCampaignTarget`, and `EvalRun` lineage fields before this dashboard work lands.
- Model health remains node-local ETS truth for this milestone; the dashboard therefore visualizes the current node’s effective breaker/fallback posture, not a cluster-wide quorum.
- No third-party component registries or icon packs are required for this phase.
