# Phase 12: Design-System Component Layer - Context

**Gathered:** 2026-06-04
**Status:** Ready for planning

<domain>
## Phase Boundary

Phase 12 builds the **enforced token gateway**: expose in `lib/scoria_web/ui.ex` the shared HEEx function components the CSS already supports (`<.table>`, `<.drawer>`, `<.modal>`, `<.field>`/`<.form_section>`, `<.notebook>` shell, `<.skeleton>`, `<.toast>`), fix `flash_group` to route through semantic tokens, and stand up an executable raw-palette drift guard.

This phase **builds and proves the components**. It does **not** convert screens or evidence panels — the roadmap distributes that work:
- **Phase 14** converts Review Queue / Incidents / Eval Workbench / Prompt Registry+Release.
- **Phase 15** converts high-traffic screens **and the 13 evidence components into thin `<.notebook>` adapters.**
- **Phase 17** drives raw-color count → 0 (final consistency sweep + proof).

Therefore Phase 12 is NOT responsible for removing all ~498 lines / 623 raw-palette occurrences across 23 files. It stands up the guard and sweeps only `ui.ex` itself plus any file it touches.
</domain>

<decisions>
## Implementation Decisions

### GA1 — Drift-guard activation & migration scope (DS-06)
- **D-01:** DS-06 ships as a **ratchet baseline guard**, not a full repo-wide sweep. Implement `test/scoria_web/ds06_drift_guard_test.exs` (ExUnit, per LiveViewTest-only posture) that scans `.ex`/`.heex` under `lib/scoria_web/` for raw palette classes (`~r/\b(stone|rose|sky|emerald|amber|blue|gray|slate|zinc|neutral|red|green|yellow|purple|pink|indigo|teal|cyan|lime|orange|violet|fuchsia)-\d/`).
- **D-02:** Commit a baseline file (e.g. `test/support/ds06_baseline.txt`) of `path:count` pairs generated by running the scanner once. The test **fails** if: any baselined file's count *exceeds* its baseline, OR any file **not** in the baseline has a nonzero count. New code can never introduce raw palette; existing screens are grandfathered at their current count.
- **D-03:** `lib/scoria_web/ui.ex` is swept to **zero** raw-palette occurrences immediately (the gateway must be self-consistent) and is **excluded** from the baseline. Any other file Phase 12 touches drops to zero and is excluded too.
- **D-04:** **Ratchet ownership downstream:** Phases 14 and 15 remove their screens' rows from the baseline as part of their own success criteria; **Phase 17 deletes the baseline file entirely and flips the guard to strict zero-tolerance** — the form the UI-SPEC's "failure message" example describes.
- **D-05:** **Criterion-#5 reconciliation:** Phase 12 success criterion #5 ("the build fails if any raw palette class appears") is satisfied in spirit — the guard exists, is wired into `mix test`, and makes raw palette unable to *return* or *grow*. The codebase is not at zero until Phase 17; the **token gateway** is clean now.

### GA2 — Evidence notebook conversion scope (DS-04)
- **D-06:** Phase 12 builds the unified `<.notebook>` shell (tabbed, slot-based, per UI-SPEC DS-04 API). Full conversion of the 13 evidence components into adapters is **Phase 15** (roadmap-owned) — out of scope here.
- **D-07:** Prove the shell by converting exactly **one** thinnest evidence component into a `<.notebook>` adapter (outer shell only, internals untouched). Planner picks the lightest candidate (e.g. `trace_tree_component` at ~7 palette occurrences, or `remote_invocation_evidence_component`). This validates the slot/tab contract without pulling Phase 15 work forward.

### GA3 — Component adoption / API proof
- **D-08:** **No full-screen migration in Phase 12.** All screen conversion stays in Phases 14/15 per roadmap. Phase 12 stays tightly scoped to "the gateway."
- **D-09:** Component APIs are validated via **`render_component`/LiveViewTest unit tests** for each new component, plus the DS-05-mandated real wiring (see GA4). Rationale: `ui.ex` is **internal app code, not a shipped Hex library**, so a late API tweak when Phase 14 becomes the first real screen consumer is cheap and low-stakes — no public-API-freeze pressure justifies pulling screen work forward.

### GA4 — Toast & skeleton wiring (DS-05)
- **D-10:** `<.toast>` is driven by a **server-held assign list** (`@toasts`) via a `put_toast/2` helper, mirroring the existing `put_flash/3` + `flash_group` pattern already proven in `approvals_live.ex`. **Not** `push_event` + JS hook — that path is invisible to `LiveViewTest` (hooks are no-ops in test env) and would create false-green CI under the LiveViewTest-only posture.
- **D-11:** Auto-dismiss uses pure `Phoenix.LiveView.JS` — `phx-mounted={JS.hide(to: ..., transition: ..., time: duration_ms)}` — no custom JS hook. Tests assert the toast renders via `render(view) =~ ...`; the disappear-after-N-ms timer is acceptably unasserted.
- **D-12:** Wire **one real end-to-end path** in Phase 12 to validate plumbing: a genuine server-triggered toast (an approvals/promote/gate action that already calls `put_flash`) and **one real `<.skeleton>` loading state** on a screen with an async load. This is the only real wiring Phase 12 does and is mandated by DS-05 regardless.

### `flash_group` fix (DS-05)
- **D-13:** Replace the raw-palette `flash_tone_class/1` in `ui.ex` (lines ~195–197) with semantic BEM modifiers (`scoria-flash--fail/info/warn/pass`) and add the `.scoria-flash` CSS to `assets/css/04-components.css` exactly as specified in UI-SPEC DS-05. Flash banners carry a tone-keyed 16×16 SVG icon (status never by color alone).

### Claude's Discretion
- Exact internal HEEx structure of each component, helper function names, test file organization, and which specific thinnest evidence component / which real toast+skeleton paths to wire — planner/researcher decide, constrained by the UI-SPEC contract and the decisions above.
</decisions>

<code_context>
## Existing Code Insights

### Reusable Assets
- **`ui.ex` existing components** (`badge`, `button`, `panel`, `empty_state`, `eyebrow`, `metric`, `tone/1`) — new components compose with these; `tone/1` already maps domain status → tone atom for badges/flash/toast.
- **Existing CSS classes** (`.scoria-table`, `.scoria-modal__panel`, `.scoria-drawer`, `.scoria-scrim`, `.scoria-input`, `.scoria-button--ghost/--sm/--primary/--danger`) — the function components are thin HEEx wrappers over CSS that already exists. This is why the phase is "expose what the CSS already supports," not net-new design.
- **`flash_group` + `put_flash` pattern in approvals** — directly reusable as the toast plumbing template.

### Established Patterns
- **LiveViewTest-only posture** — no Wallaby/headless browser in CI. Drives DS-06 as an ExUnit test (not a Mix compiler) and drives the server-assign toast mechanism (testable) over JS-hook (untestable).
- **Token-first scoped CSS, `ui.ex` as gateway** — no Tailwind utility / BEM switch (locked in STATE.md). Components emit semantic class names only.
- **Slot-based shells** — drawer/modal/notebook/field all use HEEx slots; parent LiveView owns state (sort, density, selected_tab, show, on_dismiss) and components emit `phx-click` events.

### Integration Points
- `flash_group` is rendered in the layout (`app.html.heex`) above main content — the flash fix lands there.
- `<.toast>` needs a mount point (likely the layout) + a `@toasts` assign + `put_toast/2` helper threaded into one real action handler.
- DS-06 baseline file is read at test time; regenerated when Phases 14/15 shrink it.

### Raw-palette reality (DS-06 baseline seed)
- 23 files under `lib/scoria_web/` currently contain raw palette (~498 lines / 623 occurrences). Heaviest: `review_queue_live.ex` (76), `incident_evidence_component.ex` (69), `dataset_live/promote_component.ex` (68), `workflow_live/show.ex` (55), `delegated_evidence_component.ex` (46), `prompt_live/release_workbench_live.ex` (42). The 7–8 evidence components hold ~190–217 of them. These seed the committed baseline; Phase 12 only zeroes `ui.ex` (~9) + any file it touches.
</code_context>
