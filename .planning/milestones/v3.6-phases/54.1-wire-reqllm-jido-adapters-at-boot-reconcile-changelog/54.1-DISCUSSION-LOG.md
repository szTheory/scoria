## Jido dep status — SC#1/SC#2

| Option | Description | Selected |
|--------|-------------|----------|
| a. Presence-gate via `Code.ensure_loaded?(Jido)` (Sentry optional-integration style) | Researcher A's initial rec | |
| b. Unconditional attach (mirror MCP verbatim) | The adapter references zero `Jido.*` modules, so a gate guards nothing; dormant handler is a harmless idle ETS row; MCP is the precedent | ✓ |
| c. Opt-in / skip; or make `jido` an `optional: true` dep | Re-creates the void; optional dep adds version-conflict surface + support commitment for a package Scoria never calls | |

**User's choice:** b — unconditional attach, jido stays dependency-free (D-02).
**Notes:** This was the one sharp inter-researcher disagreement. Red-team T1 resolved it decisively: `lib/scoria/observe/adapters/jido.ex` has no `Jido.*` references, so `Code.ensure_loaded?(Jido)` is misleading ceremony ("presence" is already self-enforcing at the telemetry layer). Symmetry with the unconditional MCP boot-attach is the most coherent outcome. Aligns with project doctrine (optional integrations are not hard deps; adapters-not-NIH).
